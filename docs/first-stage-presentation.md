2. **（0:09–0:25）** 一方、カタログの閲覧は1日およそ200PV。原因は「1データ＝1アプリ」という活用の型です。アプリが作られたデータしか、誰にも届きません。

## 3. v1.0 からの変更点

### なぜ全面差し替えたか

v1.0（2026-08-15）の台本は、その後1週間の実装と乖離した。特にスライド4の「MCPでアプリに接続します」は**現在も事実ではない**（MCP は Step 5 未着手で、実際は React → `/api/*`）。「根拠がなければ答えない」を掲げる資料が根拠のない主張をすることになるため、部分修正ではなく全面差し替えとした。

| v1.0 の主張 | 判定 | 実測（2026-08-21） |
| --- | --- | --- |
| #3「UIは実装済み」5画面 | 一部誤り | 動くのは3画面（プロフィール／プラン／あなたへ）。スキャン・周辺は `AppTabs.tsx` の `INACTIVE_TABS` で disabled |
| #4「MCPでアプリに接続します」 | 誤り | 台本 v2.0 執筆時点では MCP 未着手で、`/api/*` のコア3操作で接続していた。**その後 `/mcp` は実装・デプロイされ、2026-08-22 時点では本番で3ツールを公開している**（[Issue #117](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/117)）。ただし React 側は引き続き `/api/*` を呼ぶ（[ADR-008](06-reference/DECISIONS.md)。React に MCP クライアントを実装するのは禁止）ため、「MCPでアプリに接続します」は**現在も誤り** |
| #4「出典100%・CC BY 自動準拠」 | 真 | 10件全て CKAN `package_show` で検証済み |
| #5「浅草と上野、ラーメンが好き」 | 真 | `insufficient_granularity` を理由付きで返す実装が稼働 |
| #6「未回答を都へ自動還元」 | 真（記録まで） | `gaps` は本番 D1 で実際に行が増える。都への提出プロセスは構想 |
| #7「30分→3分」 | 未実測 | 企画時の推定値 |

### 構成順を変えた2点

1. **山をスライド4に前倒しした。** v1.0 では「答えられない」は #6 で1行触れるだけだった。実際には理由付きで返す画面が動いており、他チームが再現できない差別化はここにしかない。前半3枚で「出典が付く」を見せてから、4枚目で「付けられないときは答えない」に落とすと、5枚目の仕組み説明が「なぜそうなるか」の答えとして機能する。
2. **MCP を主語から外した。** #5 を「稼働中の `/api/*` ＋出典強制」に置き換え、MCP と OSS 公開は #7 で**これからの開放計画**として一括で扱う。

### #7 に尺を確保した理由

基盤開放と OSS は、審査員から質問が飛びやすい割に、話者（shiwata＝発起人／プレゼンター）が実装から最も遠いパート。v1.0 の配分ではここにインパクト（30分→3分）まで詰め込むことになり、OSS が早口の従属節に潰れる。インパクトは #8 のクロージングへ一言だけ折り込み、#7 は「MCP サーバーとして開放予定／コンシェルジュを別リポジトリへ切り出し MIT で公開予定」の2点に絞った。

## 4. 収録メモ

- **動画埋め込みは #3 と #4**。素材は**本番アプリの画面収録**（<https://tabi-concierge-tokyo.opendata-002.workers.dev>）。`public/showcase/` は使わない（使う場合のみ `fonts.googleapis.com` 依存でオフライン時に崩れるため事前のネットワーク確認が必要）
- **BGM は使用しない**（主催者規定）。音声合成を使う場合は合理的理由が要る（[CONSTRAINTS.md](01-context/CONSTRAINTS.md) §3）
- **尺の実測はスライド単位で行う。** 全体で 1:55 に収まっても、1枚ずつの尺がずれていると収録時に映像と音がずれる。超えた枚だけ削る（R-01）
- スライド内のタイムコード（右上）はペース配分用。本番書き出し前に非表示化する
- 提出用キャプチャ（1600×900px・1〜3点）は[提出資料側](submission-deck.md) §5 のチェックリストで管理する
