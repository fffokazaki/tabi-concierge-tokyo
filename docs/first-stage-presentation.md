# First Stageプレゼン｜提出資料から選ぶ8枚＋2分台本

- 収録: 2026-08-26〜30（チームの収録枠は未確定）
- 制限: **2分厳守・超過は強制終了・ライブデモ一切不可・BGMなし**
- 使用資料: 提出済みの [submission-deck.md](submission-deck.md) に対応する14枚のPPTX
- 発表時間: **1分55秒**（5秒を強制終了回避の余白として残す）
- 台本: **513字**。各スライドの上限は「持ち時間 × 毎秒4.8字」で管理する

## 1. 発表方針

審査員が2分後に、**旅コンシェルジュTOKYOは、出典を付けられない問いには答えを作らず、その未回答を次のオープンデータ改善につなげるAI旅行ガイドである**と理解できる構成にする。

First Stage専用の新しいスライド内容は作らない。提出済み14枚のうち、次の8枚を**提出資料の番号のまま**使う。

`1 → 2 → 3 → 6 → 8 → 9 → 10 → 13`

PowerPointでは提出済み原本を変更せず、発表用コピーの「目的別スライドショー」または非表示設定で上記8枚だけを表示する。静止画だけで成立させ、外部動画やライブ操作には依存しない。

## 3. トークスクリプト

### 提出資料1｜0:00–0:09

東京都の約9,600のオープンデータを、旅の相棒に。旅コンシェルジュTOKYOです。

### 提出資料2｜0:09–0:24

東京都は約9,600件を公開していますが、カタログ閲覧は1日約200PV。1データごとにアプリを作る形では、多くのデータが利用者まで届きません。

### 提出資料3｜0:24–0:35

訪日旅行者も、文化やマナーに迷ったとき、必要な公共データへたどり着けず、検索の前で立ち止まります。

### 提出資料6｜0:35–0:50

そこで、プロフィールから旅程をつくるAIガイドを実装しました。提案には、データセット名、提供元、取得日、ライセンスを出典として表示します。

### 提出資料8｜0:50–1:09

私たちの特徴は、答えを作らないことです。「ラーメンが好き」という問いに対し、対象210件中ラーメン店は3件、上野・浅草には0件。粒度不足と判定し、理由とともに未回答を返します。

### 提出資料9｜1:09–1:24

自然文をメタデータRAGで構造化し、Text-to-SQLでD1を実照会。最後に出典を強制します。同じ3操作はMCPでも公開しています。

### 提出資料10｜1:24–1:38

答えられなかった問いは、ギャップとして記録し、分類して束ねます。将来は、東京都へのオープンデータ公開リクエスト案につなげます。

### 提出資料13｜1:38–1:55

体験と操作一巡に基づく目安で、探索は約30分から約3分へ。公開されているだけのデータを、旅の意思決定に届くデータへ変えます。

## 4. 発表で使わないスライド

| 提出資料の番号 | 外す理由 |
| --- | --- |
| 4 | 解決策の要点はスライド6と8で具体的に示せるため |
| 5 | 5画面の全体像より、稼働中の画面と差別化を優先するため |
| 7 | マナーの価値はスライド3の課題に含め、2分版では出典付き旅程へ集約するため |
| 11 | OSS公開予定は将来計画であり、稼働中の価値を優先するため |
| 12 | 10件の詳細一覧は読み上げず、質疑で提示するため |
| 14 | 冒頭でチーム名を名乗り、2分版ではプロダクトの結論を優先するため |

## 5. 収録・練習メモ

- 話者は各スライドの文章を読み終えたら、間を足さずに次へ送る。スライド13だけは結論を残すため、意識してゆっくり話す
- 台本にない数値や実装範囲を即興で足さない。特に「東京都への公開リクエスト案」は**将来**、「30分→3分」は**体験と操作一巡に基づく目安**として扱う
- スライド6と8は提出済みの静止画を使う。ライブ操作・外部動画・BGMは使わない
- 収録枠が決まっていなくても、台本の練習と計測は進められる。実測結果は [Issue #132](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/132) に残す
