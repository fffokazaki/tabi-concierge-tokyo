# DOMAIN.md - ドメインモデル設計書

## 1. ドメイン概要

### ビジネスドメイン

東京都のオープンデータを、訪日観光客の旅の意思決定に変換する領域。中心にあるのは「答え」ではなく「**根拠を伴う答え**」であり、根拠（出典）を提示できないことは欠陥ではなく、次のデータ公開につながる情報として扱う。

### コアドメイン

**出典付き回答の生成と、未回答の還元**。

- すべての回答は1件以上のデータセットに裏付けられる（出典強制）
- 裏付けられない質問は「未回答」として記録され、データ公開リクエストに変換される

この2つが本プロジェクトの競争力の源泉であり、旅程生成やスポット推薦は出典付き回答の応用にすぎない。

### サブドメイン

- **旅体験**: 旅行者プロフィール、旅程、文化・マナー案内、スポット推薦（フロントエンドの5機能）
- **データ回答**: データセット検索、集計、出典生成（オープンデータ・コンシェルジュ）
- **改善還元**: 未回答の分類、データ公開リクエスト、あるべき姿レポート

## 2. 境界づけられたコンテキスト

### コンテキストマップ

```
┌────────────────────┐   MCP    ┌──────────────────────┐
│ 旅体験コンテキスト │ ───────► │ データ回答コンテキスト │
│ (旅コンシェルジュ) │ ◄─────── │  (コンシェルジュ)     │
└────────────────────┘  出典付き └──────────┬───────────┘
                          回答              │ 未回答イベント
                                            ▼
                              ┌──────────────────────────┐
                              │   改善還元コンテキスト     │
                              │ (東京都/GovTech東京へ)    │
                              └──────────────────────────┘
```

### 各コンテキストの定義

| コンテキスト名 | 責務 | 統合方式 |
| -------------- | ---- | -------- |
| 旅体験 | 旅行者の入力を受け、旅程・マナー・推薦として提示する | `/api/*` クライアント（ADR-008。MCP クライアントは実装しない） |
| データ回答 | オープンデータから答えを組み立て、出典を強制付与する | `worker/core/` を `/api/*`（[API.md](./API.md)）と `/mcp`（[MCP.md](./MCP.md)）の二面で公開 |
| 改善還元 | 未回答を分類し、都への提案に変換する | 内部イベント → 定期レポート |

**関係の性質**: 旅体験は下流、データ回答は上流。上流は旅行アプリ固有の語彙（旅程・マナー）を知らない。これが「旅行アプリは最初のクライアントにすぎない」という方針を構造で担保する。

## 3. エンティティ定義

### コアエンティティ

| エンティティ | 識別子 | 責務 |
| ------------ | ------ | ---- |
| データセット（Dataset） | カタログのデータセットID（例: `t000029d0000000021`） | オープンデータの実体とメタ情報を保持する。出典の源 |
| 質問（Question） | 質問ID | 旅行者の問いかけ。回答済み / 未回答の状態を持つ |
| 回答（Answer） | 回答ID | 質問に対する結果。**必ず1件以上の出典を伴う** |
| 旅程（Itinerary） | 旅程ID | 日付・エリア・スポット列で構成される旅の計画 |
| スポット（Spot） | スポットID | 訪問先。オープンデータ由来のものと、データに存在しないものを区別する |
| データ公開リクエスト（DataPublicationRequest） | リクエストID | 未回答から生成された都への提案 |

### エンティティ一覧

| エンティティ | 所属コンテキスト | 永続化 |
| ------------ | ---------------- | ------ |
| データセット | データ回答 | 同梱静的ファイル（[DATABASE.md](./DATABASE.md)） |
| 質問 / 回答 | データ回答 | 未定（POC では保持要否を実装時に判断） |
| 旅程 / スポット | 旅体験 | クライアント内（永続化しない） |
| データ公開リクエスト | 改善還元 | 未定（集計対象として保持が必要） |

## 4. 値オブジェクト

### 主要な値オブジェクト

| 値オブジェクト | 構成要素 | 不変条件 |
| -------------- | -------- | -------- |
| 出典（Provenance） | データセットタイトル / URL / 提供元 / ライセンス表記（CC BY 4.0）/ 実行クエリ / 取得日 | URL と提供元は必須。欠けた出典は生成できない |
| 旅行者プロフィール（TravelerProfile） | 同行者 / 興味 / ペース | 個人を特定する情報を含まない |
| エリア（Area） | エリア名（渋谷・上野・浅草 等） | POC では代表エリアに限定 |
| 未回答理由（GapReason） | 分類（データ未公開 / 粒度不足 / 対象エリア外 / その他） | 必ずいずれかに分類される |

### 値オブジェクト一覧

すべて不変（生成後に変更しない）。等価性は構成要素の値で判定する。

## 5. 集約

### 集約の境界

- **回答集約**: 回答（ルート）＋ 出典のコレクション。出典を伴わない回答は集約として成立しない
- **旅程集約**: 旅程（ルート）＋ スポット列。各スポットは自身の出典を持つか、「データなし」であることを明示する
- **リクエスト集約**: データ公開リクエスト（ルート）＋ 元になった未回答のコレクション

### 集約ルート

| 集約ルート | 不変条件 |
| ---------- | -------- |
| 回答 | `出典の件数 >= 1` |
| 旅程 | すべてのスポットが「出典あり」または「データなし（明示）」のいずれか |
| データ公開リクエスト | 少なくとも1件の未回答に紐づく |

## 6. ドメインサービス

### サービス定義

| サービス | 責務 | 備考 |
| -------- | ---- | ---- |
| データセット特定サービス | 質問から候補データセットを選ぶ（メタデータRAG） | 単一エンティティに属さないため独立 |
| 集計サービス | データセットに対する集計を実行する（Text-to-SQL） | 実行クエリを出典へ引き渡す |
| 出典生成サービス | データセットと実行クエリから出典を組み立てる | **全回答の通過点** |
| 欠損分類サービス | 未回答を理由分類し、リクエスト候補に変換する | 改善還元コンテキスト |

## 7. ドメインイベント

### イベント定義

| イベント | 発生契機 | 購読者 |
| -------- | -------- | ------ |
| `QuestionAnswered` | 出典付きの回答が生成された | KPI 集計（回答成功率） |
| `QuestionUnanswered` | 根拠データセットが見つからなかった | 欠損分類サービス |
| `GapClassified` | 未回答が理由分類された | データ公開リクエスト生成 |
| `DataPublicationRequested` | 都への提案として集約された | 四半期レポート生成 |
| `ProvenanceClicked` | 利用者が出典リンクを開いた | KPI 集計（出典クリック率＝カタログ流入） |

### イベント一覧

`QuestionUnanswered` は**エラーイベントではない**。本ドメインでは「答えられないこと」を正常な出力の一種として扱い、握りつぶさない。

## 8. ビジネスルール

### 不変条件

1. 回答は必ず1件以上の出典を持つ。出典を生成できない場合、回答を生成してはならない
2. 出典には CC BY 4.0 の表示要件を満たす提供元表記を含める
3. 根拠がない質問には「ありません」と答える。推測で埋めない
4. 未回答は必ず理由分類され、記録される（silent failure の禁止）
5. 旅行者プロフィールに個人を特定する情報を含めない

### ビジネス制約

- POC では対象エリアを渋谷・上野など代表エリアに限定する
- 利用データはカタログ掲載データに限る。カタログ外の「公表されただけのデータ」は二次利用しない（[CONSTRAINTS.md](../01-context/CONSTRAINTS.md) §3）
- データセットのスナップショットとカタログ最新版の差異は、取得日を添えて明示する

## 9. 状態遷移

### 状態遷移図

```
                 ┌──────────┐
                 │  受付済  │ 質問が入力された
                 └────┬─────┘
                      │ データセット特定
              ┌───────┴────────┐
              ▼                ▼
        ┌──────────┐     ┌──────────┐
        │  回答済  │     │  未回答  │
        └──────────┘     └────┬─────┘
                              │ 理由分類
                              ▼
                        ┌────────────┐
                        │ 分類済     │
                        └────┬───────┘
                             │ 集約
                             ▼
                     ┌────────────────┐
                     │ リクエスト化済 │ ──► 都へ提案
                     └────┬───────────┘
                          │ データが公開された
                          ▼
                     ┌────────────┐
                     │ 再回答可能 │ （回答範囲が広がる）
                     └────────────┘
```

### 状態定義

| 状態 | 説明 |
| ---- | ---- |
| 受付済 | 質問を受け取り、データセット特定を開始した |
| 回答済 | 出典付きの回答を返した |
| 未回答 | 根拠となるデータセットが見つからなかった |
| 分類済 | 未回答理由（GapReason）が確定した |
| リクエスト化済 | データ公開リクエストとして都へ提案された |
| 再回答可能 | 提案したデータが公開され、同種の質問に答えられるようになった |

### 遷移ルール

- 「受付済 → 回答済」は出典生成に成功した場合のみ
- 「未回答 → 分類済」は必ず通る（分類せずに破棄しない）
- 「リクエスト化済 → 再回答可能」は本プロジェクトの自己改善ループの完成点であり、KPI「データ公開リクエスト数」の意味を与える

## 10. リポジトリインターフェース

| リポジトリ | 対象 | 状態 |
| ---------- | ---- | ---- |
| データセットリポジトリ | 同梱オープンデータとメタ情報の取得 | POC では静的ファイル読み込み |
| 未回答リポジトリ | 未回答の記録・集計 | 未定（保持先を実装時に判断） |

## 11. ユビキタス言語

### 用語集

主要用語は [GLOSSARY.md](../06-reference/GLOSSARY.md) の「プロジェクト固有用語」に集約する。本書では概念間の関係のみ再掲する。

| 用語 | 本ドメインでの意味 |
| ---- | ------------------ |
| 出典（Provenance） | 回答の根拠となるデータセットへのリンクと実行クエリ。CC BY 表示義務を満たす手段でもある |
| 未回答（Gap） | 答えられなかった質問。改善還元コンテキストの入力 |
| データ公開リクエスト | 未回答から生成される、都への公開・更新提案 |
| コンシェルジュ | バックエンド。旅行アプリに従属しない独立した基盤 |

### 命名規則

- コード上の識別子は英語（`Provenance` / `Gap` / `DataPublicationRequest`）
- 利用者向け表示は日本語・英語の2言語

## 12. ドメインの進化

### 将来の拡張点

- カタログ外データ（都議会会議録）の取り込みと、公式 API 化の提案
- 介助者モード・音声対応（Final Stage）
- 旅体験コンテキスト以外のクライアント追加（翌年のハッカソン参加者）

### リファクタリング計画

- POC で同梱している静的データを、動的取り込みへ置き換えるかを Final Stage までに判断する
- コア操作の境界（[API.md](./API.md) §3 / [MCP.md](./MCP.md)）が旅行アプリ固有の語彙に侵食されていないか、クライアント追加時に再点検する
