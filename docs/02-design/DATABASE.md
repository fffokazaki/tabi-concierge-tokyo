# DATABASE.md - データベース設計書

> **本プロジェクトは Cloudflare D1 を使用する**（[ADR-007](../06-reference/DECISIONS.md)・2026-08-16）。用途は「オープンデータの格納（Text-to-SQL の実行基盤）」と「未回答ログ」の2つに限定する。
>
> 当初は ADR-004 に基づき「DB 不使用・データ同梱」としていたが、①企画が掲げる Text-to-SQL が実際に動かない ②「未回答は必ず記録される」不変条件（[DOMAIN.md](./DOMAIN.md) §8）の保持先が無い、という2点で限定解除した。ADR-004 の意図は「約9,600件の動的取り込みをしない」ことであり、その部分は維持している。

## 1. データベース概要

### データベース構成

- **RDBMS**: Cloudflare D1（サーバーレス SQLite）
- **理由**: Text-to-SQL を実際に成立させ、未回答ログの保持先を得るため（ADR-007）。Workers の無料枠は CPU 10ms/リクエストのため、リクエスト時に CSV をパースするより D1 側で集計するほうが安全でもある
- **スコープ**: 選定したデータセットのテーブル化と `gaps` テーブルのみ。約9,600件の動的取り込みは引き続き行わない
- **無料枠**: 500 MB/DB・5M 行読/日・100k 行書/日。10データセット規模に対し2桁の余裕がある
- **開発時の注意**: フル再取り込みは **1,645 行**の書き込み（2026-08-16 実測）。無料枠の 100k 行/日に対して1日60回以上の再取り込みが可能で、実質的な制約にならない。それでも開発中は**ローカル D1**（`--local`）を使う。リモートへの反映は意図したときだけ行い、スキーマ変更のたびに本番を触らないため

> 旧版では「フル再取り込みは約60,000行」と記載していたが、これは GIS データ主体だった旧データセット一覧を前提にした数字。確定10件（§2）では実測 1,645 行になった。

### データベース一覧

| データベース名 | 用途 | 状態 |
| -------------- | ---- | ---- |
| `tabi-concierge-tokyo` | オープンデータの格納 ＋ `gaps` テーブル | **作成済み**（2026-08-16・リージョン APAC）。バインディング名 `DB`、`database_id` は `wrangler.jsonc` に記載 |

## 2. データ資産

### データの持ち方

```
data/
  └ <dataset-id>/        # カタログのデータセットIDで管理し、出典URLと1:1に対応させる
      ├ data.csv         # 原本のスナップショット（UTF-8 に正規化して保存）
      └ meta.json        # 出典情報（カタログURL・提供元・ライセンス・取得日・原本の文字コード）
```

- 各データセットは**カタログの URL・タイトル・取得日**をメタ情報として必ず持つ。これが出典強制（[ARCHITECTURE.md](./ARCHITECTURE.md) §1）の実データ源になる
- ライセンスは CC BY 4.0。出典表示義務の詳細は [CONSTRAINTS.md](../01-context/CONSTRAINTS.md) §3
- 原本は `cp932` と `utf-8` が混在するため、保存時に UTF-8 へ正規化する（内容は変えない）。元の文字コードは `meta.json` の `sourceEncoding` に残す

### 取り込みの手順

```bash
node scripts/fetch-data.ts   # カタログAPIから10件を取得（npm run data:fetch）
npm run db:reset:local       # マイグレーション適用 → シード投入（ローカル D1）
```

リモート（本番 D1）へ反映するときは、**マイグレーションを先に適用する**。シードだけ流しても
テーブルが無いため失敗する。

```bash
npm run db:migrate           # リモートへスキーマ適用（--remote）
npm run db:seed              # リモートへシード投入（--remote）
```

- デプロイと同じく**手動実行**。push で自動反映はしない（[CLAUDE.md](../../CLAUDE.md) の技術スタック表）
- 2026-08-16 時点でリモートへのシードは未実施（ローカル D1 のみ）

- `scripts/fetch-data.ts` はリソースURLをハードコードせず、毎回カタログ API から解決する。**カタログの値（タイトル・提供元・更新頻度・ライセンス・公開状態）が `scripts/lib/datasets.ts` の宣言とズレたら失敗する**ので、古い前提のまま黙って取り込むことがない
- `scripts/seed.ts` が CSV から `db/seed.generated.sql` を生成する。生成物のため Git 管理しない（`data/` と scripts から再生成できる）

### 選定から外したもの

| 対象 | 理由 |
| ---- | ---- |
| 旧リスト（公園・防災デモ主体の10件） | 新宿区・文京区・千代田区・小金井市が対象で、代表エリア（上野・浅草・渋谷）に寄与しない。旅行アプリ主体の企画 v1.0 と噛み合わないため全面差し替え |
| 台東区 公衆無線LANアクセスポイント一覧 / バリアフリーマップ施設情報一覧 / 観光案内所 / 公園 / 食品衛生営業施設一覧 | **カタログ上は `format=CSV` だが、リソースURLの実体が HTML ページ**。機械可読データが取得できず D1 に取り込めない |
| 台東区 観光ポイント（`t131067d0000000392`） | 名称に反して 29 件のみ、**緯度経度が全件空欄**、内容が時代小説の舞台紹介に偏る。地図表示にも旅程生成にも使えない |
| めぐりん 北・南・ぐるーり（3路線） | 東西めぐりんで代表エリアを最も広くカバーできるため、1路線に絞った |

> **教訓**: カタログの `format` フィールドは自己申告であり、実体が HTML のことがある。データセットの採用可否は**リソースURLを実際に取得して**判断すること。

### 既知のデータ欠損（2026-08-16 実データ検証）

代表シナリオの「**ラーメンが好き**」に応えるデータは、カタログに**存在しない**。2026-08-15 の「小規模店舗は未カバー」という調査結果を、実データで次のとおり具体化した。

| 観点 | 実測 |
| ---- | ---- |
| 飲食店の店舗単位データ | 都内で No.8 の 210 件のみ。しかも**バリアフリー対応店に限定**された部分集合であり、飲食店の悉皆データではない |
| 台東区（上野・浅草）の収録 | 210 件中 **19 件**。いずれも寿司・焼肉・ホテル内レストラン等 |
| ラーメン店 | 210 件中 3 件（板橋区・武蔵野市・青梅市）。**代表エリアには 0 件** |

- 欠損の分類は「データ未公開」ではなく「**粒度不足**」（[DOMAIN.md](./DOMAIN.md) §4 GapReason）。飲食店データ自体は存在するが、ジャンル・エリアの粒度で旅行者の問いに答えられない
- この欠損は隠さず、「データ公開リクエスト」として都へ還元する仕組みの題材にする（[DOMAIN.md](./DOMAIN.md) §7）。**推測で埋めて回答を作ることはしない**（同 §8 不変条件3）

### 渋谷エリアの制約（2026-08-16 調査）

渋谷区のカタログ掲載データは**17件のみ**で、その大半が自治体標準オープンデータセット（公営住宅・理容所・美容所・子ども食堂など）である。**観光ポイント・名所・文化施設に相当するデータは 1 件も無い**。

- そのため渋谷は No.10（都市公園）で面を押さえるに留め、**代表シナリオの縦貫通は上野・浅草で構成する**
- 台東区は 187 件を公開しており、同じ「区」でも観光データの整備状況に大きな差がある。この差自体が、都への還元（データ公開リクエスト）の題材になる

### テーブル構成

定義は [`migrations/0001_init.sql`](../../migrations/0001_init.sql)。3テーブルのみで、用途は ADR-007 の2つに限定している。

| テーブル | 役割 | 実測 |
| -------- | ---- | ---- |
| `datasets` | 出典の源。§2 の確定10件と 1:1 | 10 行 |
| `spots` | 地物（施設・史跡・停留所・店舗）。施設一覧型9件を集約 | 1,645 行 |
| `gaps` | 未回答ログ（[DOMAIN.md](./DOMAIN.md) §8 不変条件4） | 取り込み直後は 0 行。**コア3操作が未回答を返すたびに増える**（[Issue #27](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/27)） |

**設計の芯は「出典を持たない行を作れないようにする」こと。** 出典強制をクエリ側の作法ではなくスキーマ制約として担保している。

| 不変条件 | 担保する仕組み |
| -------- | -------------- |
| すべてのスポットが出典を持つ | `spots.dataset_id` を `NOT NULL REFERENCES datasets(id)` にする。出典なしの行は INSERT が失敗する |
| 緯度経度を取り違えない | `CHECK (lat BETWEEN 35.4 AND 35.9)` / `CHECK (lon BETWEEN 138.9 AND 139.95)`。後述の X/Y 逆転を DB が拒否する |
| 未回答は必ず分類される | `gaps.reason` を `CHECK (reason IN (...))` で4分類に制約（[API_REQUIREMENTS.md](./API_REQUIREMENTS.md) の `unanswered.reason` と同じ英語の値） |

#### `gaps` への記録（Issue #27）

記録は `worker/core/gaps.ts` が行い、**`/api/*` と `/mcp` の両経路で同じように残る**（ADR-008。ルート側にロジックを置かない）。

| 列 | 入る値 |
| --- | --- |
| `question` | `search_datasets` の `query` / `aggregate_dataset` の `intent` / `get_provenance` の `query` |
| `area` | **解決後のエリア**。入力の `area` をそのまま入れない。「新宿の美術館」（`area` 未指定）が `out_of_area` で返るとき、集計に効くのは質問文から解決した「新宿」のほう |
| `category` | 絞り込みに使った分類（指定があれば） |
| `reason` | 4分類のいずれか |

- **`answered` に載る部分欠損（[Issue #29](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/29) の `gaps`）も1行ずつ記録する。** `unanswered` だけを記録すると、混在クエリで可視化したばかりの欠損が記録に残らない
- **重複排除しない。** 同じ未回答が何度起きたかを数えられる形にする
- **記録の失敗で回答経路を落とさない。** 書き込みは `try/catch` で受け、失敗しても未回答の応答はそのまま返す。ただし握りつぶさず `console.error` に出す（静かに消えると「`gaps` が 0 行なのは未回答が無いから」と誤読される）
- **入力の形が壊れている 400 と、呼び出し側の契約違反（`get_provenance` に空の `datasetIds`）は記録しない。** データ欠損の集計に呼び出し側のバグを混ぜない

記録器はコア3操作の**必須の引数**にしてある。optional にすると `/mcp` を足したときに渡し忘れても型が通り、その経路だけ黙って記録が止まる。

これらは `worker/schema.test.ts` で「実際に壊しにいく」形で検証している。

#### エリアと分類を列に持つ理由

`spots.area`（上野／浅草／渋谷）と `spots.category` は、[API_REQUIREMENTS.md](./API_REQUIREMENTS.md) の `search_datasets({ area, category })` に対応する**検索の絞り込み条件**であるため、実行時の部分一致ではなく取り込み時に確定させて列に持つ。

住所の部分一致が使えないことは実データで確認済み（[`scripts/lib/area.ts`](../../scripts/lib/area.ts) に判断の根拠を記録）:

| 住所 | `LIKE '%浅草%'` | 正しい判定 |
| ---- | --------------- | ---------- |
| 雷門2丁目18番9号（**浅草文化観光センター**） | ✗ 拾えない | 浅草 |
| 浅草橋（14件） | ✓ 拾ってしまう | 対象外（浅草寺から約2km南） |
| 元浅草（11件） | ✓ 拾ってしまう | 対象外（新御徒町付近） |

どの町字までを「浅草」と呼ぶかはデータから導出できないため、**記録された判断**として町字マッピングを持つ（浅草寺・雷門を中心とした徒歩圏／浅草通りより北側）。

#### 取り込み時に判明した実データの癖

| 癖 | 対応 |
| --- | --- |
| 台東区の独自形式は `X座標`=**経度**・`Y座標`=**緯度** で、自治体標準（`緯度,経度`）と並びが逆 | 形式ごとに写像を分け、範囲を CHECK 制約とシード時アサーションの二重で検証 |
| 丁目の表記が算用数字（`浅草7丁目`）と漢数字（`浅草一丁目`）で揺れる | 町字の切り出しで両方を境界として扱う。漢数字を見落とすと宿泊施設883件が丸ごと未分類になる |
| めぐりん停留所は**所在地列が全件空**で、地名が停留所名にしか無い | このデータセットだけ名称からエリアを判定する（`datasets.ts` の `areaFrom: "name"`） |
| 停留所名は `東西(上野公園経由・三崎坂往復ルート)27西浅草三丁目` のように**名称の中に路線名を含む** | 照合の前に括弧書きを落とす（[Issue #30](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/30)）。落とさないと路線名側の「上野公園」が先に当たり、この路線の全38停留所が上野に倒れる |
| 文字コードが `cp932` と `utf-8` で混在 | 取得時に宣言と照合し、不一致なら失敗させる |

めぐりん停留所 72件のうち **43件は判定不能（`area IS NULL`）** になる。内訳は代表エリア外（谷中・三崎坂・新御徒町・三筋 ほか）と、名称が施設名で町字を含まないもの（`東京国立博物館`・`寛永寺`・`台東区役所` ほか）。後者は実際には上野エリアだが、**このデータセット単体からは確かめられない**（所在地列が空のため）。町字マッピングに施設名を足すのは推測になるため行わない。住所を持つ他データセット（No.1・No.2）との突き合わせで解ける余地があり、[Issue #36](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/36) に分離した。

#### 統計表（No.9）を spots に入れない判断

No.9「R6国・地域別外国人旅行者行動特性調査」はクロス集計表（`,男性,女性,無回答,合計,標本数`）であり、施設一覧ではない。コア3操作のいずれもこれを地物として問い合わせないため、**`datasets` に出典としてのみ登録し、データテーブルは作らない**（`has_spots = 0`）。ADR-007 は D1 の用途を Text-to-SQL の実行基盤に限定しており、クエリされないテーブルを持たない。訪日客の行動特性は資料・企画の根拠として参照する。

## 3. データ品質と更新

### 更新頻度への対応

確定版10件に**毎月更新のデータセットは含まれない**（旧リストの「東京都の人口（推計）」を採用しなかったため、提出直前の月次差し替えは不要になった）。

更新頻度はカタログの `extras.更新頻度` に記載された値（推測ではなくカタログ記載の実値）。

| 更新頻度 | 該当 | 最終更新 | 対応 |
| -------- | ---- | -------- | ---- |

- **URL の実在確認方法**: カタログはブラウザ以外のアクセスを WAF で遮断するため、`curl` のステータスコードでは判定できない（実在 URL でも 403／存在しない URL でも同じ応答）。API の `package_show` が `success: true` を返すこと、またはブラウザで開くことで確認する（存在しない ID は 404 ページになる）

### 整合性の考え方

- POC のデータはダウンロード時点のスナップショット。回答には**出典 URL と取得日**を添え、利用者がカタログの最新版へ辿れるようにする
- 同梱データとカタログ最新版の差異は「劣化」ではなく明示すべき事実として扱う

## 4. バックアップ・リカバリ

- 同梱データは Git リポジトリで管理し、リポジトリのバックアップをもって代替とする
- 個別のバックアップ運用は行わない（本フェーズでは対象外）

## 5. セキュリティ

- 取り扱うのは公開済みオープンデータのみ。秘匿情報・個人情報は保持しない
- アクセス制御・暗号化の要件は現時点で該当なし（[CONSTRAINTS.md](../01-context/CONSTRAINTS.md) §5）
