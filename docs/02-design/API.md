# API.md - API設計書（フロントエンド ↔ バックエンド `/api/*`）

> 本システムのバックエンドは、単一の Cloudflare Worker が2つの入口を持つ（[ADR-008](../06-reference/DECISIONS.md)）。本書はそのうち **React アプリが呼ぶ `/api/*`（JSON / Hono）** の設計書である。もう1つの入口 `/mcp`（AI クライアント向けの MCP ツール公開・基盤開放面）は [MCP.md](./MCP.md) を参照。
>
> 両面は `worker/core/` の**同じコア操作**を露出する薄い皮であり、**入出力スキーマと共通仕様の SSOT は本書 §3・§4 に置く**（MCP.md には二重定義しない）。
>
> **コア3操作（§3.1〜§3.3）のエンドポイントパス・操作名・入出力スキーマは 2026-08-17 に確定した**（Issue #22）。§3.4 の追加候補（`recommend_spots` / `report_gap`）は引き続き**仮称・未確定**で、実装時に確定させること（推測で確定扱いにしない）。
>
> 実装状況（2026-08-17）: `GET /api/health` と コア3操作。コア3操作の中身は `worker/core/` の**固定データによるスタブ**で、Step 5 でメタデータRAG / Text-to-SQL に差し替える。**入出力の形はそのとき変えない**ので、フロントエンドは今の形に対して実装してよい。
>
> 入出力の TypeScript 型は [`shared/core.ts`](../../shared/core.ts) にあり、`worker/`（実装）と `src/`（React）が同じ定義を参照する。本書と型定義がずれたら本書を正とする。

## 1. API概要

### API基本情報

| 項目 | 内容 |
| ---- | ---- |
| 種別 | JSON API（Cloudflare Worker 上の Hono ルーティング、パスは `/api/*`） |
| ベース URL | SPA と同一の Worker（<https://tabi-concierge-tokyo.opendata-002.workers.dev>）。SPA は同じ Worker の静的アセットとして配信されるため、フロントエンドから見て**同一オリジン** |
| 認証 | なし（POC。§2 参照） |
| 想定クライアント | 旅コンシェルジュTOKYO（React SPA）のみ。Claude Desktop 等の AI クライアント・翌年のハッカソン参加者は `/mcp`（[MCP.md](./MCP.md)）を使う |

### API設計原則

1. **最小3操作から始める**: データセット検索・集計・出典取得。必要性が実証された操作だけを追加する
2. **出典なしの応答を返さない**: 根拠となるデータセットを提示できない場合、「回答なし」を明示的に返す。曖昧な推測を返さない
3. **未回答は失敗ではなく出力**: 答えられなかった質問は `unanswered` として記録し、データ公開リクエストの入力にする（silent failure を作らない）
4. **アプリ固有の語彙を持ち込まない**: 「旅程」「マナー」等の旅行アプリ都合の概念はクライアント側の責務。コア操作はデータセットの検索・集計・出典という汎用語彙に留める（同じ操作を `/mcp` でそのまま開放するため）
5. **ロジックは `worker/core/` のみに書く**: `/api/*` と `/mcp` は同じコア関数を呼ぶ薄いアダプタに徹し、ロジックを二重に書かない（ADR-008「AIへの指示」）

## 2. 認証・認可

- **認証方式**: なし（POC では利用者認証を伴う機能を実装しない）
- **認可モデル**: 該当なし
- **将来**: `/mcp` を外部公開（翌年参加者への開放）する段階で、レート制限を含めて再設計する（[MCP.md](./MCP.md) §5）

## 3. エンドポイント一覧

コア操作名（`search_datasets` 等）は `worker/core/` の関数名および `/mcp` のツール名に対応する共通の語彙。§3.1〜§3.3 は確定済み、§3.4 は仮称。

### 3.0 `GET /api/health` — 疎通確認（実装済み）

| 項目 | 内容 |
| ---- | ---- |
| 入力 | なし |
| 出力 | `{ status: "ok", service: "tabi-concierge-tokyo", runtime: <workerd の userAgent 実値> }` |
| 備考 | デプロイ経路の生存確認用（`worker/index.ts`）。フロントエンド側の障害種別ハンドリングは Issue #14 / PR #15 参照 |

なお、未定義の `/api/*` パスは静的アセット（SPA の index.html）へフォールバックさせず、`{ "error": "not_found" }` の 404 を返す（クライアントが JSON を期待して壊れるのを防ぐため）。

### 3.1 `search_datasets` — データセット検索（`POST /api/search-datasets`・確定）

自然言語の質問から、答えの根拠になりうるデータセットを特定する（Step 5 でメタデータRAG に差し替え）。

| 項目 | 内容 |
| ---- | ---- |
| 入力 | `{ query: string, area?: string, areas?: string[], interests?: string[], category?: string, limit?: number }`。`query` は必須（空文字・空白のみは 400）。ただし **`interests` を1件以上送る場合のみ省略できる**（興味チップだけ選んで自由文を書かない呼び出し）。`areas` / `interests` は構造化入力（下記「構造化入力」・[ADR-011](../06-reference/DECISIONS.md)） |
| 出力（回答あり） | `{ status: "answered", candidates: Array<{ datasetId, title, provider, url, matchReason }>, gaps?: Array<{ status: "unanswered", reason, message, area? }> }`。`candidates` は**必ず1件以上**（型でも非空を強制。DOMAIN.md §8 不変条件1） |
| 出力（回答なし） | `{ status: "unanswered", reason, message, gaps?: Array<{ status: "unanswered", reason, message, area? }> }`（§4 参照）。`gaps` は**理由が覆っていない別の欠損**（[Issue #70](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/70)）: `reason` は1つしか運べないため、`areas` で目的地と明示された欠損はここに載せる — 対象エリア外（`out_of_area`・理由が報告する地名は除く）と、代表エリアのうち絞り込みに使わなかったもの（`other`・「〜についても訊かれましたが、この応答では答えられていません」）。興味ごとの欠損は載せない（未回答は「何も答えていない」を全体として述べており、興味別の message は候補が存在しない文脈では書けない。興味は記録の `question` 列に残る）。無いときはキーごと省く |
| `gaps` | **答えられた候補と一緒に返す、答えられなかった側面**（下記）。欠損が無いときは**キーごと省く**（`gaps: []` は返さない）。要素は `unanswered` 応答と同じ形・同じ文言に、`area?`（その欠損がどのエリアについてのものか。応答全体のエリアと違うときだけ入る）を足したもの |
| `area` | 代表エリア（上野・浅草・渋谷）以外も**受け付ける**。対象エリア外は 400 ではなく `unanswered("out_of_area")` で返す。未指定なら質問文から代表エリア名を拾う（**明示指定が質問文より優先**）。**候補の絞り込みに使うのは1エリアだけ**で、質問文に複数の代表エリアがある場合は定義順（上野→浅草→渋谷）の最初のもの。絞り込みに使わなかったエリアは、返した候補が収録していなければ `gaps` に載る（下記「訊かれたエリアの取り落ち」）。**`areas` との同時指定は 400**（どちらを信じるかを実装が黙って決めない） |
| `areas` | **目的地として訊かれた**エリアの配列（構造化入力・[Issue #58](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/58)）。これを送ると質問文からのエリア推測を**行わない**（空配列は「目的地なし」の明示で、未指定とは意味が違う）。絞り込みに使うのは**最初の代表エリア1つ**（並び順は呼び出し側の意図として尊重する。質問文推測の「定義順」と違う点に注意）。代表エリア以外の要素は目的地と明示されたエリア外として扱い、`out_of_area` の欠損として添える — **応答全体が `unanswered` でも落とさない**（`unanswered` 側の `gaps`・[Issue #70](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/70)。代表エリアが1つも無ければ応答全体が `unanswered("out_of_area")` になり、理由が報告する地名を除いた残りが `gaps` に載る）。要素は正規化される（前後空白・空要素・重複の除去） |
| `interests` | 興味の配列（構造化入力・[Issue #53](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/53)）。要素は**日本語の表示ラベル**（例 `"ナイトライフ"`。`"culture"` のようなドメイン値の識別子はキーワード表に当たらず、取り落ちの欠損になるだけ — マッチは日本語の部分一致のため）。候補のマッチに使うほか、**返した候補が覆っていない興味を1件ずつ `gaps` に載せる**（下記「部分欠損」）。要素は正規化される（前後空白・空要素・重複の除去） |
| 配列の上限 | `areas` / `interests` は**最大 20 件・要素 100 文字**。超過は黙って切り詰めず 400（`limit` と同じ方針。要素数ぶんの欠損が `gaps` テーブルへ記録されるため、認証なしの公開 API で無制限に受けない） |
| `category` | **絞り込みの述語ではなくスコアリングのヒント**。ただし指定して1件も当たらない場合はエリアだけの候補へ落とさず `unanswered` を返す（指定を黙って捨てないため）。その `message` は**実際に照合した集合**（エリアで絞り込んだ候補か、全10件のキーワード表か）で当たらなかったことだけを述べ、「10件に対応するものが無い」とは断定しない（[Issue #59](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/59)。エリアで絞り込んでいた場合、絞り込みの外に該当データが実在しうる） |
| `limit` | **既定 4・上限 10**。既定値はフロントエンドが1ルートに3〜4停留地を想定しているため（[API_REQUIREMENTS.md](./API_REQUIREMENTS.md) §1）。上限はデータセットが10件しかないため。範囲外は 400 で、黙って丸めない。**`interests` を送った呼び出しでは、枠に収まらない候補の選び方が変わる**（下記「興味カバレッジ優先の選定」） |
| 前提 | マッチは**日本語の部分一致**。英語のクエリには当たらない（多言語対応は未着手） |
| 未確定 | スコアリング方法（現状はキーワード一致数の単純な順位づけ。同点はカタログ登録順で解決するため、**同点内の順位は関連度を表さない**。Step 5 で再設計する） |

判定の順序に意味がある。エリア外を先に弾き、キーワードが当たれば候補を返す。**当たらなかったときに初めて**、ジャンル指定の飲食（粒度不足）→ マナー・作法の調査済み欠損（未公開・[ADR-010](../06-reference/DECISIONS.md)）→ 渋谷の観光データ欠損（未公開）→ 分類指定の空振り → エリアだけの絞り込み、の順に落とす。ジャンル判定・マナー判定をエリアのフォールバックより後ろに回すと、答えられない問い（ラーメン・浅草のマナー）にエリアのデータセット一覧を返して欠損が消える。最後のエリアだけの絞り込みは、**エリア名のほかに何か訊かれていた場合に欠損を1件添える**（下記「エリア・フォールバックに添える欠損」）。加えて、`answered` を返すどの経路でも、**訊かれた代表エリアのうち返した候補が収録していないもの**を欠損に載せる（下記「訊かれたエリアの取り落ち」）。

日本語は分かち書きしないため、地名・ジャンル語の部分一致は語の境界を見ない。「銀座線」（浅草・上野を通る地下鉄）を「銀座」として対象エリア外にしない、「〜のそば（近く）」を飲食のジャンル指定にしない、といった除外を実装側に持っている。

#### 部分欠損（`gaps`）

答えられる興味と答えられない興味を1つの `query` に混ぜられる（例「上野の美術館とラーメン」）と、以前は**答えられる候補だけを返し、ラーメン側の欠損は応答のどこにも現れなかった**。代表シナリオ「明日は浅草と上野、ラーメンが好き」が最も自然に生む入力の形であり、切り替え前のフロントエンドは `trip.interests` を1つの自然文にまとめて送っていた（現在は `interests` を分けて送る — [API_REQUIREMENTS.md](./API_REQUIREMENTS.md) §1・Issue #53）ため実際に踏んでいた。興味を `query` に畳み込む呼び出し（API コンソール・将来の `/mcp` の自然文経路）では今も起きる。

[Issue #29](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/29) で解消し、**答えられた候補を返したうえで、答えられなかった側面を `gaps` に載せる**ようにした。

```jsonc
{
  "status": "answered",
  "candidates": [ { "datasetId": "t131067d0000000236", "title": "文化観光施設", "…": "…" } ],
  "gaps": [
    {
      "status": "unanswered",
      "reason": "insufficient_granularity",
      "message": "飲食店の店舗データは…「ラーメン」の粒度では答えられません。"
    }
  ]
}
```

- **語から判定する欠損は、実測で「答えられない」と言い切れる既知の欠損だけ**。ジャンル指定の飲食（`insufficient_granularity`）・マナー・作法（`data_not_published`・[Issue #43](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/43)／[ADR-010](../06-reference/DECISIONS.md)）・渋谷の観光データ未公開（`data_not_published`）の3つで、いずれも `unanswered` として返すときと**同じ値**を返す。マナーの語彙は**カタログに無いことを調査で確認した語**（マナー・作法・エチケット・おもてなし）に限る。自然文を興味に分解することはしない（分解は Step 5 の LLM 側の仕事で、スタブに作り込むと二重になる）
- **構造化入力 `interests` を送った呼び出しでは、興味ごとの取り落ちも載せる**（[Issue #53](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/53)／[ADR-011](../06-reference/DECISIONS.md)）。返した候補のキーワード表に当たらなかった興味を、`other` の欠損として1件ずつ添える（`"ナイトライフ"` の例: `「ナイトライフ」について訊かれましたが、返した候補のキーワードには「ナイトライフ」の語に当たるものがありませんでした。`）。「無い」と断定しない — 実装が知っているのは照合の結果だけで、答えになるデータの実在は判定していない（Issue #59 と同じ判断）。既知の欠損（ジャンル・マナー・渋谷の観光）として**実際に報告された**興味は二重に載せない（ジャンルは報告される1語に対応する興味だけを畳む。`["ラーメン", "寿司"]` の寿司のように報告に対応しない興味は `other` の取り落ちとして載せる）。**`query` に畳み込んだ興味にはこの判定は効かない**（キーワードが1件でも当たると `answered` になり、どの興味に答えたかを判定できない — それが Issue #53 の症状そのもの）。応答全体が `unanswered` になる経路では興味ごとの欠損は載せない（未回答が「何も答えていない」を全体として覆っている — [Issue #70](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/70) の判断。`areas` 由来の対象エリア外は同じ経路でも `unanswered` 側の `gaps` に載る点と扱いが違う）
- **対象エリア外の地名（`out_of_area`）は、質問文から拾ったものは部分欠損にしない。** 「新宿のホテルから上野の美術館へ」の新宿は**出発地**であって、新宿のデータを求めてはいない。「新宿について訊かれた」と「新宿を経路として書いた」を見分ける手段がスタブに無いため、報告すると答えられている応答にノイズを足すことになる。上記3つは**求めているデータの種類**を指す語なので、散文中の言及と取り違えにくい。なお**エリア外そのものを訊かれたときの `unanswered("out_of_area")` は従来どおり**（`{ area: "新宿" }` など）。**例外は `areas` で目的地と明示された場合**（Issue #58）— 呼び出し側が目的地だと言っているので見分けの問題が無く、`out_of_area` の欠損（`area` にその地名を持つ）として載せる。載せないと「上野・新宿を回りたい」の新宿だけが応答から黙って消える
- **エリアだけで絞った候補を返す経路では、`other` の欠損を1件添える**（[Issue #50](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/50)）。上記3つと同時には起きない（いずれもこの経路より手前で `unanswered` として返るため）。ただし**この経路の `gaps` が必ず1件とは限らない** — 下記「訊かれたエリアの取り落ち」の欠損が同時に付く（`"上野・渋谷の公園"` は2件）。詳細は下記
- **訊かれた代表エリアを候補が覆っていない場合も、`other` の欠損を1件ずつ添える**（[Issue #52](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/52)）。この欠損だけ `area` を持ち、応答全体のエリアとは別のエリアを指す。詳細は下記
- **すべて答えられない場合は従来どおり `status: "unanswered"`。** `answered` ＋ 全部 `gaps` にはしない（それでは「答えがある」と嘘になる）。ただし `unanswered` は理由を**1つしか運べない**ため、複数の側面が同時に答えられない場合は先に判定されたものだけが返る
- **`gaps` は optional で、無いときはキーごと省く。** 既存クライアントは無視しても壊れないが、無視すると欠損が画面に出ない点に注意

#### エリア・フォールバックに添える欠損

キーワードが1件も当たらなくても、そのエリアを収録したデータセットは**事実として**提示できる（「上野」だけの質問など）。しかしこの経路は、**エリア名のほかに何か訊かれていた**場合には訊かれた内容の答えになっていない。

[Issue #50](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/50) までは、それを黙って `answered` として返していた。`gaps` が空なので画面に出ず、`gaps` テーブルにも記録されなかったため、「ナイトライフ」の問いに渋谷区の都市公園が、「ショッピング」の問いに台東区のトイレ情報が、**本物の CC BY 出典つきで**返っていた（`unanswered` は必ず記録される、という §8 不変条件4 が最も効いてほしい場所で破れていた）。

**質問文からエリア名と区切り記号を除いた残余が空かどうか**で分ける。

| `query` | `gaps` |
| --- | --- |
| `"上野"` | 添えない（エリアの一覧が答えそのもの。ノイズを足さない） |
| `"上野・浅草"` | 添えない（この経路としては。台東区のデータセットが両方を収録しているので「訊かれたエリアの取り落ち」も付かない） |
| `"上野・渋谷"` | この経路としては添えない（残余が空）。ただし候補が渋谷を収録していないため「訊かれたエリアの取り落ち」が1件付く |
| `"ナイトライフ、渋谷"` | `other` を1件 ＋ `gaps` テーブルへ記録 |
| `"ショッピング、上野"` | `other` を1件 ＋ `gaps` テーブルへ記録 |

- **`reason` は `other`。** `data_not_published`（最も強い分類）はカタログ側に無いことを実測した場合にしか使えず、この経路に来る問い（ナイトライフ・ショッピングなど）は**未調査**なので、未公開と言い切ると推測で埋めることになる（CLAUDE.md 絶対ルール #1）
- **語には分解しない。** 内容語の取り出しには形態素解析が要り、規則をスタブに作り込むと Step 5 の分解と二重になる。判定に使うのは「エリア名以外が残るか」の一点だけ。助詞は落とさないので `"上野で"` は内容ありと判定される（**過検知の側に倒してある**）
- **過検知した分も `gaps` テーブルに積まれる。** `"上野に行きたい"` `"渋谷区"` `"上野駅"` `"浅草周辺"` はいずれも残余が残るため欠損が1件付き、D1 に `other` の行が入る。実際にはエリアの一覧が答えである問いなので、**[DOMAIN.md](./DOMAIN.md) §7 の集計では `other` を額面どおり読めない**（データ公開リクエストへの還元時に差し引く必要がある）。`message` が「質問文の語に当たるデータセットが無かった」＝実際に行ったことしか書いていないので、応答そのものは嘘にならない
- **この経路の行を他の `other` と区別する列は無い。** `gaps` の列は `question` / `area` / `category` / `reason` / `created_at` だけで、`other` の産出元は他にもある（分類の空振り・最終フォールバック・`aggregate_dataset` の未知 ID とスタブの行欠落・`get_provenance` の未知 ID）。この経路の行は `reason = 'other' AND area IS NOT NULL AND category IS NULL` で概ね取り出せるが、**`aggregate_dataset` の `other` と混ざる**（プランの主経路では `intent` に同じ `query` を渡すので `question` も `area` も一致する）。分離が必要になった時点で `reason` の細分＝マイグレーションが要る
- **残余は判定にのみ使い、`message` には埋め込まない。** `query` は自由文がそのまま渡るため、エリア名を除いた残余は `"で夜遊びしたい"` のような壊れた文字列になる。欠損を可視化するための文が、新たな意味不明な文字列の出所になってはいけない
- **`aggregate_dataset` はこの経路の候補でも質問文との適合を見ない**（エリア指定があればその行に絞るだけ）。したがって欠損を添えても、旅程には無関係な地物が出典つきで載る。Step 5（Text-to-SQL 化）で候補の妥当性そのものを直す対象。照合していない事実は応答の `query` に明記される（[Issue #78](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/78)・§3.2）
- **複数の代表エリアはこの判定では拾えない。** `"上野・渋谷"` はどちらもエリア名なので残余が空になり、この経路は「エリアだけの質問」と答える。それは正しい（内容は訊かれていない）が、渋谷に答えていないことは別の判定が見る（下記「訊かれたエリアの取り落ち」・[Issue #52](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/52)）
- **この手当てが効くのは「キーワードが1件も当たらなかった」経路だけ**。1件でも当たるとキーワード経路で `answered` になり、`query` に畳み込まれた興味の取り落ちは残らない。`"ナイトライフ、上野で夜遊びしたい"` は銭湯のキーワード「夜」が「夜遊び」に部分一致するため `gaps` なしで銭湯を返す（渋谷で効くのは、渋谷を収録するのが都市公園1件だけで銭湯が候補集合から外れるためで、判定が正しいからではない）。**興味チップを複数選ぶほど何かが当たるので、実際に旅程が組み上がるケースほど発火しない** — この非対称の解消が構造化入力 `interests`（[Issue #53](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/53)／ADR-011）で、興味を畳み込む前の配列で送ればキーワード経路でも興味ごとの取り落ちが載る（上記「部分欠損」）。プラン画面も `interests`（興味の配列）と `query`（自由文のみ）を分けて送る形へ切り替え済み（Issue #53・`src/features/plan/buildPlan.ts` の `buildSearchInput`）

#### 訊かれたエリアの取り落ち

候補の絞り込みに使うエリアは1つだけなので、質問文に複数の代表エリアが書かれていると**そのうち1つの分しか候補にならない**。[Issue #52](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/52) までは、残りのエリアの要求が応答にも `gaps` テーブルにも残らなかった。

```
query="上野・渋谷"（修正前）
  → answered / gaps なし / 記録 0件
  → 候補: 名所・史跡・文化観光施設・文化財一覧・トイレ情報（すべて台東区）
```

渋谷を収録する都市公園・都立公園一覧は候補に入らず、「渋谷について訊かれたが答えていない」ことがどこにも残らない（§8 不変条件4 の違反）。`"上野・浅草"` は両方とも台東区のデータセットが収録しているため実害が出ず、**データセットが分かれている組み合わせでだけ症状が出る**ため気づきにくかった。

**「訊かれた代表エリア」と「返した候補が収録しているエリア」を突き合わせ、覆えていないエリアを1件ずつ `gaps` に載せる。**

| `query` / `area` | `gaps` |
| --- | --- |
| `"上野・渋谷"` | `other` を1件（`area: "渋谷"`） ＋ `gaps` テーブルへ記録 |
| `"上野・浅草"` | 添えない（台東区の8件がいずれも両方を収録しているので、答えていないエリアが無い） |
| `"上野の美術館と渋谷の公園"` | `other` を1件（`area: "渋谷"`）。**キーワードが当たった経路でも報告する** |
| `"新宿から上野へ行きたい"` | 添えない（新宿は代表エリアではない。[Issue #29](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/29) の判断を維持） |
| `"渋谷から上野の美術館へ行きたい"` | `other` を1件（`area: "渋谷"`）。**query だけの呼び出しでは出発地のつもりでも報告する**（下記・[Issue #58](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/58)） |
| `{ query: "渋谷から上野の美術館へ行きたい", areas: ["上野"] }` | 添えない（目的地を構造化して明示したので、出発地の渋谷は「訊かれた」に数えない。Issue #58 の解消経路） |
| `{ query: "美術館を回りたい", areas: ["上野", "渋谷"] }` | `other` を1件（`area: "渋谷"`）。`areas` は過検知を消す入力であって、取り落ちの報告を消す入力ではない |
| `{ query: "上野の公園", area: "渋谷" }` | 添えない（明示指定が優先。上野は呼び出し側が意図して外したもの） |
| `{ query: "上野・渋谷", category: "公園" }` | この判定に届かない。分類指定の空振りが手前で `unanswered` を返す（下記） |

- **判定は「解決に使わなかったエリア」ではなく「返した候補が収録していないエリア」。** 前者にすると `"上野・浅草"` に浅草の欠損が付くが、実際には答えられている。ノイズを足さない（Issue #29 の AC）ためには候補の `areas` を実測で見る必要がある
- **`reason` は `other`。** 渋谷にはデータがある（都市公園123件）ので `data_not_published` は使えず、渋谷は対象エリアなので `out_of_area` でもない。`message` も「無い」と書かない — **無いのではなく返していない**ので、そう書くと嘘になる。実際に行ったこと（`"上野"` で絞り込んだ結果、渋谷のデータセットが候補に入っていない）だけを書く
- **この欠損だけ `area` を持つ。** 応答全体のエリアは解決結果（上野）だが、この欠損は渋谷についてのもの。記録（`gaps.area`）が応答全体の値だけを見ていると、**どのエリアに答えられなかったかが集計から消える**（それが Issue #52 の症状そのもの）。`message` から地名を抜き出す実装にはしない（文言を直した瞬間に集計が壊れる）
- **対象エリア外の地名は見ない。** 代表エリアだけを突き合わせる。`NON_TARGET_AREAS` を混ぜると `"新宿から上野へ行きたい"` の新宿＝出発地が欠損として報告される
- **質問文からの推測は、代表エリアについて過検知の側に倒したまま**（[Issue #58](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/58) で確定した仕様）。`"渋谷から上野の美術館へ"` を `query` だけで送ると、出発地かもしれない渋谷も「訊かれた」と数える。対象エリア外の新宿と**逆に倒すのは事情が違うため** — 新宿は POC の対象外で**そもそも答えられない**ので報告しても行動につながらないが、渋谷は対象エリアでデータがあり、渋谷のデータも欲しい可能性が残る。質問文の形だけでは出発地と目的地を見分けられない（見分けはスタブに形態素解析を持ち込む話になる）ので、**区別を知っている呼び出し側が `areas` で目的地を明示する**のが解消経路（ADR-011。質問文からの抽出は Step 5 の LLM 側の仕事）。`query` だけの呼び出しの過検知分は Issue #50 と同じく `gaps` テーブルに積まれるので、[DOMAIN.md](./DOMAIN.md) §7 の集計では差し引く必要がある
- **`category` を指定した空振りはこの判定に届かない。** 分類指定が1件も当たらないときは手前で `unanswered("other")` を返すため、覆えなかったエリアの欠損は付かない（記録の `area` は解決結果のほう）。応答全体が「答えられていない」なので Issue #52 の症状（`answered` で黙って落ちる）にはならない。その `message` は実際に照合した集合で当たらなかったことだけを述べる（[Issue #59](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/59) で「10件に無い」の断定をやめた）。この経路を通るのは `category` を送る呼び出し（API コンソール・将来の `/mcp`）だけで、プラン画面は `category` を送らない（興味は `interests`、要望は `query` で送る — Issue #53）ため通らない
- **候補を両エリアぶん返す案（Issue #52 の対処案 a）は採らなかった。** 利用者の要求には近いが `limit` の配分とスコアリングの再設計を伴い、かつ**両方に答えてしまうと記録すべき欠損が消える**ため受け入れ条件（答えなかったエリアが `gaps` テーブルの `area` 列から分かること）を満たせない。Step 5 のスコアリング再設計で改めて扱う

#### 興味カバレッジ優先の選定

スコアはキーワード一致数なので**同点が頻繁に起きる**。同点の順位は `no` 昇順（カタログ登録順）で決まり、これは関連度と無関係な基準 — つまり `limit` で切ると、**あとから足したデータセットほど構造的に落ちる**。

```
interests=["ラーメン","文化","家族向け","自然"] / limit=4（修正前）
  → 6件が score=1 の同点（名所・史跡／文化観光施設／文化財一覧／トイレ情報／銭湯／都市公園・都立公園一覧）
  → no 昇順の上位4件だけが残り、「自然」の唯一の一致先（no:10 都市公園）が毎回落ちる
  → gaps に「『自然』…返した候補のキーワードには当たるものがありませんでした」
```

文言は「返した候補について」しか主張していないので嘘ではない。しかし**カタログに答えられるデータが実在するのに「答えられなかった」と見せる**ことになり、[DOMAIN.md](./DOMAIN.md) §7 の実演としては誤った見せ方になる（[Issue #84](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/84)）。

**`interests` があるときは、まだ覆えていない興味を最も多く覆う候補から順に枠を確保し、残り枠をスコア順で埋める。**

| 呼び出し | 候補 |
| --- | --- |
| `{ interests: ["ラーメン","文化","家族向け","自然"], limit: 4 }` | 名所・史跡／文化観光施設／トイレ情報／都市公園・都立公園一覧（自然の欠損は出ない。ラーメンは従来どおり粒度不足） |
| `{ query: "文化、家族向け、自然", limit: 4 }` | 名所・史跡／文化観光施設／文化財一覧／トイレ情報（**自然文に畳み込むと効かない**。都市公園は落ちる） |
| `{ query: "上野の美術館", interests: ["文化","自然"], limit: 2 }` | 文化観光施設／文化財一覧（自然の一致先は渋谷収録なので上野の絞り込みに入らない。欠損は従来どおり出る） |
| `{ interests: ["ラーメン","文化","家族向け","自然"], limit: 6 }` | 同点6件がそのまま返る（**切り捨てが起きないので枠の確保は動かない**。あなたへ画面の現行設定はこちら） |
| `{ interests: ["観光","家族向け","自然"], limit: 2 }` | 名所・史跡／トイレ情報。**「自然」の一致先は候補集合に居るが枠が尽きて入らず、欠損として報告される** |

- **枠の確保に使う述語は、欠損の判定（`interestCovered`）と同一。** 選定と報告が別々の基準を見ていたことが症状の原因なので、ここを揃えるのが修正の本体。別々に戻すと同じ症状が再発する
- **実在する答えがあるのに出ていた欠損しか消さない。** 一致先がカタログに1件も無い興味（ショッピング）や、エリアの絞り込みの外にしか一致先が無い興味（上野で訊かれた「自然」）は確保しようがないので、従来どおり報告される
- **より強い分類で報告済みの興味（ジャンル・マナー・渋谷の観光）には枠を使わない。** ラーメンはここで外れる（`insufficient_granularity` として `collectPartialGaps` が報告済み）。外さないと、報告の役に立たないまま関連度の高い候補を押し出すことになる
- **枠が足りなければ従来どおり欠損になる。** 報告対象の興味が `limit` を超えた分は、一致先が候補集合に居ても入らない。`interests` は最大20件・`limit` は上限10 なので、**これは仕様上ふつうに起きる入力**。「枠に入らなかっただけなのに欠損に見える」が消えるのは `limit` に収まる範囲だけ
- **偽陽性の一致先を能動的に拾う（既知の限界）。** `interestCovered` は部分一致でしかないため、興味「緑茶」は都市公園のキーワード「緑」に当たる。旧実装ではこの誤マッチが効くのは「たまたま枠内に居たとき」だけだったが、いまは探しに行って枠に座らせ、スコアの高い候補を押し出し、欠損も消す。**枠を確保できた＝その興味に本当に答えた、ではない**（選定と報告が同じ盲点を共有する）。直すには興味の語の分解が要り、それは Step 5 の LLM 側の仕事。興味チップのラベルを決める側は、キーワード表（`worker/core/catalog.ts`）の語を**含まない**ラベルほど判定が正確になる
- **貪欲法なので最小の枠数になるとは限らない。** 各段で「まだ覆えていない興味を最も多く覆う候補」を取るだけで、全体最適（集合被覆）は解かない。同数のときは `usable` の順（スコア降順 → `no` 昇順）で決める
- **`no` 昇順は残る。** 残り枠を埋める段の同点解決は引き続きカタログ登録順で、変わったのは「先に枠を確保する段が入った」ことだけ。同点内の順位が関連度を表さない点は変わらない
- **効くのは `interests` を送った呼び出しだけ。** 自然文に畳み込まれた興味は分解できない（Issue #53 と同じ理由 — 分解は Step 5 の LLM 側の仕事で、スタブに形態素解析を持ち込まない）。プラン画面も興味チップを選んだ呼び出しでは `interests` を送るため（Issue #53 で構造化送信へ切り替え。チップ未選択で自由文だけなら従来どおり）、キーワードの一致が `limit: 4` を超えれば枠の確保が働く。**あなたへ画面は現行の `limit: 6` では切り捨てが起きず、枠の確保は動かない**（発火するのは `limit` を下げた場合と、API コンソール・将来の `/mcp` からの直接呼び出し）
- **返す順序はスコア順のまま。** 確保した枠は「入れるかどうか」にだけ効かせ、並びは従来どおり（スコア降順 → `no` 昇順）の部分列にする
- **エリアの取り落ち（上記）には同じ手当てを入れていない。** あちらは候補の絞り込み自体が1エリアぶんなので、覆えないエリアのデータセットはそもそも選定の対象集合に入らない。対処は `limit` の配分とスコアリングの再設計を伴うため Step 5 で扱う

> **未合意**: 画面での表示方法はフロントエンド担当と未合意（[Issue #29](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/29) の DoD）。[API_REQUIREMENTS.md](./API_REQUIREMENTS.md) に**提案**として記載してある。

### 3.2 `aggregate_dataset` — 集計（`POST /api/aggregate-dataset`・確定）

特定したデータセットに対して集計・抽出を行う（Step 5 で Text-to-SQL に差し替え）。

| 項目 | 内容 |
| ---- | ---- |
| 入力 | `{ datasetId: string, intent: string }`。両方必須 |
| 出力（回答あり） | `{ status: "answered", result: { name, summary }, query: string }` |
| 出力（回答なし） | `{ status: "unanswered", reason, message }` |
| 出力語彙 | `result` は **`name` / `summary` の汎用語彙**（設計原則4）。`Stop.place` / `Stop.note` へのマッピングはフロントエンド側の責務（2026-08-17 合意） |
| `query` | 実行したクエリ。**省略不可**（§4）。スタブは SQL を実行していないため、SQL 風の文字列ではなく「どのスナップショットのヘッダを除く何行目を、どう選んで固定で返したか」を記録する。行の選定根拠（固定サンプルのうち当該エリアの最初の1件 / 既知のエリア名が見つからず固定サンプルの先頭）と、**intent の内容との照合はしていない**ことを必ず含む（[Issue #78](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/78)） |
| `intent` のエリア | **指定されたエリアの地物しか返さない。** 一致する行が無ければ `unanswered`（そのデータセットが当該エリアを収録していなければ `data_not_published`）。対象エリア外の地名は `search_datasets` と同じく `out_of_area`。別エリアの行で代替すると、本物の出典がついた誤答になる |
| `intent` に既知のエリア名が無い場合 | 固定サンプルの先頭を代表として返す。「エリア無指定」とは断定しない — 判定は既知の語彙表（代表エリア・対象外エリア）への照合であって網羅ではなく、未知の地名（例: 巣鴨）が書かれていてもこの経路に落ちる。**intent の内容との照合はどの経路でも行っていない**（内容側のガードは飲食店データセットへのジャンル指定のみ）。選定が収録順に依存する事実は `query` に明記して読み取れるようにする（[Issue #78](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/78)）。内容適合そのものは Step 5（[Issue #32](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/32)・Text-to-SQL）で解消する |
| 未確定 | 対応する集計操作の範囲（Step 5 で確定）、`result` に集計値そのもの（件数・平均等）を載せる形 |

### 3.3 `get_provenance` — 出典取得（`POST /api/provenance`・確定）

回答に添付する出典情報を構造的に返す。

| 項目 | 内容 |
| ---- | ---- |
| 入力 | `{ datasetIds: string[], query: string }`。`datasetIds` は1件以上、`query` は必須（集計を経た場合は実行クエリ、検索のみの経路では検索条件） |
| 出力（回答あり） | `{ status: "answered", sources: ProvenanceSource[] }`。`ProvenanceSource` は `datasetId` / `datasetTitle` / `provider` / `license: "CC BY 4.0"` / `url` / `query` / `retrievedAt` の7フィールド（§4 の必須項目と同一）。`sources` は**必ず1件以上** |
| 出力（回答なし） | `{ status: "unanswered", reason, message }` |
| 複数データセット横断 | 入力の `query` を各 source に同じ値で複写する（source ごとに別のクエリを持たせない）。同じ `datasetId` を重ねて渡されても出典は1件にまとめる。**知らない `datasetId` が1件でも混ざったら、既知のぶんだけ返さず全体を `unanswered` にする**（黙って落とすと呼び出し側が「出典が揃った」と誤認するため） |
| 未確定 | 複数ソースを画面上でどう並べるか（表示ルールはフロントエンド側の決定事項） |

## 4. 共通仕様

> 本節は `/api/*` と `/mcp` の**両経路に適用される**（出典強制の不変条件は両方の経路で満たす。担保は「必ず `worker/core/` を通す」構造で行う。ADR-008「影響」）。

### 応答の必須要素

すべての応答は次のいずれかの形をとる。

1. **回答あり**: 結果 ＋ 根拠情報（`status: "answered"`）
2. **回答なし**: 未回答理由の分類 ＋ 確かめた事実を述べる `message`（`status: "unanswered"`）

`message` に「該当するオープンデータが（あり／見つかり）ません」の**名乗りの一文を付けない**（[Issue #107](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/107)）。画面（プラン画面・あなたへ画面）が同じ一文を未回答の見出しとして描画するため、`message` 側が名乗ると見出しと本文で重複する。「回答なし」であることは `status` / `reason`（画面では見出し）が担い、`message` は確かめた事実だけを書く。

`message` の述語は、無いことを**確かめた**分岐（ジャンル粒度・対象エリア外・渋谷の観光データ欠損・マナー解説の欠損）では断定・言い切り（「〜答えられません」「公開されていません」「確認済みです」「対象エリアの外です」）、キーワード表に**当たらなかっただけ**の分岐（分類指定の空振り・最後のフォールバック）では照合の結果（「〜ありませんでした」）と使い分ける（[Issue #59](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/59)）。確かめていないことを断定しないため（CLAUDE.md 絶対ルール #1）。この使い分けが成立するのは `message` の中だけで、画面の見出しは分類を問わず固定文（見出しの扱いは [Issue #110](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/110)）。

回答なしの形は3操作で共通（**HTTP 200**。エラーにしない）。

```ts
{
  status: "unanswered";
  reason: "data_not_published" | "insufficient_granularity" | "out_of_area" | "other";
  message: string;   // 画面に出せる日本語。何が無くて答えられなかったのかを具体的に書く
}
```

`reason` の値は D1 の `gaps.reason` の CHECK 制約（`migrations/0001_init.sql`）と同一で、自由文字列は許さない。分類が増殖すると未回答を集計できなくなり、データ公開リクエストへの還元（[DOMAIN.md](./DOMAIN.md) §7）が成立しないため。

| `reason` | 使う場面 |
| -------- | -------- |
| `data_not_published` | カタログに該当データが存在しないことを**確かめられた**場合（例: 渋谷区は観光・名所・文化施設のデータを公開していない）。最も強い主張なので、迷ったら使わない |
| `insufficient_granularity` | データはあるが問いに答えられる粒度ではない（例: 飲食店データにジャンルの列が無い） |
| `out_of_area` | POC の対象エリア（上野・浅草・渋谷）の外 |
| `other` | 上記のいずれにも当てはまらない。**利用中の10件では答えられない**（カタログ全体に無いとは言えない）場合もここ |

「利用中の10件に無いデータセットID」は `other` に分類する。これはオープンデータの欠損ではなく呼び出し側の指定違いなので、`data_not_published` に混ぜると未回答の集計（[DOMAIN.md](./DOMAIN.md) §7 のデータ公開リクエスト）が汚れる。

「根拠情報」の必須項目は操作の性質で決まる。

| コア操作 | 根拠情報として必須 |
| ------ | ------------------ |
| `search_datasets` | データセットID・タイトル・提供元・URL（**実行クエリは持たない**。検索条件を添える） |
| `aggregate_dataset` | 上記に加えて**実行クエリ**（集計を伴うため） |
| `get_provenance` | データセットID・タイトル・提供元・URL・ライセンス表記・取得日。集計を経た場合はその実行クエリ |

- 出典を伴わない「回答あり」は**仕様違反**として扱う
- 集計を経ない経路（「周辺」「あなたへ」のように `search_datasets` → `get_provenance` と辿る場合）では、実行クエリの代わりに検索条件を根拠情報とする。**実行クエリの不在を理由に出典を省略してはならない**

### エラーレスポンス

エラーは「**入力の形が仕様を満たさない**」場合だけに使う（2026-08-17 確定・Issue #22）。

```ts
{ error: "invalid_request" | "not_found" | "internal_error"; message?: string }
```

| HTTP | `error` | 発生条件 |
| ---- | ------- | -------- |
| 400 | `invalid_request` | ボディが JSON として読めない／JSON オブジェクトでない／必須項目の欠落・空文字／`limit` が 1〜10 の整数でない |
| 404 | `not_found` | 未定義の `/api/*` パス（定義済みパスに別メソッドで来た場合もここに落ちる） |
| 500 | `internal_error` | 想定外の例外。Hono の既定応答（`text/plain`）に落とさず JSON を返す（未定義パスを 404 の JSON にしているのと同じ理由）。原因は `console.error` に記録する |

- 「データが見つからない」は**エラーではなく正常な回答なし**（`unanswered`・HTTP 200）として区別すること。混ぜると、データ欠損が入力ミスに紛れて集計できなくなる
- 「利用中の10件に無いデータセットID」は入力エラーではなく `unanswered`（`other`）として返す。呼び出し経路によって扱いが変わらないようにするため
- 文字列の入力は境界で trim する。転送時の書式ノイズ（`"t131067d0000000251\n"` など）が「データが無い」として未回答の統計に積み上がるのを防ぐため
- `/mcp` は MCP のエラー表現に合わせるが、エラー分類は `worker/core/` で共通化する（未実装）
