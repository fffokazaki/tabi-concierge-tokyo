# API.md - API設計書（フロントエンド ↔ バックエンド `/api/*`）

> 本システムのバックエンドは、単一の Cloudflare Worker が2つの入口を持つ（[ADR-008](../06-reference/DECISIONS.md)）。本書はそのうち **React アプリが呼ぶ `/api/*`（JSON / Hono）** の設計書である。もう1つの入口 `/mcp`（AI クライアント向けの MCP ツール公開・基盤開放面）は [MCP.md](./MCP.md) を参照。
>
> 両面は `worker/core/` の**同じコア操作**を露出する薄い皮であり、**入出力スキーマと共通仕様の SSOT は本書 §3・§4 に置く**（MCP.md には二重定義しない）。
>
> **エンドポイントパス・コア操作名・引数スキーマはすべて仮称であり未確定。** POC 実装時に確定させ、本書を更新すること（推測で確定扱いにしない）。実装済みは `GET /api/health` のみ（2026-08-16 時点）。

## 1. API概要

### API基本情報

| 項目 | 内容 |
| ---- | ---- |
| 種別 | JSON API（Cloudflare Worker 上の Hono ルーティング、パスは `/api/*`） |
| ベース URL | SPA と同一の Worker（<https://tabi-concierge-tokyo.opendata-002.workers.dev>）。SPA は同じ Worker の静的アセットとして配信されるため、フロントエンドから見て**同一オリジン** |
| 認証 | なし（POC。§2 参照） |
| 想定クライアント | 旅コンシェルジュTOKYO（React SPA）のみ。Claude Desktop 等の AI クライアント・翌年のハッカソン参加者は `/mcp`（[MCP.md](./MCP.md)）を使う |

### API設計原則

1. **最小3操作から始める**: データセット検索・集計・出典取得。必要性が実証された操作だけを追加する
2. **出典なしの応答を返さない**: 根拠となるデータセットを提示できない場合、「回答なし」を明示的に返す。曖昧な推測を返さない
3. **未回答は失敗ではなく出力**: 答えられなかった質問は `unanswered` として記録し、データ公開リクエストの入力にする（silent failure を作らない）
4. **アプリ固有の語彙を持ち込まない**: 「旅程」「マナー」等の旅行アプリ都合の概念はクライアント側の責務。コア操作はデータセットの検索・集計・出典という汎用語彙に留める（同じ操作を `/mcp` でそのまま開放するため）
5. **ロジックは `worker/core/` のみに書く**: `/api/*` と `/mcp` は同じコア関数を呼ぶ薄いアダプタに徹し、ロジックを二重に書かない（ADR-008「AIへの指示」）

## 3. エンドポイント一覧

コア操作名（`search_datasets` 等）は `worker/core/` の関数名および `/mcp` のツール名に対応する共通の語彙で、仮称・未確定。エンドポイントパスも同様に仮称。

### 3.0 `GET /api/health` — 疎通確認（実装済み）

| 項目 | 内容 |
| ---- | ---- |
| 入力 | なし |
| 出力 | `{ status: "ok", service: "tabi-concierge-tokyo", runtime: <workerd の userAgent 実値> }` |
| 備考 | デプロイ経路の生存確認用（`worker/index.ts`）。フロントエンド側の障害種別ハンドリングは Issue #14 / PR #15 参照 |

なお、未定義の `/api/*` パスは静的アセット（SPA の index.html）へフォールバックさせず、`{ "error": "not_found" }` の 404 を返す（クライアントが JSON を期待して壊れるのを防ぐため）。

### 3.1 `search_datasets`（仮称）— データセット検索

自然言語の質問から、答えの根拠になりうるデータセットをメタデータRAG で特定する。エンドポイントは `POST /api/search-datasets`（仮称）を想定。

| 項目 | 内容 |
| ---- | ---- |
| 入力 | 質問文（自然言語）、任意でエリア・カテゴリ等の絞り込み条件 |
| 出力 | データセット候補のリスト（カタログID・タイトル・提供元・URL・適合理由） |
| 未確定 | 引数スキーマ、候補件数の上限、スコアリング方法 |

### 3.2 `aggregate_dataset`（仮称）— 集計

特定したデータセットに対して、その場で集計・抽出を行う（Text-to-SQL）。エンドポイントは `POST /api/aggregate-dataset`（仮称）を想定。

| 項目 | 内容 |
| ---- | ---- |
| 入力 | データセットID、集計意図（自然言語または構造化条件） |
| 出力 | 集計結果と、**実行したクエリ**（出典に添えるため必須） |
| 未確定 | 引数スキーマ、対応する集計操作の範囲、エラー時の返却形式 |

### 3.3 `get_provenance`（仮称）— 出典取得

回答に添付する出典情報（データセットリンク・提供元・ライセンス表記・取得日）を構造的に返す。エンドポイントは `POST /api/provenance`（仮称）を想定。

| 項目 | 内容 |
| ---- | ---- |
| 入力 | データセットID（複数可）、実行クエリ（集計を経た場合のみ。検索のみの経路では検索条件） |
| 出力 | 出典チップ表示に必要な構造化データ（データセットID・タイトル・URL・提供元・CC BY 4.0 表記・取得日。§4 の必須項目と同一） |
| 未確定 | 引数スキーマ、複数データセット横断時の表記ルール |

## 4. 共通仕様

> 本節は `/api/*` と `/mcp` の**両経路に適用される**（出典強制の不変条件は両方の経路で満たす。担保は「必ず `worker/core/` を通す」構造で行う。ADR-008「影響」）。

### 応答の必須要素

すべての応答は次のいずれかの形をとる。

1. **回答あり**: 結果 ＋ 根拠情報
2. **回答なし**: 「該当するオープンデータがありません」＋ 未回答理由の分類（データ未公開 / 粒度不足 / 対象エリア外 等）

「根拠情報」の必須項目は操作の性質で決まる。

| コア操作 | 根拠情報として必須 |
| ------ | ------------------ |
| `search_datasets` | データセットID・タイトル・提供元・URL（**実行クエリは持たない**。検索条件を添える） |
| `aggregate_dataset` | 上記に加えて**実行クエリ**（集計を伴うため） |
| `get_provenance` | データセットID・タイトル・提供元・URL・ライセンス表記・取得日。集計を経た場合はその実行クエリ |

- 出典を伴わない「回答あり」は**仕様違反**として扱う
- 集計を経ない経路（「周辺」「あなたへ」のように `search_datasets` → `get_provenance` と辿る場合）では、実行クエリの代わりに検索条件を根拠情報とする。**実行クエリの不在を理由に出典を省略してはならない**

### エラーレスポンス

- 未定（実装時に定義する。`/api/*` は HTTP ステータス＋JSON、`/mcp` は MCP のエラー表現に合わせるが、エラー分類は `worker/core/` で共通化する）
- 「データが見つからない」は**エラーではなく正常な回答なし**として区別すること

### ページネーション
