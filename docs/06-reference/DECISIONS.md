# DECISIONS.md - アーキテクチャ決定記録（ADR）

> 本プロジェクトの設計判断を記録する。決定の一次情報は Notion のミーティングノート（[PROJECT.md](../01-context/PROJECT.md) §1 参照）にあり、本書はそれを ADR 形式で構造化したもの。

## ADR-001: 企画をオープンデータ・コンシェルジュ1案に絞り込む

### ステータス

承認済み（2026-08-07 ハドルMTG）

### コンテキスト

チームは4案（オープンデータ・コンシェルジュ／障がい者ナビ／Travel Companion／Sports Connect）を検討していた。ハッカソンまでの時間が限られる中、複数案の並行検討はどれも中途半端になるリスクがあった。

### 決定

オープンデータ・コンシェルジュ1案に絞る。他の3案は取り下げる（元資料はチャット履歴に保存）。

### 理由

- 主催者（東京都）自身の課題である「公開と活用の断絶」（約9,600データセット vs 1日約200PV）に正面から答えられる
- 「1データ＝1アプリ」という活用の型そのものを問い直す提案であり、審査基準のアイデア力・データ活用の両方に効く
- 他案で出た知見（「マナーなど書かれていない＝オープンデータの欠損」）を、本案の「あるべきオープンデータの提案エンジン」に取り込める

### 影響

- **ポジティブ**: 準備リソースを1案に集中できる。他案の知見も捨てずに済む
- **ネガティブ**: 案の分散によるリスクヘッジができない

### 代替案比較

| 選択肢 | メリット | デメリット | 却下理由 |
| ------ | -------- | ---------- | -------- |
| 4案の並行検討 | 有望な案を後から選べる | 準備が分散し、どれも完成度が上がらない | 提出までの期間が短い |
| 障がい者ナビ等の単独案 | 対象課題が明確 | 「1データ＝1アプリ」の型を踏襲してしまう | 主催者の課題構造に踏み込めない |

### 関連

- ADR-004（スコープ確定）

## ADR-002: バックエンドを主催者提供スタック（OpenCode ＋ Cloudflare）で完結させる

### ステータス

承認済み（2026-08-07）

### コンテキスト

バックエンド（メタデータRAG ＋ Text-to-SQL ＋ 出典強制）の実行基盤を選ぶ必要があった。ハッカソン期間中に環境構築へ時間を割く余裕はない。

### 決定

主催者が提供するスタック（OpenCode ＋ Cloudflare Workers AI）で完結させる。

### 理由

- 主催者公認スタックであり、審査における技術的な実現性の説明が容易
- 環境構築コストが小さく、実装時間を機能に充てられる
- サーバーレスのためインフラ運用の負担がない

### 影響

- **ポジティブ**: 実装着手が早い。技術力の審査観点で公式スタック利用を明記できる
- **ネガティブ**: 実行環境の制約（利用枠・機能）を受け入れる必要がある。バージョン情報が未確認のまま着手する項目が残る

### AIへの指示

- **必須**: 実装着手時に OpenCode / Cloudflare の実バージョンを確認し、[ARCHITECTURE.md](../02-design/ARCHITECTURE.md) §8 の「未確認」を実値へ更新すること
- **禁止**: バージョンを推測で記載すること

### 関連

- [ARCHITECTURE.md](../02-design/ARCHITECTURE.md) §8

## ADR-003: フロント＝旅行アプリ／バック＝コンシェルジュを MCP で接続する

### ステータス

承認済み（2026-08-15 ミーティング）

### コンテキスト

「オープンデータ・コンシェルジュ」をそのまま画面として見せると、審査員にはチャットボットにしか映らない。一方で、既にショウさん作成の旅行アプリ UI（5機能）が動作確認済みで存在していた。両者をどう位置づけるかを決める必要があった。

### 決定

ユーザーに届けるのは旅行アプリ「旅コンシェルジュTOKYO」（5機能）とし、その背後にオープンデータ・コンシェルジュをバックエンドとして置く。両者は **MCP（Model Context Protocol）** で接続し、最小3ツール（データセット検索・集計・出典取得）から始める。

### 理由

- 旅行者は「オープンデータを使っている」と意識せずに恩恵を受けられる（サービスデザインの審査観点）
- コンシェルジュを MCP サーバーとして独立させることで、旅行アプリは「最初のクライアント」という位置づけになり、翌年のハッカソン参加者への基盤開放が構造として成立する
- 実装済み UI 資産を活かせる

### 影響

- **ポジティブ**: 「1データ＝1アプリ」を終わらせる、という主張が構造として証明される
- **ネガティブ**: MCP 接続レイヤーの実装が追加で必要になる。ツール境界に旅行アプリ固有の語彙を持ち込まない規律が要る

### AIへの指示

- **必須**: MCP ツールは汎用語彙（データセット・集計・出典）で定義すること
- **禁止**: 「旅程」「マナー」等クライアント固有の概念をツール名・引数に持ち込むこと
- **参照すべきファイル**: [API.md](../02-design/API.md)、[DOMAIN.md](../02-design/DOMAIN.md) §2

### 関連

- ADR-005（出典強制）

## ADR-004: 当日スコープを POC レベルに確定する

### ステータス

承認済み（2026-08-15 ミーティング）

### コンテキスト

提出締切（2026-08-23 17:00）まで、実際に開発へ充てられる日数はごく限られる（2026-08-15 のチーム合意では「2日間でフル実装は目指さない」と表現された。暦上は8日あるが、稼働可能日ベースでの判断）。約9,600件の動的取り込みを含むフル実装は明らかに間に合わない。

### 決定

「このコンセプトでこのデータが使える」ことを示す **POC レベル**に留める。具体的には、一部データをダウンロードしてアプリに組み込み、渋谷・上野など代表エリアに絞った画面イメージで示す。動的なバックエンド更新の仕組みは作らず、将来構想として語る。

### 理由

- 提出物に求められるのは実現性の証明であり、完全性ではない
- 既存 UI のモックデータ（渋谷ナイトライフ・上野ファミリー）をオープンデータ由来の内容へ差し替えるだけで代表エリアの画面を作れる
- ライブデモは First Stage で不可のため、動的更新の実演機会がそもそもない

### 影響

- **ポジティブ**: 期限内に「縦に貫通したシナリオ」（データ → 旅程 → 出典）を完成させられる
- **ネガティブ**: 同梱データはスナップショットであり、カタログ最新版との差異が発生する（取得日の明示で対処）

### 関連

- [DATABASE.md](../02-design/DATABASE.md)、[CONSTRAINTS.md](../01-context/CONSTRAINTS.md) §7

## ADR-005: 出典強制を機能要件かつライセンス遵守手段として設計に組み込む

### ステータス

承認済み（2026-08-15。二次利用ルールの確認結果を反映）

### コンテキスト

東京都オープンデータカタログ掲載データは CC BY 4.0 であり、二次利用（加工・組込・商用）は自由だが**出典表示が必要**。一方、カタログに掲載されていない「公表されただけのデータ」は二次利用できない。また、生成AIの回答には根拠のない内容が混入するリスクがある。

### 決定

全回答に出典（データセットリンク＋実行クエリ）を構造的に強制付与する。出典を生成できない場合は回答を生成せず「ありません」と答える。利用データはカタログ掲載データに限定する。

### 理由

- CC BY 4.0 の表示義務をアーキテクチャレベルで自動的に満たせる（コンプライアンスが機能になる）
- 根拠のない生成を構造的に遮断でき、公共データを扱うサービスとしての信頼性が上がる
- 「答えられなかった」ことが可視化され、データ公開リクエストという次の価値に変換できる

### 影響

- **ポジティブ**: 出典クリック率がそのままカタログへの流入という KPI になる。未回答が改善ループの入力になる
- **ネガティブ**: データが存在しない領域では回答できず、体験としては「答えてくれない」場面が生じる（これは欠損の可視化として受け入れる）

### AIへの指示

- **必須**: すべての回答経路を出典生成サービスに通すこと
- **禁止**: 出典を伴わない回答の生成、および未回答の握りつぶし（silent failure）
- **参照すべきファイル**: [DOMAIN.md](../02-design/DOMAIN.md) §8（不変条件）

### 関連

- ADR-003、[CONSTRAINTS.md](../01-context/CONSTRAINTS.md) §3

## ADR-006: PoC 期間の Git Workflow を軽量フローにし、運用ルールをリポジトリ内へ移す

### ステータス

承認済み（2026-08-15）

### コンテキスト

本リポジトリは AI仕様駆動開発を導入し、Issue 起票 → ブランチ → Draft PR → セルフレビュー（ローカル + クロスモデル）→ AC 照合 → squash merge → cleanup → ACE という手順で運用してきた。しかし PoC 段階の作業単位に対しては手数が多く、提出締切（2026-08-23）までの密度に見合わない。

より重要な問題として、**この手順はほぼすべてがメンテナ個人の環境に依存していた**。手順の定義はメンテナのグローバル設定（`~/.claude/CLAUDE.md`）にあり、`/close-issue` `/merge-cleanup` `/ace-curate` は個人が導入した Claude Code プラグインが提供している。本ハッカソンでは**組織外のメンバーが参加する**ため、その人たちから見ると本リポジトリには読める運用ルールが1つも存在しない状態だった（`CLAUDE.md` / `AGENTS.md` / `CONTRIBUTING.md` のいずれも未作成）。

つまり解くべき問題は「重い手順を軽くする」ではなく、「**個人環境にある運用ルールを、プラグインを持たない人でも回せる重さでリポジトリ内へ移す**」ことだった。

### 決定

1. **軽量フローを既定とする**: ブランチ作成 → 実装・コミット → PR 作成 → レビュー → squash merge → ブランチ削除。**Issue 起票は任意**（仕様に議論が必要なとき・作業を分担するときだけ）、**ブランチと PR は必須**（`main` / `develop` への直接コミットは禁止）
2. **一括実行を許可する**: 「マージして」等の指示のタイミングで、ブランチ作成からクリーンアップまでを一括で実行してよい。ステップごとの確認を求めない
3. **ACE（知見記録）は任意**とする。メンテナ環境では必須運用を継続する
4. **運用ルールをリポジトリ内へ置く**: `CLAUDE.md`（Claude Code 向け）・`AGENTS.md`（Codex ほか AI 向け）・`CONTRIBUTING.md`（人間向け）を新規作成し、いずれも外部プラグイン・個人設定に依存せず単独で完結させる
5. **適用期間は当面無期限**とし、実装規模が肥大化した時点で本 ADR を改定する

### 理由

- 外部メンバーにとって、現状の実効ルールは「重い」のではなく「存在しない」。まず読める形にすることが最優先
- ブランチと PR を残せば、Issue を省いても変更履歴とレビュー機会は失われない。逆にこの2つを外すと、外部メンバーの変更がレビューなしで統合ブランチに入る
- Issue 起票の価値は「議論の場」と「分担の可視化」にあり、1人で完結する小さな変更では手数だけが残る
- ACE は蓄積された知見が次の作業を速くする仕組みで、参加期間が短い人には投資回収が起きない

### 影響

- **ポジティブ**: 外部メンバーがリポジトリだけで作業できる。PoC の作業速度が上がる。プラグイン非保有者との運用差が明示される
- **ネガティブ**: Issue を省いた変更は「なぜやったか」が PR 本文だけに残る（PR 本文に理由を書く運用で補う）。ACE を任意にすると知見の蓄積速度が落ちる

### AIへの指示

- **必須**: `develop` からブランチを切り、PR を経由してマージすること
- **禁止**: `main` / `develop` への直接コミット。ステップごとにユーザーへ確認を取って一括実行を止めること
- **参照すべきファイル**: [CLAUDE.md](../../CLAUDE.md) / [AGENTS.md](../../AGENTS.md)

### 関連

- [CONTRIBUTING.md](../../CONTRIBUTING.md)、[PLAYBOOK.md](../08-knowledge/PLAYBOOK.md)（ACE の任意運用）

## ADR-007: Cloudflare D1 を採用し、ADR-004 の「DB 不使用」を限定解除する

### ステータス

承認済み（2026-08-16）

### コンテキスト

ADR-004 は当日スコープを POC に絞る判断として「データベースは使用しない／ダウンロード済みデータを同梱する」と決めた。しかし実装アーキテクチャを具体化する段階で、この決定が2つの要求と衝突することが判明した。

1. **企画が「Text-to-SQL」を技術的主張として掲げている**。データを静的 JSON のまま持つと SQL は1行も実行されず、主張の裏付けが図解だけになる
2. **[DOMAIN.md](../02-design/DOMAIN.md) §8 の不変条件「未回答は必ず理由分類され、記録される」**を満たす保持先が無い。同 §10 では未回答リポジトリの保持先が「未定」のまま宙に浮いていた

加えて Cloudflare Workers の無料枠には **CPU 10ms / リクエスト**という制約があり、リクエストのたびに CSV / GeoJSON をパースして集計する設計はこの上限に当たりやすい（D1 のクエリ待ち時間は CPU 時間にカウントされない）。

### 決定

**Cloudflare D1 を採用する。** 用途は次の2つに限定する。

| 用途 | 内容 |
| --- | --- |
| オープンデータの格納 | 選定したデータセットをテーブル化し、`aggregate_dataset` が実際に SQL を実行する |
| 未回答ログ（`gaps` テーブル） | 未回答の理由分類を記録する。書き込みは `await` し、失敗を握りつぶさない |

ADR-004 は撤回しない。**その意図は「約9,600件の動的取り込みをしない」ことであり、アプリケーション状態の永続化を禁じたものではない**、と解釈を明確化したうえでの限定解除とする。

### 理由

- 企画が主張する Text-to-SQL が、図解ではなく実際に動く形になる
- 宙に浮いていた不変条件（未回答の記録）の保持先が決まる
- CPU 10ms の制約に対して、集計を D1 側へ寄せるのが素直（同梱 JSON を毎回パースする案の方が CPU 的に危険だった）
- 無料枠（500MB / 5M 行読/日 / 100k 行書/日）に対して10データセット規模は2桁の余裕がある

### 影響

- **ポジティブ**: 技術的主張が実物になる。不変条件が実装可能になる
- **ネガティブ**: スキーマ設計とデータ取り込みの手間が増える（実データの列名・欠損値・全角数字の揺れは必ず手間取る）。マイグレーションという運用対象が1つ増える

### AIへの指示

- **必須**: 開発中は**ローカル D1**（`wrangler dev` の既定）を使う。全データセットのフル再取り込みは約60,000行書き込みで、リモートだと無料枠の日次上限に対し1日1.6回しかできない
- **必須**: Text-to-SQL のリトライ回数に上限を切る（subrequest 50/リクエストに当たるため）
- **禁止**: リクエスト時に CSV / GeoJSON をパースすること（CPU 10ms を超える）
- **禁止**: `gaps` への書き込みを `ctx.waitUntil()` に投げっぱなしにすること（書き込み失敗が観測されず silent failure になる）

### 関連

- ADR-004（POC スコープ）、ADR-005（出典強制）、[DATABASE.md](../02-design/DATABASE.md)

## ADR-008: 単一 Worker で `/api/*` と `/mcp` を二面公開する

### ステータス

承認済み（2026-08-15）

### コンテキスト

ADR-003 で「フロントエンドは MCP でバックエンドに接続する」と決めたが、実装を具体化する段階で前提の誤りが判明した。**MCP は AI エージェントがツールを選んで呼ぶためのプロトコルであり、ブラウザ ↔ サーバー間の汎用 API プロトコルではない。** React アプリは「何を呼ぶか」を最初から知っているため、MCP を挟んでもツール一覧の取得・セッション確立・JSON-RPC ラッパーというオーバーヘッドが増えるだけで得るものがない。

一方、MCP を捨てると ADR-003 の核心である「旅行アプリは最初のクライアントにすぎない／基盤を翌年の参加者へ開放する」という主張の裏付けが失われる。

### 決定

単一の Cloudflare Worker が2つの入口を持つ構成にする。コアロジック（検索・集計・出典生成）は `worker/core/` に1つだけ置き、外側の皮を2枚にする。

| 入口 | 相手 | 形式 |
| --- | --- | --- |
| `/api/*` | React アプリ | 通常の JSON（Hono） |
| `/mcp` | Claude Desktop・翌年の参加者・審査員の手元 | MCP（Streamable HTTP） |

MCP の実装には `agents/mcp/server` の **`createMcpHandler`** を使う。`McpAgent` は公式ドキュメントで **deprecated / feature-frozen** と明記されており、新規サーバーには使わない。`createMcpHandler` はステートレスなため **Durable Objects もマイグレーションも不要**。

### 理由

- ブラウザからは素直な JSON、AI クライアントからは MCP という、それぞれに適した形で提供できる
- 「旅行アプリは最初のクライアントにすぎない」が、**実際に2つ目のクライアントが接続する形**で証明できる。審査席で Claude Desktop から同じサーバーへ繋いで見せられる
- コアが1つなので、二面公開の追加コストは薄いアダプタ層のみ

### 影響

- **ポジティブ**: ADR-003 の主張が図解ではなく実物になる。フロントエンドの実装が単純になる
- **ネガティブ**: 入口が2つあるぶん、出典強制の不変条件を**両方の経路で**満たす必要がある（`core/` を必ず通す設計で担保する）

### AIへの指示

- **必須**: `/api/*` と `/mcp` は `worker/core/` の同じ関数を呼ぶこと。ロジックを二重に書かない
- **禁止**: `McpAgent` を使うこと（deprecated）。React 側に MCP クライアントを実装すること
- **参照すべきファイル**: [API.md](../02-design/API.md)

### 関連

- ADR-003（MCP 接続の決定）、ADR-005（出典強制）

## ADR-009: `main` の運用は保留し、PoC 期間は `develop` を単一の統合ブランチとする

### ステータス

承認済み（2026-08-17）

### コンテキスト

リポジトリには `main` と `develop` の2ブランチが存在するが、**`main` を何に使うかを決めていない**。2026-08-17 時点で `main` は `develop` から **43 コミット遅れ**ており、実質的に放置されている。

一方で運用の実態は次のとおり、すべて `develop` を軸に回っている。

- デフォルトブランチは `develop`（PR の base、`Closes #N` の発火先）
- [ADR-006](#adr-006-poc-期間の-git-workflow-を軽量フローにし運用ルールをリポジトリ内へ移す) の軽量フローは `develop` から切って `develop` へ戻す
- Cloudflare へのデプロイは `develop` の内容を手動で反映する（`main` は経由しない）

にもかかわらず [DEPLOYMENT.md](../05-operations/DEPLOYMENT.md) §1 のブランチ戦略には、テンプレート由来の Git Flow（`main` / `release/*` / `hotfix/*`）がそのまま残っていた。**文書が実態と食い違ったまま、外部メンバーに「`main` が本番リリース」と読ませる状態**になっていた。

### 決定

1. **`main` の運用方針は保留する。** 本番リリースの受け皿にするか、単に削除するか、提出後のアーカイブ点にするかを決めていない。**決めていないことを、決めていないと記録する**
2. **PoC 期間中は `develop` を唯一の統合ブランチとして扱う。** 実装・ドキュメント・デプロイのすべてが `develop` を指す
3. `release/*` / `hotfix/*` は**使わない**。リリース列を持たないため、これらを分ける意味が無い
4. **`main` への直接コミット禁止は維持する**（ADR-006 の決定1）。放置しているブランチだからこそ、意図しない差分を入れない
5. 提出（2026-08-23）後、`main` の位置づけを改めて決める。そのとき本 ADR を改定する

### 理由

- **PoC には並行リリース列が無い。** リリース列が1本しかないなら、統合ブランチも1本でよい。`main` を維持する作業（同期・整合確認）は、それが守る対象が無いまま発生する純粋なコスト
- **「未定」を明示しないと、既定の解釈が入り込む。** ブランチ名 `main` は「本番」を強く連想させ、テンプレート由来の Git Flow 記述と合わさって、実際には誰も更新していないブランチが本番だと誤読される
- 締切まで6日の時点で分岐戦略を新設するのは、得られるものに対してリスクが大きい
- **削除ではなく保留を選んだのは、判断材料が揃っていないため。** 提出後に「公開用の安定版を `main` に置く」判断があり得る

### 影響

- **ポジティブ**:
  - 文書と実態が一致する。外部メンバーが `main` を本番と誤読しない
  - 維持コストの無い運用に収束する
  - 「未定である」ことが記録として残り、提出後に判断を再開できる
- **ネガティブ**:
  - `main` は `develop` から乖離し続ける（意図した状態だが、リポジトリを一見した人には不自然に映る）
  - 本番相当のコードを指すブランチが無いため、**「今デプロイされているもの」は Git ではなく Cloudflare 側の Version ID でしか辿れない**。デプロイ記録を [DEPLOYMENT.md](../05-operations/DEPLOYMENT.md) §3 に残すことで補う

### AIへの指示

- **必須**: ブランチは `develop` から切り、`develop` へ PR を出す
- **禁止**: `main` へのコミット・マージ・`main` を base にした PR。`release/*` / `hotfix/*` の作成
- **参照すべきファイル**: [CLAUDE.md](../../CLAUDE.md) / [DEPLOYMENT.md](../05-operations/DEPLOYMENT.md) §1

### 関連

- [ADR-006](#adr-006-poc-期間の-git-workflow-を軽量フローにし運用ルールをリポジトリ内へ移す)（軽量フロー）
- [Issue #46](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/46)（本番反映の契機を決める）

## ADR-010: マナー解説はカタログ外から補わず、調査済み欠損としてデータ公開リクエストへ還元する

### ステータス

承認済み（2026-08-18）

### コンテキスト

プラン画面のリード文「マナーの解説付きでルートを作成します」に応えるデータが無い。[Issue #31](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/31) で仮データ（`mockScenarios.ts` の「鳥居をくぐる前に一礼し…」等。出典を持たない）を削除して以来、マナー欄は空である。

[Issue #43](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/43) の調査（2026-08-17・[DATABASE.md](../02-design/DATABASE.md) §2）で次が確定した。

- マナー解説そのものはカタログ約9,600件に **0 件**（作法／エチケット／参拝／おもてなし／ピクトグラム 各0件。「マナー」6件は調査統計・路上禁煙地区で訪日客向け作法は0件）
- 「ルールを場所として公開したデータ」（公衆喫煙所・ごみ分別・路上禁煙地区）は代表エリアにもカタログ掲載があるが、**5件すべて実体がリンク切れ（HTTP 404）**

Issue #43 は選択肢を4つ挙げていた: A. カタログから探す（→ 無いことを確認済み）／B. 出典を明示した外部情報（神社本庁等）の引用／C. `EtiquetteTip.source` の型で出典種別を分ける／D. 出さない。

### 決定

1. **案B（カタログ外の外部出典）・案C（出典種別の型分け）は採らない。** カタログ掲載データ以外を組み込まない原則（[CONSTRAINTS.md](../01-context/CONSTRAINTS.md) §3）と出典強制の設計（[DOMAIN.md](../02-design/DOMAIN.md) §8）に例外を作らない
2. **マナー・作法の問いには「調査済みの欠損」を返す。** `search_datasets` にマナー系語彙の判定を置き、`unanswered("data_not_published")` として応答する。カタログに無いことを確かめてあるため、最も強い分類を使ってよい
3. **欠損はデータ公開リクエストへの還元（エスカレーション）として扱う。** 応答の `message` で「未回答は記録され、データ公開リクエストの題材になる」ことを利用者に伝える。問い合わせのたびに `gaps` へ記録が積まれ、**頻度がそのまま公開リクエストの根拠データになる**（DOMAIN.md §7）
4. **提出物では、この欠損自体を還元ループの実例として扱う。** 「観光施策のリード文に据えるほど必要とされているデータが、カタログに存在しない」は、オープンデータ・コンシェルジュ層（未回答の可視化 → 都への還元）の最も具体的な実演になる。リンク切れ5件は「公開すると宣言されたデータが取得できない」というカタログ運用そのものへの指摘として添える

### 理由

- **未回答の可視化はこの企画の半分そのもの。** 「探したが無かった」を隠して外部情報で埋めるより、無いことを構造化して還元する方がコアドメインに忠実
- **案Bは出典強制の設計に穴を開ける。** カタログ外データの二次利用は原則不可で、引用の範囲判断が個別に必要になる。外部サイトへのリンクだけなら制約は軽いが、解説を表示できないため「マナー解説機能」の実体にならない
- **案Cの型分けは「出典があるように見える例外」を常設化する。** 一度作ると、以後のデータ欠損もカタログ外で埋める誘因になる
- **`data_not_published` の要件（確かめてあること）を満たしている。** 検索語・件数・実体の取得可否まで DATABASE.md に記録済みで、推測ではない

### 影響

- **ポジティブ**:
  - 出典強制の不変条件に例外を作らずに済む
  - マナーの問い合わせが記録され、還元の根拠データになる
  - 提出ストーリーが「作れませんでした」ではなく「無いことを確認し、必要性の根拠と共に都へ還元する」になる
- **ネガティブ**:
  - プラン画面のマナー欄は空のまま（看板機能の直接的な実演はできない）
  - リード文と実態のずれが残る。フロントエンド側の文言調整（調査済みであることの明示等）は別 Issue で扱う

### AIへの指示

- **必須**: マナー系の問いへの応答は `unanswered("data_not_published")` とし、調査日を `message` に明記する。語彙は**調査で確認した語**に限る（未調査の語で `data_not_published` を返すのは推測）
- **禁止**: カタログ外の出典（神社・自治体サイト等）をマナー解説として組み込むこと。仮データの復活
- **参照すべきファイル**: [DATABASE.md](../02-design/DATABASE.md) §2「マナー解説のデータ欠損」／[DOMAIN.md](../02-design/DOMAIN.md) §7

### 関連

- [Issue #43](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/43)（マナー解説に出典を用意する）
- [ADR-007](#adr-007-cloudflare-d1-を採用しadr-004-のdb-不使用を限定解除する)（`gaps` テーブル＝記録の保持先）

> **追記（2026-08-20）**

> 決定2〜4（`data_not_published` の応答・記録・還元ループ）は本 ADR のまま有効。

## ADR-011: 「何を訊かれたか」は構造化入力で受け、質問文からの推測はフォールバックに留める

### ステータス

承認済み（2026-08-18）

### コンテキスト

`search_datasets` の欠損判定には、自然文 `query` からの推測に**構造上解けない**取り違えが2つ残っていた。

- **興味の取り落ちの沈黙**（[Issue #53](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/53)）: フロントエンドは興味チップを1つの自然文に畳み込んで送る（`buildQuery`）。キーワードが1件でも当たると `answered` になり、答えていない興味は応答のどこにも残らない。**興味を複数選ぶほど何かが当たるので、実際に旅程が組み上がるケースほど欠損が沈黙する**
- **出発地の過検知**（[Issue #58](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/58)）: 「渋谷から上野へ」の渋谷（出発地）と「上野と渋谷を回りたい」の渋谷（目的地）は質問文の形だけでは見分けられず、過検知の側に倒してあった

どちらも解消には自然文の分解（形態素解析）が要るが、スタブに分解規則を作り込むと Step 5 で LLM が担う分解と二重になる（Issue #29 以来の方針）。

### 決定

1. **`search_datasets` に構造化入力 `interests?: string[]`（興味の配列）と `areas?: string[]`（目的地エリアの配列）を optional で追加する。** 呼び出し側は畳み込む前の構造化データを持っている（`trip.interests` は discrete、目的地も UI 上は選択値）ので、畳み込んでから推測で復元するのではなく、**畳み込む前の形をそのまま受ける**
2. **`areas` があるときは質問文からのエリア推測を行わない**（空配列は「目的地なし」の明示）。`interests` は候補マッチに使い、**返した候補が覆っていない興味を1件ずつ `gaps` に載せる**。判定は既存のキーワード表との照合だけで、**形態素解析は持ち込まない**
3. **`query` だけの呼び出しは従来どおり推測で倒したままにする**（興味の取り落ちは沈黙・出発地は過検知）。自然文からの抽出は Step 5 の LLM 側の仕事で、スタブでは解かない（Issue #58 の案(b)を query 経路のフォールバックとして採用）

### 理由

- **区別を知っているのは呼び出し側。** 「どれが興味でどれが目的地か」はフロントエンドが構造として持っている情報で、自然文に畳み込んだ時点で失われる。失われる前に受けるのが、推測の精度を上げるより確実
- **optional 追加なので既存クライアントを壊さない。** フロントエンドの送信側対応（`src/`・担当合意が必要）を待たずにバックエンドを先行できる
- **スタブに分解規則を作り込まない方針（Issue #29・#50・#53 で繰り返し確認）と両立する。** 構造化入力の照合は列挙済みのキーワード表と代表エリア名だけで済む

### 影響

- **ポジティブ**:
  - 構造化して呼べば、興味の取り落とし・出発地の過検知が解消する（`/mcp` の AI クライアントは Step 5 で最初からこの形で呼べる）
  - `gaps` テーブルの `other` の過検知分（DOMAIN.md §7 で差し引く対象）が、構造化呼び出しの普及に応じて減る
- **ネガティブ**:
  - フロントエンドが対応するまで、プラン画面経由の呼び出しは従来の精度のまま（Issue #53 に残作業として記載）
  - `search_datasets` の入力が2系統（自然文／構造化）になり、仕様の説明が長くなる

### AIへの指示

- **必須**: 欠損判定の精度を上げたい場合、まず構造化入力で受けられないかを検討する。質問文からの推測規則（形態素解析・品詞判定・助詞の解釈）をスタブに足すのは禁止
- **禁止**: `areas` があるのに質問文からエリアを拾うこと。`interests` の要素を分解・正規化すること
- **参照すべきファイル**: [API.md](../02-design/API.md) §3.1（入出力の SSOT）／`worker/core/operations.ts`

> **追記（2026-08-21）**
> フロントエンド（プラン画面）の送信側対応は [Issue #53](https://github.com/fffokazaki/tabi-concierge-tokyo/issues/53) の PR #113 で完了した（`interests` + `query`（自由文のみ）の分離送信・`buildSearchInput`）。
> 「影響（ネガティブ）」1点目（プラン画面経由は従来の精度のまま）は解消済み。`areas` は引き続き送らない（エリアの入力欄が無い — Issue #42）。

## ADR-012: マナーの「参考情報」としてJNTOを限定的に組み込む（ADR-010の一部改定）

### ステータス

承認済み（2026-08-20）。**[ADR-010](#adr-010-マナー解説はカタログ外から補わず調査済み欠損としてデータ公開リクエストへ還元する)の決定1（「案B＝カタログ外の外部出典の引用は採らない」）を、下記の限定条件つきで一部改定する。** ADR-010 の決定2〜4（`data_not_published` の応答・記録・還元ループとしての位置づけ）はそのまま維持する。

### コンテキスト

ADR-010 は「マナー解説はカタログ内に無いことを確認済みなので、カタログ外の外部出典（神社本庁等）で埋めない」と決定し、AIへの指示でも「カタログ外の出典をマナー解説として組み込むこと」を明示的に禁止していた。

チームは今回、JNTO（日本政府観光局・`japan.travel`）が公開する訪日観光客向けマナーガイドを、**マナー・作法の参考情報として**追加することを承認した。表示箇所は2つ: **プラン画面のマナー欄**（選択中の停留地のカテゴリに応じて表示）と、**あなたへ画面の各レコメンドカード**（見出しは無いが、性質としてはマナー欄と同じ参考情報という位置づけ）。カテゴリ別に5ページ（神社・寺／銭湯／飲食店／公園・バス停・公共交通／一般）を人手で要約し、要約文と JNTO への出典リンクをセットで表示する。

### 決定

1. **JNTO の要約＋リンクを、マナー・作法の参考情報としてプラン画面のマナー欄・あなたへ画面の各レコメンドカードに追加してよい。ただし以下を満たす場合に限る**:
   - ラベルは「出典」ではなく **「参考: JNTO」**とし、本アプリが「出典」という語をカタログ CC BY 4.0 データの意味で使っている慣用と衝突させない
   - 見た目は `ProvenanceChip`（CC BY 出典チップ）と**似せない**。配色・枠線・アイコンを変え、一見して別種の情報だと分かるようにする
   - **既存の「出典のあるマナー情報はありません」という誠実な空表示（Issue #67）は残したまま、その下に追加する。** 置き換えない — 「カタログには無い」という事実と「参考までに公式情報源を案内する」という別種の情報を両方見せる
   - カテゴリの判定はデータセットの表示タイトルではなく `datasetId`（安定した識別子）で行う
   - 要約文は実際の JNTO ページの内容に基づく（推測で書き足さない。絶対ルール #1 と同じ精神）
2. **この改定はマナー・作法の参考情報としての用途（プラン画面のマナー欄・あなたへ画面の各レコメンドカードの JNTO 参考情報）に限る。** 停留地名・所在地・営業時間など、`回答`（旅程を構成する具体的な事実）に使うデータは引き続きカタログ CC BY 4.0 のみとする。ADR-010・絶対ルール #4 の核である「事実の回答はカタログ外で埋めない」は変えない
3. **CLAUDE.md 絶対ルール #4 に、この例外を簡潔に反映する**（詳細はこの ADR を参照させ、ルール本文を長くしない）

### 理由

- **「マナー」欄の参考情報と「回答」の事実データは、出典なしの回答を作らないという不変条件（DOMAIN.md §8・絶対ルール #2）の適用対象として性質が違う。** 後者は「この場所のこの事実」を主張するものだが、前者は「一般的な作法の参考として、公的な観光案内機関の情報を案内する」ものであり、個別の事実主張ではない。ラベル・見た目を明確に分ければ、利用者が両者を取り違えることはない
- **JNTO は東京都のオープンデータカタログとは無関係な別法人（観光庁所管）であり、CONSTRAINTS.md §3 が禁じる「都の非カタログデータの二次利用」には該当しない。** ADR-010 が実際に守ろうとしていたのは製品設計上の「全回答カタログ由来」という自主的な不変条件であり、チームはこの決定でその不変条件の適用範囲を「回答」に限定し、「参考情報」は対象外と明確化した
- **「マナーの解説付きでルートを作成します」という看板機能を、提出までに実際に見せられる形にする価値がチームの判断で優先された。** ADR-010 が記録した「データが無いことの還元ループ」という提出ストーリーはそのまま活きる（空表示は消さない）ため、どちらの価値も両立できる

### 影響

- **ポジティブ**:
  - マナー欄に初めて具体的な内容が表示される（プラン・あなたへ両方）
  - Issue #67 の誠実な空表示は維持されるため、「データ公開リクエストへの還元」という ADR-010 のストーリーは損なわれない
- **ネガティブ**:
  - アプリ内に「出典（CC BY・カタログ）」と「参考（JNTO・外部）」という2種類の情報源が混在することになり、今後の実装者が両者を混同しないよう継続的な注意が要る
  - JNTO 側の5ページの内容が変わった場合、要約文は自動追従しない（人手更新が必要）。定期確認の仕組みは今回のスコープ外

### AIへの指示

- **必須**: 「参考: JNTO」の表示は `ProvenanceChip` と別コンポーネントにし、ラベル・配色を必ず区別する。カテゴリ判定は `datasetId` で行う（表示タイトルではない）
- **禁止**: この例外をマナー・作法の参考情報以外（停留地の名称・説明・所在地など、回答の事実データ）に広げること。JNTO を含むいかなる外部サイトも「出典」と表示すること（「参考」を使う）。Issue #67 の空表示を JNTO 参考情報に置き換えて消すこと
- **参照すべきファイル**: [ADR-010](#adr-010-マナー解説はカタログ外から補わず調査済み欠損としてデータ公開リクエストへ還元する)（維持される部分の確認）／`src/features/plan/jntoEtiquette.ts`（カテゴリ対応表の実装）
