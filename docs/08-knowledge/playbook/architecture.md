### ACE-28-1: 出典を強制する設計では、フォールバックの既定値が最大の欠陥になる

| Category | architecture | Origin | PR #28 |
| Date | 2026-08-17 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: 「答えが見つからないときに、それらしい既定値を返す」実装は、**出典が本物であるほど危険**になる。出典なしの推測は読み手が疑えるが、実在するデータセットID・提供元・URL が添えられた誤答は「検証済みの答え」に見える。出典強制は、根拠のない回答を防ぐ仕組みであると同時に、**誤答の説得力を上げてしまう装置**でもある。

**Context**: `aggregate_dataset` のスタブで、集計意図のエリアに一致する固定データが無いとき `?? samples.at(0)` で先頭行へ落としていた。10件中6件が片方のエリアの固定データしか持っていなかったため、「浅草で銭湯」の検索結果をそのまま集計に渡すという**設計どおりの経路**で、上野の燕湯が `status: "answered"` ＋ 台東区銭湯データへの出典つきで返った。フロントエンドは `name` を `Stop.place` にマッピングするので、浅草の行程表に上野の銭湯が並ぶ。レビュー9本のうち4本が独立にこれを最重要指摘として挙げた（うち1本は別モデル）。

**Action**: 検索・抽出・推薦のように「該当が無い」があり得る処理では、フォールバックを書く前に**それが誤答になり得るかを問う**。誤答になり得るなら、既定値ではなく「答えられない」を返す。

- `?? 先頭要素` / `|| デフォルト` は、**問いの条件を捨てている**箇所を探す目印になる
- 「答えられない」を返せるように、応答の型に未回答の枝を最初から持たせる（HTTP エラーではなく正常な応答として）
- 「そのエリアを収録していない」と「収録しているがスタブに固定データが無い」は別の理由分類にする。前者はデータの欠損、後者は実装の欠落で、混ぜると欠損の集計が汚れる
- 不変条件は型で表す。空配列を許さない型（`[T, ...T[]]`）にすると、「候補ゼロの回答あり」がコンパイルの時点で作れなくなる

### ACE-39-1: 「他が当たらなかったときだけ発火する判定」を「当たっても報告する」に変えると、誤検知の性質が変わる

| Category | architecture | Origin | PR #39 / Issue #29 |
| Date | 2026-08-17 |
| Helpful | 2 | Harmful | 0 |
| Status | active |

既存の未回答判定を「他の候補が1件も当たらなかったとき」から「当たっていても部分欠損として併記する」へ広げると、それまで**後段のフォールバックに隠されていた誤検知が表に出る**。実際、質問文中の対象エリア外の地名を欠損として報告したところ、「新宿のホテルから上野の美術館へ」の新宿（出発地）まで欠損になった。判定を広げるときは、その語が**求めている対象を指すのか、文脈として書かれただけか**を見分けられるかで採否を決める。見分けられないものは報告しない（推測で埋めるより黙って落とすほうが、応答の信頼度を保てる場面がある）。

### ACE-51-1: ガードは「見ているフィールド」と「置かれた分岐」の両方で到達性を確かめる

| Category | architecture | Origin | PR #51 / Issue #50 |
| Date | 2026-08-18 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: 正しい原則を書いたガードでも、**製品経路が渡さないフィールドを見ていれば存在しないのと同じ**。同じことが分岐にも起きる。ガードを1つの分岐だけに置くと、同じ出力へ到達する他の分岐がそのまま素通りする。ガードの有無ではなく「実際の呼び出し元から、その値が入り、その分岐を通るか」で評価する。

**Context**: `search_datasets` の末尾に `if (input.category?.trim())` のガードがあり、「落とすとトイレや宿泊施設を返すことになる（指定を黙って捨てない）」とコメントまで付いていた。しかし `buildQuery` は興味も要望もすべて `query` に畳み込むため `category` を送らず、送るのはデバッグ用の API コンソールだけ。**唯一の製品経路からこの柵は届いていなかった**。結果、防ぐつもりだった挙動（「ナイトライフ」の問いに渋谷区の都市公園、「ショッピング」の問いに台東区のトイレ情報を、本物の CC BY 出典つきで返す）がそのまま起きていた。徴候はコメント自体にあった — 例示の「『神社』の問いにトイレ」は再現しない（`神社` は名所・史跡の keywords にある）。**到達しない柵の例は検証されないので、腐ったまま残る**。

さらに修正側でも同じ失敗をした。欠損を添える判定を「キーワードが1件も当たらなかった」分岐にだけ置いたため、1語でも当たると無効化された。`"ナイトライフ、上野で夜遊びしたい"` は銭湯のキーワード「夜」が「夜遊び」に部分一致してキーワード経路で `answered` になり、gaps も記録も残らない。興味チップを複数選ぶほど何かが当たるので、**実際に旅程が組み上がるケースほど発火しない**（既定値が既に2つ選択済み）。レビューで「ガードが評価される場所はどこか」と問われて初めて判明した。

**Action**: ガードを書く / レビューするときは次の2つを実測で確かめる。

- **フィールドの到達性**: 実際の呼び出し元を辿り、そのフィールドが populate されるか。されないなら、そのガードは仕様ではなく願望
- **分岐の到達性**: 同じ出力へ至る他の分岐を数え上げ、それぞれで発火するか。1箇所だけに置いた判定は、他の分岐の存在が仕様になる

修正の有効範囲は「直した」と書く前に境界ケースを流して確認し、狭ければ PR 本文と文書に明記して残りを別 Issue にする（→ [ACE-28-1](#ace-28-1) の「フォールバックが誤答になり得るか」と対で使う）。

### ACE-51-3: 欠損・未回答の message には、実測で確かめたことだけを書く

| Category | architecture | Origin | PR #51 / Issue #50 |
| Date | 2026-08-18 |
| Helpful | 3 | Harmful | 0 |
| Status | active |

**Insight**: 「出典なしの回答を作らない」は**回答本文だけの規則ではない**。欠損・未回答の `message` も画面に出る主張なので、同じ検証水準がかかる。実装が確かめていない範囲まで書くと、欠損を可視化するための文が新しい未検証の主張になる。

**Context**: エリア・フォールバックに添える欠損の文言を「質問文の内容に対応するデータセットが**利用中の10件にない**ため…」と書いた。実装が知っているのは「キーワード表に当たらなかった」だけで、10件が問いをカバーするかは判定していない。実際 `"ナイトライフ、上野"` に対して銭湯（営業 15:00〜0:00・キーワードに「夜」）は10件の中に実在する。しかも**同じ10件から候補を返しながら「対応するものが無い」と言う**ので、読み手から見て自己矛盾でもあった。レビューで指摘されて「質問文の語に当たるデータセットが無かったため」に直した。副産物として、残余が助詞だけの過検知（`"上野に行きたい"` など）でも文が嘘にならなくなった。

**Action**: 未回答・欠損の文言は「実際に行ったこと」の記述に留める。同じリポジトリの `describeQuery`（SQL を実行していないスタブで、SQL 風の文字列ではなく「どのスナップショットの何行目を固定で返したか」を書く）が先例。判定の根拠より広い範囲を断定していないか、文ごとに「これはコードが確かめたか」を問う。

### ACE-57-1: 「訊かれたのに答えていない」は、入力で拾い落としたものではなく出力が覆っていないもので判定する

| Category | architecture | Origin | PR #57 / Issue #52 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 要求の取り落ちを検出するとき、**入力側の解析結果**（何を絞り込みに使い、何を使わなかったか）で判定すると、実際には答えられているケースまで欠損になる。**返した結果が要求を覆っているか**を実測で突き合わせると、同じ実装量で「ノイズを足さない」条件まで満たせる。

**Context**: `search_datasets` は質問文から代表エリアを1つだけ選んで候補を絞るため、`"上野・渋谷"` の候補は上野の分だけになり、渋谷の要求が応答にも `gaps` テーブルにも残らなかった。素直な直し方は「絞り込みに使わなかったエリアを欠損にする」だが、それだと `"上野・浅草"` で浅草が欠損になる — 台東区のデータセット8件は**いずれも上野と浅草の両方を収録している**ので、実際には浅草にも答えられている。受け入れ条件が明示的に「ノイズになる欠損を足さない」と要求していた。返した候補の `areas` と訊かれたエリアを突き合わせる形にしたら、`"上野・浅草"` は自然に空になり、`"上野・渋谷"` の渋谷だけが残った。副産物として、キーワードが当たった経路（`"上野の美術館と渋谷の公園"`）でも同じ判定がそのまま効いた。

**Action**: 欠損検出は「何を落としたか」ではなく「**返したもので何が満たせていないか**」で書く。突き合わせに使えるメタデータ（ここでは各データセットの収録エリア）が既にあるなら、入力の解析を精緻化するより先にそれを使う。入力側の判定は「どう解釈したか」しか知らないが、出力側の判定は「実際に何を返したか」を知っている（→ 判定を広げるときの誤検知の性質は [ACE-39-1](#ace-39-1)）。

### ACE-57-2: 「応答から記録を導出する」設計に行ごとの差分が要るなら、応答側に構造化して持たせる

| Category | architecture | Origin | PR #57 / Issue #52 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 「記録は各 return 地点ではなく**応答が確定した1か所**で導出する」設計（書き忘れを構造的に潰す）は、記録の**1行ごとに違う値**が必要になった瞬間に破綻しかける。逃げ道として `message` から値を逆算したくなるが、それは文言を直した瞬間に集計が壊れる。応答そのものに構造化フィールドを足せば、1か所導出を保ったまま行ごとの差分を運べる。

**Context**: `gaps` テーブルの `area` 列には応答全体の解決エリアを入れていた。`"上野・渋谷"` では渋谷についての欠損行まで `area = "上野"` になり、**答えなかったエリアが集計から消える** — 受け入れ条件が名指しで要求していた値がそこだった。`Unanswered` 全体を広げるのではなく、`gaps` の要素型だけを `Gap = Unanswered & { area?: RepresentativeArea }` に広げ、導出側は `gap.area ?? context.area` にした。トップレベルの `unanswered` にも `area` を足すと、そこでは誰も設定しない曖昧なフィールドが増え、`out_of_area` の応答で意味が二重になる。

**Action**: 1か所導出の設計に per-row の差分が要るとわかったら、(1) 導出元（応答）に構造化して持たせる (2) 広げる型は**その差分が実際に出る場所だけ**に絞る。`message` からの逆算は選択肢に入れない。広げた型の doc には「現状これを設定するのはどの欠損か」を書く — 型で縛れない約束なので、次に欠損の種類を足す人が読み直せる形にしておく。

### ACE-57-3: 同じ文型の入力でも、対象範囲の内か外かで過検知の倒し方は逆になる

| Category | architecture | Origin | PR #57 / Issue #52 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 「出発地として書かれた地名を要求と誤認しない」という判断は、**その地名が答えられる対象かどうかで向きが変わる**。対象外の地名は報告しても行動につながらないので黙る側へ、対象内の地名はデータがあり要求の可能性が残るので報告する側へ倒す。「同じ文型だから同じ扱い」で揃えると、片方で必ず間違える。

**Context**: `"新宿から上野へ行きたい"` の新宿（POC 対象外）は Issue #29 で「報告しない」と決めた。同じ形の `"渋谷から上野の美術館へ"` の渋谷は**対象エリアでデータがある**（都市公園123件）ので、揃えて黙らせると渋谷のデータを求めていた場合に落とす — それが直そうとしていた Issue #52 の症状そのもの。逆に倒し、過検知であることを文書とテストに明示して別 Issue（#58）に分離した。クロスモデルレビューは「Issue #29 の方針と不整合」として Important で挙げてきたが、元 Issue 本文にも「対象エリア外と代表エリアで扱いが違う点に注意」とあり、揃えるのが正解ではなかった。

**Action**: 過検知/過少検知の向きは、「報告して外れたときのコスト」と「黙って外れたときのコスト」を**その語が答えられる対象かどうかで分けて**見積もる。決めた向きは**テストで固定する** — コメントだけだと次に触る人が「不整合だ」と揃えてしまう。倒した向きは文書にも書き、区別が要る場合は別 Issue にする。

### ACE-62-1: 応答の共通の書き出しも主張を運ぶ — 分岐で真偽が変わるなら使い分けて契約に書く

| Category | architecture | Origin | PR #62 / Issue #59 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: `unanswered` 応答の統一書き出し「該当するオープンデータがありません」は、それ自体が**存在の断定**を運ぶ。定型句の真偽は分岐によって変わる — 無いことを確かめた分岐（ジャンル粒度・エリア外・渋谷の観光データ）では真、キーワード表に当たらなかっただけの分岐では未確認。分岐で真偽が変わる定型句は、断定形（ありません）と行為の記述形（見つかりませんでした）に分け、**使い分けの基準を契約文書に昇格する**。

**Context**: Issue #59 で message 本文の断定（「10件に対応するものが無い」）は直したが、書き出しの定型句が同じ断定を運んでいることは、クロスモデルレビュー（Codex・信頼度97）が指摘するまで見えなかった。[ACE-51-3](#ace-51-3) の「実測で確かめたことだけを書く」を**本文には適用済みなのに、全分岐共通の「枠」は無検査だった**。書き出しは API.md §4 の応答契約に見える形で書かれていたため、単純削除ではなく「確かめた分岐は断定・照合しただけの分岐は記述」の使い分けとして §4 に明記した。

**Action**: 応答の定型句・共通プレフィックスを見たら、それが運ぶ主張（存在断定・完了断定・網羅断定）を分岐ごとに真偽判定する。分岐で変わるなら定型句を分岐させ、基準を契約文書（API 仕様）に書く。「本文は直したが枠が残る」はセルフレビューの盲点になりやすく、cross-model レビューの価値が出やすい箇所でもある。

### ACE-64-2: 参照側に設定を再掲しない — 定義側のフラグ＋前提が崩れたら生成を止める

| Category | architecture | Origin | PR #64 / Issue #36 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: データセット定義（datasets.ts）を持つ構造で、処理側（seed.ts）に生 ID のリストを再掲すると、typo・ID 変更が**参照 0 件のまま無言で完走**する形で現れる。宣言は定義側の boolean フラグに置き（typo が型・存在レベルで起こり得ない）、処理側は「対象 0 件」「前提の矛盾（継承元が自身も名称判定）」を検出したら生成を止める。

**Context**: エリア継承の索引元を `AREA_INHERITANCE_SOURCE_IDS = ["t131067..."]` と seed.ts に書いた初版に対し、レビューが「ID を書き間違えても継承 0 件で成功する。継承 0 件のときはログ自体が出ないため通知経路も消える」と指摘（CLAUDE.md 絶対ルール #3 と逆向きの挙動）。`DatasetDef.areaInheritanceSource?: true` へ移し、`areaFrom: "name"` との両立（継承の連鎖で根拠が住所列に着地しなくなる）も生成時に拒否した。既存の座標検証（errors → exit 1）と同じ機構に載せた。

**Action**: 定義の一覧が既にあるのに処理側で ID・名前を再掲しそうになったら、定義側の属性（フラグ）に変える。処理側には「選ばれた集合が空」「前提どうしの矛盾」の検出を置き、既存の検証機構（このリポジトリでは seed.ts の errors）に載せて黙って完走させない。

### ACE-66-1: 埋められない看板機能は、欠損の記録頻度を還元の根拠に変える（エスカレーション）

| Category | architecture | Origin | PR #66 / Issue #43 / ADR-010 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 看板機能に必要なデータが存在しないとき、外部ソースで埋める案は出典強制の設計に例外を作り、以後の欠損もカタログ外で埋める誘因になる。このプロジェクトでは「未回答の可視化 → データ公開リクエスト」がドメインの半分なので、**欠損そのものを機能に転換**できる: 調査済みの `data_not_published` を返し、message で「記録され、公開リクエストの題材になる」と利用者に伝え、問い合わせの記録頻度を還元の根拠データにする。

**Context**: マナー解説（プラン画面のリード文の機能）がカタログ約9,600件に 0 件で、外部引用（案B）・出典種別の型分け（案C）が検討されていた。ユーザーの「無いのであればエスカレーションとした方がすっきりする」という方向づけを受け、ADR-010 として決定。「作れませんでした」ではなく「無いことを確認し、必要性の根拠と共に都へ還元する」という提出ストーリーになり、リンク切れ5件（公開宣言済みデータが取得できない）というカタログ運用への指摘も添えられた。

| ---------- | ------------ |
| Category   | architecture |
| Origin     | PR #86 / Issue #84 |
| Date       | 2026-08-19 |

**Insight**: 呼び出し側（フロントエンド）で、呼び出し先（サーバー）の応答の**性質**を前提にした不変条件を組むとき、その性質を実装で確かめずに書くと、被害はコメントの事実誤りだけでは終わらない。**その前提の上に立てた判定ロジックが、狙ったケースで一度も成立しない**。テストは自分が想定した入力で書くため緑のまま通り、空振りしていることに気づけない。

**Context**: `buildRecommendations.ts` の `dedupeGaps` に「集計側の未回答は『どのデータセットで起きたか』を含まない文面なので、複数の候補が同じ理由で落ちると同一の行が並ぶ」と書いた。`worker/core/operations.ts` の `computeAggregateDataset` を読むと**6分岐のうち5つが `${entry.title}` / `${datasetId}` を文面へ埋め込む**（非依存なのは `out_of_area` だけで、しかもあなたへ画面からは到達しない）。その結果、`reason` + `message` を一意キーにした「全滅時に理由が1つに定まるなら分類を引き継ぐ」が**候補2件以上でまず成立せず**、Issue #84 が起こりやすくした多候補ケースで新分岐が効いていなかった。Toolkit のセルフレビューが `operations.ts` を読んで指摘するまで、テスト（自分で書いた単一候補のケース）は全て緑だった。

**Action**: 他レイヤの出力について「〜という性質を持つ」と書きそうになったら、**書く前にその生成箇所を開いて全分岐を数える**。数えられないなら、その性質に依存しない設計にする。キーの粒度は目的別に分けること — 表示の重複防止（`DataGapCard` の React key ＝ `reason` + `message`）と分類の判定（`reason` のみ）を同じキーで兼ねると、片方の都合がもう片方を壊す。あわせて、性質に依存する分岐は**その性質が崩れた入力**（同じ分類・異なる文面）でテストする。関連: [ACE-82-4](./testing.md#ace-82-4)（コメントに書いた実測事実はテストで固定する）。

### ACE-93-2: 個別の判定を全体の分類へ引き上げると主張の範囲が広がる — 強い分類ほど引き上げない

| フィールド | 値           |
| ---------- | ------------ |
| Category   | architecture |
| Origin     | PR #93 / Issue #89 |
| Date       | 2026-08-20 |
| Helpful    | 0            |
| Harmful    | 0            |
| Status     | active       |

**Insight**: 「候補が全滅したのだから、個々の未回答理由をそのまま画面全体の理由として返せばいい」は、**分類が持つ主張の範囲を黙って広げる**。1件のデータセットについて確かめたことを、画面全体について確かめたことにしてしまう。分類の強さは一様ではないので、「引き上げるか否か」ではなく「**どの分類なら引き上げても主張が広がらないか**」を問う必要がある。答えが即座に出ないなら、それは設計判断であって、実装のついでに決めてよいものではない。

**Context**: `buildRecommendations.ts` の全滅パスで、集計側の `unanswered` の `reason` / `message` をそのまま返す実装を一度入れた。`shared/core.ts` は `data_not_published` を「カタログに該当データが存在しないことを確かめられた場合。最も強い主張なので、迷ったら使わない」と定義しているが、`computeAggregateDataset` が返すこの分類の意味は「**その1件のデータセット**が対象エリアの地物を収録していない」でしかない。引き上げると `ForYouScreen` に「該当するオープンデータがありません／分類: data_not_published」と出て、確かめていない範囲を確かめたと主張することになる（絶対ルール #1）。`insufficient_granularity` / `out_of_area` は引き上げても範囲が変わらない、という非対称がある。

**Action**: 個別の判定を集約して全体の判定にするコードを書くときは、**分類ごとに「この判定が主張している範囲」を並べて比較する**。範囲が変わる分類が1つでもあれば、一律の引き上げをやめて汎用分類に倒し、判断の根拠をコード中に残したうえで別 Issue（本件は #94）へ送る。「全部同じ扱いでよいか」を問わずに集約すると、最も強い主張をする分類が黙って通る。関連: [ACE-73-2](#ace-73-2)（message が前提にする文脈が消える場所ではその文言を使わない）。
