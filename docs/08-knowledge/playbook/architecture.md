### ACE-28-1: 出典を強制する設計では、フォールバックの既定値が最大の欠陥になる

| Category | architecture | Origin | PR #28 |
| Date | 2026-08-17 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: 「答えが見つからないときに、それらしい既定値を返す」実装は、**出典が本物であるほど危険**になる。出典なしの推測は読み手が疑えるが、実在するデータセットID・提供元・URL が添えられた誤答は「検証済みの答え」に見える。出典強制は、根拠のない回答を防ぐ仕組みであると同時に、**誤答の説得力を上げてしまう装置**でもある。

**Context**: `aggregate_dataset` のスタブで、集計意図のエリアに一致する固定データが無いとき `?? samples.at(0)` で先頭行へ落としていた。10件中6件が片方のエリアの固定データしか持っていなかったため、「浅草で銭湯」の検索結果をそのまま集計に渡すという**設計どおりの経路**で、上野の燕湯が `status: "answered"` ＋ 台東区銭湯データへの出典つきで返った。フロントエンドは `name` を `Stop.place` にマッピングするので、浅草の行程表に上野の銭湯が並ぶ。レビュー9本のうち4本が独立にこれを最重要指摘として挙げた（うち1本は別モデル）。

**Action**: 検索・抽出・推薦のように「該当が無い」があり得る処理では、フォールバックを書く前に**それが誤答になり得るかを問う**。誤答になり得るなら、既定値ではなく「答えられない」を返す。

- `?? 先頭要素` / `|| デフォルト` は、**問いの条件を捨てている**箇所を探す目印になる
- 「答えられない」を返せるように、応答の型に未回答の枝を最初から持たせる（HTTP エラーではなく正常な応答として）
- 「そのエリアを収録していない」と「収録しているがスタブに固定データが無い」は別の理由分類にする。前者はデータの欠損、後者は実装の欠落で、混ぜると欠損の集計が汚れる
- 不変条件は型で表す。空配列を許さない型（`[T, ...T[]]`）にすると、「候補ゼロの回答あり」がコンパイルの時点で作れなくなる

### ACE-39-1: 「他が当たらなかったときだけ発火する判定」を「当たっても報告する」に変えると、誤検知の性質が変わる

| Category | architecture | Origin | PR #39 / Issue #29 |
| Date | 2026-08-17 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

既存の未回答判定を「他の候補が1件も当たらなかったとき」から「当たっていても部分欠損として併記する」へ広げると、それまで**後段のフォールバックに隠されていた誤検知が表に出る**。実際、質問文中の対象エリア外の地名を欠損として報告したところ、「新宿のホテルから上野の美術館へ」の新宿（出発地）まで欠損になった。判定を広げるときは、その語が**求めている対象を指すのか、文脈として書かれただけか**を見分けられるかで採否を決める。見分けられないものは報告しない（推測で埋めるより黙って落とすほうが、応答の信頼度を保てる場面がある）。

### ACE-44-1: 「本番から落ちる」前提を持つモジュールは、置き場所そのものが契約になっている

| Category | architecture | Origin | PR #44 / Issue #31 |
| Date | 2026-08-17 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

開発専用機能（`import.meta.env.DEV` で囲った画面など）が本番バンドルから tree-shaking で落ちる前提は、**そのディレクトリを本番経路から import した瞬間に、型検査もテストも通ったまま崩れる**。共通化したいロジックが開発専用ディレクトリにある場合は、import せず中立な場所へ移してから使う。移設後はビルド成果物を実際に grep して、開発専用の文字列が入っていないことを確かめる（前提が生きていることは、ビルド出力を見るまで確認できない）。

### ACE-51-1: ガードは「見ているフィールド」と「置かれた分岐」の両方で到達性を確かめる

| Category | architecture | Origin | PR #51 / Issue #50 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 正しい原則を書いたガードでも、**製品経路が渡さないフィールドを見ていれば存在しないのと同じ**。同じことが分岐にも起きる。ガードを1つの分岐だけに置くと、同じ出力へ到達する他の分岐がそのまま素通りする。ガードの有無ではなく「実際の呼び出し元から、その値が入り、その分岐を通るか」で評価する。

**Context**: `search_datasets` の末尾に `if (input.category?.trim())` のガードがあり、「落とすとトイレや宿泊施設を返すことになる（指定を黙って捨てない）」とコメントまで付いていた。しかし `buildQuery` は興味も要望もすべて `query` に畳み込むため `category` を送らず、送るのはデバッグ用の API コンソールだけ。**唯一の製品経路からこの柵は届いていなかった**。結果、防ぐつもりだった挙動（「ナイトライフ」の問いに渋谷区の都市公園、「ショッピング」の問いに台東区のトイレ情報を、本物の CC BY 出典つきで返す）がそのまま起きていた。徴候はコメント自体にあった — 例示の「『神社』の問いにトイレ」は再現しない（`神社` は名所・史跡の keywords にある）。**到達しない柵の例は検証されないので、腐ったまま残る**。

さらに修正側でも同じ失敗をした。欠損を添える判定を「キーワードが1件も当たらなかった」分岐にだけ置いたため、1語でも当たると無効化された。`"ナイトライフ、上野で夜遊びしたい"` は銭湯のキーワード「夜」が「夜遊び」に部分一致してキーワード経路で `answered` になり、gaps も記録も残らない。興味チップを複数選ぶほど何かが当たるので、**実際に旅程が組み上がるケースほど発火しない**（既定値が既に2つ選択済み）。レビューで「ガードが評価される場所はどこか」と問われて初めて判明した。

**Action**: ガードを書く / レビューするときは次の2つを実測で確かめる。

- **フィールドの到達性**: 実際の呼び出し元を辿り、そのフィールドが populate されるか。されないなら、そのガードは仕様ではなく願望
- **分岐の到達性**: 同じ出力へ至る他の分岐を数え上げ、それぞれで発火するか。1箇所だけに置いた判定は、他の分岐の存在が仕様になる

修正の有効範囲は「直した」と書く前に境界ケースを流して確認し、狭ければ PR 本文と文書に明記して残りを別 Issue にする（→ [ACE-28-1](#ace-28-1) の「フォールバックが誤答になり得るか」と対で使う）。

### ACE-51-3: 欠損・未回答の message には、実測で確かめたことだけを書く

| Category | architecture | Origin | PR #51 / Issue #50 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 「出典なしの回答を作らない」は**回答本文だけの規則ではない**。欠損・未回答の `message` も画面に出る主張なので、同じ検証水準がかかる。実装が確かめていない範囲まで書くと、欠損を可視化するための文が新しい未検証の主張になる。

**Context**: エリア・フォールバックに添える欠損の文言を「質問文の内容に対応するデータセットが**利用中の10件にない**ため…」と書いた。実装が知っているのは「キーワード表に当たらなかった」だけで、10件が問いをカバーするかは判定していない。実際 `"ナイトライフ、上野"` に対して銭湯（営業 15:00〜0:00・キーワードに「夜」）は10件の中に実在する。しかも**同じ10件から候補を返しながら「対応するものが無い」と言う**ので、読み手から見て自己矛盾でもあった。レビューで指摘されて「質問文の語に当たるデータセットが無かったため」に直した。副産物として、残余が助詞だけの過検知（`"上野に行きたい"` など）でも文が嘘にならなくなった。

**Action**: 未回答・欠損の文言は「実際に行ったこと」の記述に留める。同じリポジトリの `describeQuery`（SQL を実行していないスタブで、SQL 風の文字列ではなく「どのスナップショットの何行目を固定で返したか」を書く）が先例。判定の根拠より広い範囲を断定していないか、文ごとに「これはコードが確かめたか」を問う。
