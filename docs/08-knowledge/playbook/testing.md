### ACE-23-2: ステータスコードを根拠にする前に、対照群でそのコードの意味を確かめる

| Category | testing | Origin | PR #23 |
| Date | 2026-08-16 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

確定した10件のカタログURLが実在するかを `curl` で検証したところ、**全件 403** が返った。URL が壊れているように見えるが、実際は WAF がブラウザ以外のアクセスを遮断していただけだった。User-Agent を偽装すると 202 になるが、**存在しない ID でも同じ 202** が返るため、どちらのコードも実在判定に使えない。対照群（存在しないIDを1件混ぜる）を取らずに最初の 403 を報告していれば「URL が全部死んでいる」という誤報になり、逆に UA 偽装後の 202 を成功と読めば「全件実在」という誤検証になっていた。ブラウザで開くと実在ページは表示され、存在しない ID は 404 ページになり、初めて判定できた。**外形監視・URL 実在確認・疎通確認では、成功と失敗の両方の入力を通してコードが実際に区別されることを確かめてから、そのコードを根拠に使う。** 判定に使えない環境だと分かった場合は、その事実と代替の確認方法を文書に残す（[DATABASE.md](../../02-design/DATABASE.md) §3 に記録済み）。

### ACE-28-2: 自分で書いたテストは「発火しない条件」を無意識に選ぶ — 直したら戻して落ちることを確かめる

| Category | testing | Origin | PR #28 |
| Date | 2026-08-17 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: 実装者が自分でテストを書くと、**通る条件を無意識に選んでしまう**。テストの名前と、そのテストが実際に守っている性質はしばしば一致しない。緑であることは、そのテストが何かを検証している証拠にならない。

**Context**: コア3操作のスタブで2件やらかした。(1)「候補件数の既定は4件で、limit で狭められる」というテストは、キーワードが2件しか当たらないクエリを使っていたため、`slice(0, limit)` を**丸ごと削除しても緑**だった（既定値もキャップも実質ノーガード）。(2)「集計意図のエリアで返す行が変わる」テストは、10件中**フォールバックが構造的に発火し得ない**データセット（上野・浅草の両方の固定データを持つ名所・史跡）を選んでいた。実際には6件が片方のエリアしか持たず、そこでは「浅草の銭湯」に上野の銭湯が返る欠陥が生きていた。どちらも別のレビュアーに指摘されるまで気づかなかった。

**Action**: バグを直したら、**直した箇所を一時的に元へ戻し、テストが落ちることを確認してから戻す**。落ちなければ、そのテストはその修正を守っていない。

```bash
cp src/target.ts /tmp/target.bak
# バグを再注入（フォールバックを戻す、クランプを外す、値を偽物にする 等）
npm test        # ここで落ちなければテストが無意味
cp /tmp/target.bak src/target.ts
```

固定データの検証にも同じ手が効く（実在する施設名を捏造値に差し替えて落ちることを見る）。「テストを足した」ではなく「テストが効いた」までを確認する。ACE-25-2 の「設定が効いた」まで確認する話と同じ構造で、対象がテストになったもの。

### ACE-39-2: `git stash` を使った「戻して落ちるか」検証は HEAD 基準 — ベース基準で見たいなら checkout する

| Category | testing | Origin | PR #39 / Issue #29 |
| Date | 2026-08-17 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

ACE-28-2 の「実装を戻してテストが落ちるか確かめる」を `git stash push <files>` で行うと、戻る先は**ベースブランチではなく直前のコミット**になる。作業途中でコミットを重ねていると、検証しているつもりの機能ではなく「最後のコミットで直した分」だけを見ることになり、落ちる件数が想定と噛み合わない（実際に 5 件落ちるはずが 1 件になった）。ベースブランチ基準で見たいときは `git checkout <base> -- <files>` で戻し、作業ツリーは別途退避しておく。落ちた件数が想定と違ったら、まず基準を疑う。

### ACE-40-1: 書き込みの副作用は「読み戻すテスト」と「無効化して落ちるか」の二段で確かめる

| Category | testing | Origin | PR #40 / Issue #27 |
| Date | 2026-08-17 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

ログ・監査記録のように「失敗しても応答を落とさない」書き込みは、黙って無効になってもすべてのテストが緑のまま通る。書き込み先を読み戻すテストを書いたうえで、**記録器を no-op にしたときと、テーブルを用意し忘れたときの両方で実際に落ちること**を確かめる。特に後者は罠で、`@cloudflare/vitest-pool-workers` の D1 はテストファイルごとに空で立ち上がるため、migrations の適用を忘れると「テストは緑のまま記録だけ失われる」状態になる。

### ACE-51-4: 公開 API 経由で内部関数の境界を測るテストは、入力がその関数に到達しているか確かめる

| Category | testing | Origin | PR #51 / Issue #50 |
| Date | 2026-08-18 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: 内部関数の境界（定数の網羅・閾値など）を公開 API 越しにテストするとき、**入力が手前の分岐で return されていれば、その関数は一度も呼ばれない**。テストは緑のまま、境界は何も固定されない。判定の順序がある関数では、意図した分岐へ届く入力を選べているかがテストの前提になる。

**Context**: 区切り記号の定数に長音符を入れない境界を固定するつもりで、`searchDatasets({ query: "ラーメン、上野" })` のテストを書いた。しかしこの入力はジャンル判定（`genre && usable.length === 0`）で先に `unanswered` を返すため、境界を持つ `hasContentBeyondArea` は**一度も呼ばれない**。定数の中身を変えてもテストは緑だった。ついでにコメントの根拠も誤っていた — この定数の使い道は1箇所だけで、除去後の文字列は空かどうかしか見ないため、長音符を入れても語の照合には影響しない。**他人の PR で「構造上失敗しえないテスト」を指摘した直後に、自分が同じものを書いていた。**

**Action**: 内部関数の境界を公開 API 経由で測るテストでは、次のどちらかを取る。

- その関数の観測可能な効果（この場合は `gaps` の有無）をアサートし、到達していることを同時に固定する
- 関数を直接テストする（境界だけを見たいなら公開 API を経由しない）

書いたあと **境界の値を変えてテストが落ちるか**を確認する（→ [ACE-28-2](#ace-28-2)「戻して落ちることを確かめる」の適用先を、修正差分だけでなく定数・閾値にも広げる）。

### ACE-62-3: 文言契約のテストは完全一致で固定し、到達性は副作用で確かめる

| Category | testing | Origin | PR #62 / Issue #59 |
| Date | 2026-08-18 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: 旧文言の否定アサート（`not.toContain("対応するものがありません")`）は、**他分岐に旧文言が残っている間だけ**判別力を持つ。文言そのものは `toBe` の完全一致で固定し（言い換えによる断定の再混入も検出できる）、「対象分岐に到達した」ことは message ではなく**観測可能な副作用**（gaps recorder の記録行）で固定する。

**Context**: エリア未指定側のテストは否定アサートで「分類ガードに到達した」を示したつもりだったが、それが機能していたのは末尾フォールバックに旧文言が**たまたま残っていたから**。姉妹分岐を直した瞬間に判別力が消える構造だった（PR #62 レビュー Suggestion）。[ACE-51-4](#ace-51-4) の失敗モード（入力が対象関数に到達していないテスト）が「いま起きるか、後で起きるか」の違いでしかなかった。

**Action**: (1) 契約として固定したい文言は `toBe` 完全一致で書く (2) 分岐への到達は文言ではなく副作用（記録行の `question`/`area`/`category`/`reason`）でアサートする (3) 否定アサートを書くときは「いま何がこれを真にしているか」を確かめ、直す予定のない他分岐の現状に依存していたら書き直す。

### ACE-49-5: 「〜を描画しない」型の否定アサーションは、本番データの実物を確認してから書く

| Category | testing | Origin | PR #49 / Issue #54 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: UI の否定アサーションは、テストフィクスチャが実データより単純だと**通ってしまう**。通っている事実は「実装がその性質を持つ」ことを何も保証しない。しかも落ちたときのメッセージが仕様に見えるため、次の人が**データ側を削る**方向へ倒れる危険がある。

**Context**: `DataGapCard.test.tsx` の `expect(screen.queryByText(/\d+件/)).not.toBeInTheDocument()`。意図はデザインカンプの「312人がリクエストしています」を描画しないことだったが、実際の gap message は件数を含む（`cuisineGenreUnanswered` の「210件・バリアフリー対応店に限定」、`shibuyaSightseeingUnanswered` の「渋谷区のカタログ掲載データは17件」）。バックエンドは未回答と部分欠損に**同じ文言**を返す設計（Issue #29）なので、件数を含む message は必ず画面に出る。テストが通っていたのはフィクスチャの message が短縮文だったためで、フィクスチャを実物に近づけた瞬間に赤くなる。件数はデータ不足の根拠そのものなので、削られると困る側だった。

**Action**: 否定アサーションを書く前に、その正規表現が**実データの実物**に当たらないかを確かめる（文言の生成元テンプレートを grep する）。意図を覆う具体的なアサーション（ロール・固有の文言）が既にあるなら、広い正規表現は足さない。「フィクスチャを実データに近づけると落ちるテスト」は、テストではなく仕様の誤記。

### ACE-82-4: コメントに書いた実測事実は、テストで固定しないと次の変更で静かに嘘になる

| フィールド | 値           |
| ---------- | ------------ |
| Category   | testing |
| Origin     | PR #82 / Issue #84 |
| Date       | 2026-08-19 |
| Helpful    | 2            |
| Harmful    | 0            |
| Status     | active       |

**Insight**: 定数の選定根拠を「なぜこの値か」まで丁寧にコメントへ書くと、その瞬間は最良の文書になる。しかしコメントが根拠にしているのが**実測した現在のデータの性質**（「今のカタログでは6件が同点1位になる」）である場合、データが1件増えただけで前提が崩れる。コードは動き続け、テストも通り、コメントだけが嘘になる — しかもその嘘は「この値で十分」という**安全側に見える主張**なので、誰も疑わない。

**Context**: `RECOMMENDATION_LIMIT = 6` のコメントに、同点1位となる6件のデータセット名と各々の一致キーワードまで実測どおり書かれていた（質の高いコメント）。しかし「6件同点」を固定するテストは無く、カタログに11件目を足した時点で、コメントは正しいまま値が不足する状態へ静かに移行する。検知手段はコメントを読み直すことだけ。

**Action**: コメントに「今のデータではこうなる」型の**観測**を書いたら、同じ観測をアサーションにしてテストへ置く（件数・順序・特定 ID の含有）。テストが落ちたとき、コメントも一緒に直す場所が分かるよう、テスト名か近傍コメントから定数を参照する。逆に、テストにできない観測（本番データでの目視など）は、コメントに**観測日と観測方法**を明記して、鮮度を読み手が判断できるようにする。

### ACE-86-3: テストの有効性は「修正前に落ちるか」ではなく「守りたい変異で落ちるか」で測る

| フィールド | 値      |
| ---------- | ------- |
| Category   | testing |
| Origin     | PR #86 / Issue #84 |
| Date       | 2026-08-19 |
| Helpful    | 2       |
| Harmful    | 0       |
| Status     | active  |

**Insight**: 回帰テストを書いたあと「修正前の実装で落ちること」を確認するのは有効な検算だが、**それだけでは測れないテストがある**。「やり過ぎ防止のガード」（新機能が余計なことをしないことを守るテスト）は修正前にも通るのが正常なので、この検算では有効性を判定できない。判定するには**守りたい変異を実際に実装へ入れて落ちるか**を見るしかない。入力の選び方次第で、正しい実装と壊れた実装が**バイト単位で同一の出力**になり、何も検証していないテストが「通っている」状態で残る。

**Context**: PR #86 で「より強い分類で報告済みの興味には枠を使わない」を守るテストを `{ query: "文化", interests: ["浅草寺のマナー"], limit: 2 }` で書いた。しかし守りたい変異（絞り込みを通さず生の `interests` を選定へ渡す）を入れても、確保される候補が元々スコア1位の「名所・史跡」なので結果が完全に一致し、テストは緑のままだった。レビューの指摘で `{ query: "美術館", interests: ["公園でのマナー"], limit: 2 }` へ差し替え（変異では都市公園が枠を取って押し出しが起きる）、実際に変異を入れて1件だけ落ちることを確認した。`gaps` はどちらの実装でも同じなので、候補リストの assert だけが判別の手段だった。

**Action**: 「◯◯しないこと」を守るテストを書いたら、**その ◯◯ をするコードを一時的に入れて実行する**（`git stash` や1行の置換で足りる。確認後に必ず戻す）。落ちなければ入力を変える — 押し出し・順序変化・件数変化のいずれかが**観測可能な差**として出るケースを選ぶ。差が観測できる assert がどれかも、コメントに書き残しておく（次に入力を変える人が判別力を壊さないため）。

### ACE-106-2: 完全一致テストは「実装と期待値の同時書き換え」を通す — 語彙は独立した不変条件で縛る

| Category | testing | Origin | PR #106 / Issue #99 |
| Date | 2026-08-20 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

文面を `toBe` で固定しても、文面を変える人が期待値も一緒に書き換えれば通る。**禁止語の一覧を別の不変条件として持つ**と、その同時書き換えを塞げる（今回は利用者向け文面に「スタブ」「POC」等が再混入する経路）。

対象はヘルパを個別列挙するのではなく実際の呼び出しから集めると、分岐を足した人が登録を忘れても効く。ただし呼び出しが全部 `answered` へ倒れると検査対象ゼロで緑になるので、**入力ごとに1件以上**を主張する（合計の下限では他の入力が埋めてしまう）。

### ACE-138-1: 新機能のテストは、その機能を無効化しても通る入力を選んでいないか変異で確かめる

「自然文だけの呼び出しでも興味の取り落としを報告できる」という新機能の中核テストを、質問文「上野の美術館と**ラーメン**を楽しみたい」で書いた。**分解結果を判定へ渡さない変異を入れても12件すべて緑のまま**だった。

分解経由でしか報告されない語（「ナイトライフ」— カタログのキーワード表に1件も当たらず、`interests` として渡らない限り欠損にならない）へ差し替えて、変異で落ちることを確認した。

[ACE-86-3](#ace-86-3) は「守りたい変異で落ちるか」を測れと言っているが、**既存機能と新機能が同じ観測結果を出す入力**では、その検算自体が成立しない。新機能のテストを書いたら「この入力は、新機能が無くても同じ結果になるのでは？」を先に疑い、**新機能だけが作れる出力**を選ぶ。差が出ない場合は、既存経路が反応しない題材を探す。

### ACE-145-2: 並列化の「順序が変わらない」テストは、マイクロタスクの解決順に頼ると偽陽性で通る

| Category | testing | Origin | PR #145 / Issue #142 |
| Date | 2026-08-22 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

直列 → 並列にする変更で最も壊れやすいのは「結果を**到着順**に積んでしまう」実装で、そこを守るテストは「応答が候補順と違う順に返っても並びが変わらない」形になる。ところが**遅延の作り方でテストの判別力が消える**。

最初に書いた版は「1件目の応答を、3件目が呼ばれたら解放する」形でプロミスを繋いだ。これは到着順に積む実装（`extracted.push` を `Promise.all` のコールバック内で行う版）でも**通ってしまった** — 1件目の継続がマイクロタスクの先頭に積まれ、3件目が `Response` を読み終えるより先に完了するため、到着順が結局候補順になる。

`await new Promise((r) => setTimeout(r, 20))` で**実時間の遅延**に変えたところ、到着順に積む実装は `絹本著色元三大師画像 → 寛永寺` を返して落ちるようになった。

順序を入れ替える意図のテストは、**壊した実装を1回作って落ちることを確かめる**（変異テスト。[ACE-138-1](#ace-138-1)）。並行処理では特に、マイクロタスクの解決順は「たまたま」であって設計ではない。

### ACE-150-3: 「検査した意味」と「実行される意味」がずれると、検査は静かに素通りする

| Category | testing | Origin | PR #150 / Issue #148 |
| Date | 2026-08-22 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

生成 SQL の検査を書く過程で、**同じ種類の思い込みで3回**すり抜けを作った。3つとも実測で覆った:

- **`actual.includes(value)` で照合した** → `LIKE '文化'` はワイルドカードが無いので SQLite では**完全一致**（`'文化%'` は前方一致）。「区民文化財」に当たらない SQL が検査を通り、0行になる
- **`NOT LIKE` を `LIKE` へ正規化した** → 否定は全行を除外しうる。実在値を使った除外条件が「当たる LIKE」として通る
- **シングルクォートだけ走査した** → SQLite は `"自然"` を**その名前の列が無ければ文字列**として扱う。`category = "自然"` がエラーにならず0行を返し、偽の未回答になる

3つ目は「識別子として解釈されてエラーになるはず」と考えていたが、**テストを書いたら実際には0行が返っていた**。[ACE-137-1](./architecture.md#ace-137-1)（検査した文字列と実行する文字列が別物なら、その差が迂回路になる）の**意味論版**である。

**検査を書いたら、検査対象の言語仕様を実測で確かめる。** 「たぶんエラーになる」「たぶん当たる」で書いた検査は、当たらない側に倒れたときに**黙って通す**。実行系（ここでは D1）を使ったテストで、通す／弾くの両側を固定すること。
