### ACE-25-1: 外部データの写像は列名ではなく「値の集合」を見てから書く

| Category | data-processing | Origin | PR #25 |
| Date | 2026-08-16 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 外部データの取り込みで壊れるのは、例外を投げない箇所である。列名とヘッダを確認しただけで写像を書くと、「該当0件」「未分類」という**正常に見える出力**で静かに失敗する。

**Context**: 東京都オープンデータ10件を D1 へ取り込む際、同一提供元（台東区）・同一カタログ内でも表記が揺れており、3つの静かな失敗を踏んだ。

| 踏んだもの | 症状 | 気づいた経緯 |
| --- | --- | --- |
| 丸印が `〇`(U+3007 漢数字ゼロ) なのに `○`(U+25CB 白丸) と比較 | 外国語メニュー130件・ハラール54件・ベジタリアン73件が全部 false。**見た目で区別できない** | レビュー指摘 → DB へ `COUNT(*) WHERE note LIKE '%外国語%'` で 0 を確認 |
| 丁目が算用数字（`浅草7丁目`）と漢数字（`浅草一丁目`）で揺れる | 町字が「浅草一丁目」になり宿泊施設883件が丸ごと未分類 | 集計結果が「全件対象外」で不自然だったため |
| 停留所データは所在地列が**全件空** | 72件全部が未分類 | 同上 |

いずれもエラーログは出ず、型でも防げない。集計結果を眺めて「この数字はおかしい」と気づくしかなかった。

**Action**: 取り込みの写像を書く前に、**判定に使う列の値の集合を実際に出す**。

```bash
python3 -c "...; print({x['対象列'] for x in rows})"   # 値の種類・非空件数
```

取り込み後は「データセット別 × 分類別の件数」を必ず出し、**0件・全件が同じ分類に倒れている箇所を異常として扱う**。合計行数が合っていても中身が壊れていることがある。文字の同一性が疑わしい比較（丸印・ダッシュ・全角空白）は判定関数へ集約し、テストでコードポイントごと固定する。

### ACE-25-2: 新しいディレクトリは references に入れるまで `tsc -b` の検査を素通りする

| Category | data-processing | Origin | PR #25 |
| Date | 2026-08-16 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: `tsc -b` は `tsconfig.json` の `references` に登録されたプロジェクトしか見ない。新しいトップレベルディレクトリを作っても、参照を足すまでは**型検査ゼロのまま `npm run typecheck` が成功する**。

**Context**: データ取り込み用に `scripts/` を新設したところ、`tsconfig.app.json`（`include: ["src"]`）と `tsconfig.worker.json`（`include: ["worker"]`）のどちらにも含まれず、6ファイルが無検査だった。typecheck は緑のまま。既知の「`tsc --noEmit` だけだと1ファイルも検査せず静かに通る」と同じ構造で、今度は**対象ディレクトリ側**で再発した。

**Action**: トップレベルにディレクトリを追加したら `tsconfig.<name>.json` を作り、`tsconfig.json` の `references` に加える。そのうえで**わざと型エラーを1行入れて、検出されることを確認する**。

```bash
printf 'const x: number = "壊れた";\n' > <dir>/__probe.ts
npm run typecheck   # ここでエラーが出なければ、そのディレクトリは検査されていない
rm <dir>/__probe.ts
```

「設定を足した」ではなく「設定が効いた」までを確認する。緑は無検査と区別がつかない。

### ACE-28-3: 日本語の部分一致は語の境界を見ない — 語彙リストは誤爆の除外とセットで書く

| Category | data-processing | Origin | PR #28 |
| Date | 2026-08-17 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: 日本語は分かち書きしないため、`includes()` による語彙マッチには**必ず誤爆が埋め込まれる**。英語なら単語境界（`\b`）で防げる種類の誤りが、日本語では設計時に個別へ潰すしかない。厄介なのは、誤爆が「答えられる問いを握りつぶす」方向に働くこと。

**Context**: 検索の未回答分類で2件見つかった。(1) 飲食ジャンル語に素の「そば」を入れたため、「上野駅の**そば**の公園」（近く の意）が飲食の粒度不足として弾かれた。(2) 対象エリア外の地名に「銀座」を入れたため、「**銀座線**で行けるお寺」が対象エリア外になった。銀座線は浅草・上野を通る地下鉄で、まさに代表シナリオの移動手段である。さらに (3) データセットのキーワードに代表エリア名「渋谷」を入れていたため、「渋谷の美術館」が公園データに当たり、渋谷の観光データ欠損（実測で0件）が可視化されなくなっていた。

**Action**: 語彙リストを書いたら、**その語を含む別語** を出して1件ずつ潰す。潰し方は3通りある。

- 語を置き換える（「そば」→「蕎麦」「そば屋」）
- 除外語を持たせる（「銀座」は「銀座線」を含むときは判定しない）
- そもそも入れない（エリア名をキーワードにしない。エリアは別の軸で絞る）

誤爆の判定は**そのドメインの語彙**でしか作れない（東京の地名なら路線名、飲食なら「そば／近く」）。リストと同じ場所に、なぜ除外したのかをコメントで残す。

### ACE-28-4: `tsc` の include が要るのは「どこからも import されていないファイル」— import 済みなら検査される

| Category | data-processing | Origin | PR #28 |
| Date | 2026-08-17 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: [ACE-25-2](#ace-25-2) の精緻化。「新しいディレクトリは検査を素通りする」は正しいが、**理由が違うと対策も間違える**。TypeScript のプログラムに入るのは「include されたファイル」＋「そこから import で辿れるファイル」。したがって、参照済みプロジェクトから import されているファイルは **include に無くても検査される**。include が効くのは、まだどこからも import されていないファイルに対してだけ。

**Context**: `shared/` を新設し、両 tsconfig の `include` に足したうえで「include に入れないと、src から参照していても型検査の対象にならない」とコメントに書いた。レビューで「その因果は成り立たないはず」と指摘され、実測したら**指摘が正しかった**。`include` から外しても、`src` が import している `shared/core.ts` の型エラーは3プロジェクトすべてで検出される。一方、どこからも import していないファイルを置くと検出は0件になる。つまり include は必要だが、必要な理由は「参照されていてもダメだから」ではなく「まだ参照されていないファイルのため」だった。

**Action**: 設定の**効果**だけでなく**理由**を検証してからコメントに書く。片方向（設定を入れると検出される）だけでは因果を特定できない。両方向を測る。

```bash
# ① import 済みのファイルに型エラー → include を外しても検出されるか
# ② どこからも import していないファイルに型エラー → include が無いと検出されないか
```

一般論（「TypeScript はこう動くはず」）で断定しない。このリポジトリは `tsc -b` の project references 運用で、`tsc --noEmit` だけだと1ファイルも検査せず通る前例がある。

### ACE-37-1: 名称からエリアを引くとき、括弧書きは「その地物の所在地」ではない

| Category | data-processing | Origin | PR #37 / Issue #30 |
| Date | 2026-08-17 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

住所列を持たないデータで名称から地名を引くとき、名称に含まれる括弧書き（路線名・経由地・補足）は**その地物の所在地ではない**のに、部分一致では区別できずに先に当たる。実データでは `東西(上野公園経由・三崎坂往復ルート)27西浅草三丁目` の路線名側「上野公園」が勝ち、この路線の全38停留所が上野に倒れていた。名称ベースの判定を書くときは括弧書きを落としてから照合し、曖昧語の除外も**落とした後**に適用する（前に適用すると、括弧内の語だけで地物を判定不能にする）。半角・全角の両方が実データに存在するので両方を対象にする。

### ACE-64-1: 名称に構造があるなら、照合は包含ではなく構造に合わせて狭める

| Category | data-processing | Origin | PR #64 / Issue #36 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 「名称に施設名が含まれるか」の照合を `includes` で書くと、索引の側に短い名称（「上野駅」）しか無いとき、別の地物（「上野駅入谷口」）へ根拠なく一致する。対象の名称に**既知の構造**（めぐりん停留所は「路線(括弧)＋番号＋本体」）があるなら、実在の対応が現れる位置（末尾）に照合を狭める。`endsWith` は `includes` の真部分集合なので、取りこぼしは実測で確認した上で採る。

**Context**: Issue #36 の検討点「部分一致にすると誤爆する（上野駅と上野駅入谷口）」に対し、初版は「完全一致の包含」を採ったが、包含では索引の構成次第で同じ誤爆が残ることをクロスモデルレビューが指摘した。末尾一致へ狭めても実測3件（東京国立博物館・寛永寺・旧東京音楽学校奏楽堂）は全て捕捉でき、結果は不変だった。[ACE-37-1](#ace-37-1)（括弧書きは所在地ではない）と同じく、名称の構造知識を照合の制約に変換した。

**Action**: 名称どうしを突き合わせるときは、まず対象の名称フォーマットを実データで確認し、(1) 一致が現れる位置が決まっているなら `includes` でなく `endsWith`/`startsWith` へ狭める (2) 狭めた方式で既知の正解が全件捕捉できることを実測してから採用する (3) 誤爆側のネガティブテスト（短い索引名だけがある状態）を必ず書く。

### ACE-69-2: 部分一致の haystack に絞り込みキーを混ぜない — 「新宿」は「宿」に当たる

| Category | data-processing | Origin | PR #69 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 日本語の部分一致マッチでは、**内容語の照合対象（haystack）と絞り込みキー（エリア名）を混ぜてはいけない**。目的地の配列を haystack に入れたところ、「新宿」が宿泊施設のキーワード「宿」に部分一致し、ラーメンの問いに（未回答であるべき経路で）ホテル一覧が answered で返った。地名は候補の絞り込みに使う値であって、キーワード表と照合する内容ではない。

**Context**: テストが先に落ちて発覚（`{interests:["ラーメン"], areas:["上野","新宿"]}` が `insufficient_granularity` にならず answered）。既存の `area`（単数）も haystack に入っていたが、対象エリア外なら早期 return するため実害が出ていなかっただけ。`query` 内の地名が当たるのは従来挙動として維持し、`areas` だけ haystack から外した。

**Action**: 部分一致の照合を組むときは、入力の各フィールドを「内容（照合する）」と「フィルタ（照合しない）」に分類してから haystack を組み立てる。地名・ID・分類キーをテキスト照合に混ぜる場合は、既知の包含関係（新宿⊃宿・銀座線⊃銀座）の誤マッチを必ずテストで確かめる。

### ACE-69-4: 頻度が根拠になる記録は、1リクエスト内の入力重複を正規化してから積む

| Category | data-processing | Origin | PR #69 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: `gaps` テーブルは「重複排除しない（何度訊かれたかを数える）」方針だが、それは**リクエスト間**の頻度集計のための設計。配列入力（`interests` / `areas`）をそのまま欠損生成に流すと、`["文化", "文化"]` のような**1リクエスト内の重複**が2行になり、公開リクエストの根拠となる頻度が呼び出し側の送り方だけで水増しされる。認証なしの公開 API では、配列の上限（件数・要素長）も同じ理由で必要になる（1リクエストで要素数ぶんの行を積める）。

**Context**: Claude テスト分析（criticality 7）と Codex（優先度 8）が独立に指摘。core の入口で trim・空要素除去・Set による重複除去を1か所で行い（境界を通らない直接呼び出しも守る）、境界には 20 件・100 文字の上限を置いた（超過は黙って切り詰めず 400）。

**Action**: 「記録の件数」が集計・意思決定の入力になるテーブルへ書く経路では、(1) 何の頻度を数えたいのか（リクエスト間か、入力要素間か）を先に決め、(2) 数えたい単位に合わせて入力を正規化し、(3) 公開面なら上限で行数の上界を作る。
