### ACE-9-3: ローカルに入れたスキル・リファレンスの「推奨 API」も陳腐化する — 公式ドキュメントで裏取りする

| Category | tooling | Origin | PR #9 |

| Status | active |

### ACE-23-1: 外部カタログのメタデータは自己申告 — 採否は「実体を取得できるか」で決める

| Category | tooling | Origin | PR #23 |
| Date | 2026-08-16 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

東京都オープンデータカタログから利用データ10件を選定する際、CKAN API の `resources[].format` が `CSV` でも、リソースURLの実体が HTML ページのデータセットが**候補中5件**あった。さらに「観光ポイント」は名称に反して29件のみ・緯度経度が全件空欄で、地図表示にも旅程生成にも使えなかった。カタログの `format` とタイトルは登録者の自己申告であり、機械可読性も内容の充足も保証しない。API が `success: true` を返すことは「登録されている」証明にすぎず、「使える」証明ではない。**外部データソースの採否は、リソースURLを実際に取得し、先頭バイトで実体形式を判定し、必要な列（座標等）の充足率を数えてから決める**。名称と `format` だけで一覧表を埋めると、取り込み工程に入って初めて半数が使えないと判明する。関連: [ACE-9-1](./process.md#ace-9-1)（記述は実物を開くまで信じない）

### ACE-28-5: 同期のスタブを Hono に載せるときは、戻り値の型と `await` で「後から async にする」に備える

| Category | tooling | Origin | PR #28 |
| Date | 2026-08-17 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: `c.json(value)` は `JSON.stringify` を通すだけなので、`value` が Promise だと **`{}` がシリアライズされる**。例外もログも出ず、HTTP 200 で空オブジェクトが返る。同期のスタブを後から async 化する予定があるなら、ハンドラの戻り値を `unknown` で受けてはいけない。型が Promise を弾かず、差し替えた瞬間に全エンドポイントが静かに壊れる。

**Context**: コア3操作のスタブを固定データ（同期）で書き、共通アダプタを `run: (input: T) => unknown` として `c.json(run(input))` としていた。コアは Step 5 で D1（当然 async）に差し替える予定で、その旨をコード内のコメントにも書いていた。**引き金を自分で予告しながら、型では塞いでいなかった**。

**Action**: 差し替え予定のある関数は、戻り値を型引数で受けて `await` する。1語と1つの型引数で塞げる。

```ts
const jsonRoute =
  <T, R>(parse: (body: unknown) => ParseResult<T>, run: (input: T) => R | Promise<R>) =>
  async (c: Context) => {
    // ...
    return c.json(await run(parsed.value));
  };
```

`await` は同期値に対しても安全なので、スタブの段階から入れておく。「後で async にするときに直す」は、直す前に本番へ出る。

### ACE-34-1: デバッグ用の画面は「検証しないこと」が仕様 — 通常のフォームの作法を持ち込まない

| Category | tooling | Origin | PR #34 |
| Date | 2026-08-17 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: API を確かめるための道具は、通常の UI と価値の向きが逆になる。入力を検証・補正すると 400 の経路が試せなくなり、応答の形を検証して弾くと「サーバーが仕様外の応答を返している」というまさに見たい事象が画面から消える。**道具の仕事は正しさの強制ではなく、ありのままの観測**。

**Context**: スタブのコア3操作を試す開発用コンソール（`src/features/console/`）で採った方針。範囲外の `limit: 0` や空の `datasetIds` をそのまま送れることをテストで固定し（「不正入力が補正されずに送信される」ことを送信ボディのレベルで検証）、応答は `unknown` のまま生 JSON で表示する。一方で**失敗の分類だけは厳密にする**: 送信前（シリアライズ失敗）・未達（network）・受信済みで読めない（parse）を混ぜると、道具自体が原因と逆方向へデバッグを誘導する。cross-model レビューが「stringify と fetch が同じ try」を Critical として検出したのはこの境界の混入だった。

**Action**: デバッグ・観測用の画面を作るときは、次の3点を仕様として明文化する。

- 入力は検証しない（エラー経路を試せることが価値）。変換は「JSON でどう表現するか」の都合に限る
- 応答の形を検証しない（仕様外をそのまま見せる）。ただし型の参照が必要な箇所は SSOT から `Pick` で導出し、書き写さない
- 失敗の**分類だけは**厳密にする。catch の範囲は「送信前 / 未達 / 受信済み」の境界で切る（1つの try に押し込むと誤分類が埋まる）

通常フォームの作法（バリデーション・補正・型ガード）を無意識に持ち込むと、道具としての価値が静かに消える。

### ACE-97-1: vendored なツールの欠陥は直さず、開示して上流へ送る

| フィールド | 値      |
| ---------- | ------- |
| Category   | tooling |
| Origin     | PR #97  |
| Date       | 2026-08-20 |
| Helpful    | 1       |
| Harmful    | 0       |
| Status     | active  |

**Insight**: テンプレートから取り込んだ（vendored な）コードに欠陥を見つけても、**ローカルで直すのは多くの場合正しくない**。再同期で巻き戻るうえ、上流のテストが担保している範囲から外れて、こちらには検証手段が無くなる。取るべきは (1) 欠陥を実測で確定する (2) 上流へ再現手順つきで起票する (3) **その欠陥が現れる範囲を運用文書へ開示する** の3つ。直さないこと自体は問題ではなく、**直っていないと知らせないこと**が問題になる。

**Context**: `sync-playbook-frontmatter.ts` を ff-dev-toolkit 0.28.0 から取り込んだ際、Codex のクロスモデルレビューが fail-open を2件指摘した — `## Changelog` を丸ごと消すと version 検証がスキップされる／`version`・`ace_entry_count` を `metadata:` 配下へネストしてもトップレベルとして受理される。fixture を作って両方とも再現を確認した。Codex の提案（`readTopLevelField` 相当を全読み取り箇所と書き込み経路へ適用）は複数箇所に及び、1行の改変ですら「再同期で戻すな」とコメントを書いた状況で divergence を3倍にする。どちらも `/ace-curate` が起こすドリフトではなく、実際に起こすドリフト（件数の乖離）はゲートが捕まえることを実測してある。

**Action**: vendored なコードの欠陥は、**その欠陥が到達可能かを実測してから**扱いを決める。到達しないなら直さず、上流へ起票して**ゲートが検証する範囲・しない範囲を運用文書に書く**。「ゲートを入れた」とだけ書くと、読んだ人は全部検証されていると受け取る。到達するなら、直すコストと再同期での巻き戻りコストを比べたうえで判断する（直すなら再適用手順を文書側に残す → [ACE-97-2](#ace-97-2)）。

### ACE-97-2: 再同期で消える場所に、再同期の警告を書かない

| フィールド | 値      |
| ---------- | ------- |
| Category   | tooling |
| Origin     | PR #97  |
| Date       | 2026-08-20 |
| Helpful    | 0       |
| Harmful    | 0       |
| Status     | active  |

**Insight**: vendored なファイルへローカル改変を入れたとき、「再同期で戻すな」という警告を**そのファイルの中に**書いても機能しない。丸ごと上書きする再同期ではファイルごと消えるからで、警告が生き残るのは手動 3way マージのときだけ ―― **それは最も警告を必要としない経路**である（差分が目に入るため）。記録は上書きされない場所（運用文書）へ置く。

**Context**: `scripts/ace/sync-playbook-frontmatter.ts` の import 拡張子を `.js` → `.ts` へ変えた際、理由と「再同期時に再適用すること」を import 直上のコメントに書いた。Toolkit のセルフレビューが「まるごと上書きする再同期ではそのファイルごと消える」と指摘。取り込み元バージョン（0.28.0）もリポジトリ内のどこにも無く、PR 説明にしか存在しなかった。

**Action**: vendored なファイルを置くときは、運用文書側に**取り込み元バージョン・ファイルごとの改変有無・再適用手順**の表を作る。「上流とバイト一致」と書くなら `diff` で確かめてから書く（書いた時点で検証していない主張になる → [ACE-93-1](./architecture.md#ace-93-1)）。ファイル内コメントは補助として残してよいが、それを唯一の記録にしない。改変量も実測で書く — 「1行だけ」と書いた変更が、説明コメント込みで実際は7行だった。

### ACE-145-4: cross-model レビューの実行中にワークツリーを触ると、結果ごと破棄される

| Category | tooling | Origin | PR #145 / Issue #142 |
| Date | 2026-08-22 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

`multi-agent.sh --task review` をバックグラウンドで走らせている間にファイルを1つ編集したら、完了時に「The repository changed while the review was running — discarding the result.」で統合レポートが作られず、各観点の md も `Status: discarded` になった（2026-08-22 実測）。**サブエージェントは実行中にワークツリーを読むため、途中で変わると「何を見た結果なのか」が確定しない** ―― 破棄は正しい挙動で、緩めるべきものではない。

レビューを起動したら**終わるまでツリーを触らない**。待っている間にやってよいのはリモート操作（`gh pr edit` / `gh issue create`）と読み取りだけ。指摘への対応は結果が返ってから 1 fix commit にまとめ、次巡はコミット後に回す。

破棄された md の中身は読めるので情報としては使えるが、**「安定した版に対する検証済みの結果」としては扱わない**。実装を直したうえで巡を回し直すこと。
