### ACE-51-2: 「すべての経路で同じ」型の不変条件を破るときは、コードのコメントと設計文書を同時に grep する

| Category | documentation-quality | Origin | PR #51 / Issue #50 |
| Date | 2026-08-18 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: 全称命題として書かれた不変条件は、**同じ文言がコードのコメントと設計文書の両方に置かれている**ことが多い。破るときに片方だけ直すと、残った方が「守られていない不変条件を保証するコメント」になる。これは単なる腐敗ではなく、次に触る人がその前提で読むため**同じ欠陥を再生産する装置**になる。

**Context**: `searchDatasets` の doc コメントに「**`answered` を返すどの経路でも同じ `gaps` を添える**ので、『候補は出たが欠損は消えた』という壊れ方が経路ごとに再発しない」とあった。エリア・フォールバックだけ1件多く添える修正を入れたため事実でなくなり、`API.md` の該当記述は削除して Changelog にも「事実でなくなった」と書いたのに、**コードのコメントには残したまま push した**。独立した2つのレビューが揃って最重要指摘に挙げ、一方は根拠として自分が書いた Changelog を引用してきた。皮肉なことに、この不変条件が守られていなかったこと自体が、直そうとしていた Issue #50 の原因（経路ごとに欠損の添え方が違うのに揃っていると思われていた）だった。

**Action**: 不変条件を破る変更では、その文言を**コードと文書の両方に grep してから**着手し、同じコミットで両方直す。「〜はすべて / どの経路でも / 必ず」で始まる記述は破壊時に嘘になる候補なので、実装側にも同じ文が無いか探す（→ 文書内の二重記述は [ACE-19-1](#ace-19-1)、全称命題そのものの危険は [ACE-6-1](#ace-6-1)）。

- 逆向きにも効く: **文書を直せたのにコードのコメントを直せなかった**という差は、自分が SSOT を文書側だと認識している証拠でもある。実装のコメントは SSOT ではないが、読まれる回数は文書より多い

### ACE-64-3: 文書が断定した実測値は、その実測を再現するテストで固定する

| Category | documentation-quality | Origin | PR #64 / Issue #36 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 設計文書に「実測で N 件・根拠はこの行」と断定を書いたら、**同じ実測を再現するテスト**をセットで置く。文書の断定はコードやデータの変更に自動追随しないので、テストが無いと「実装は変わったが文書は昔の実測のまま」が静かに起きる（テストは 1 件も落ちないのに文書だけが嘘になる）。

**Context**: DATABASE.md §2 に「継承できたのは 3 件」と根拠行つきの表を書いた。同点時の根拠選択が `DATASETS` の並び順に依存していたため、配列の順序を入れ替えるだけで表の「名所・史跡 35行目」が黙って別の行に変わる構造だった（レビュー Warning）。data/ の CSV を読んで継承結果 3 件と根拠行を完全一致で固定する実データテストを scripts/ 側（Node で動く vitest プロジェクト）へ追加した。固定データの出典を機械照合する catalog-samples.test.ts と同じ役割分担。

**Action**: 文書に実測値（件数・行番号・ID）を断定形で書いたら、(1) その値を導出する手順をテストとして書けるか確認する (2) 書けるなら完全一致で固定し、テスト側のコメントに対応する文書箇所を記す (3) 書けない（外部 API 依存など）なら文書側に測定日と再測定手順を残す。

### ACE-66-2: 調査済みの断定は、調査の範囲・粒度に文言を一致させる

| Category | documentation-quality | Origin | PR #66 / Issue #43 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 「調査済みだから断定してよい」は、**調査した範囲でしか**成り立たない。調査記録が「解説は 0 件（§2.1）」「ルールを場所として公開したデータは実在するがリンク切れ（§2.2）」と2種類に分けているのに、応答文言を「マナー・作法に相当するデータは存在しない」と書くと、§2.2 の問い（「ごみ分別のマナー」）に対して事実に反する。断定の主語を調査の粒度（「解説に相当するデータ」）まで絞る。

**Context**: Issue #43 のエスカレーション実装で、`data_not_published`（最も強い分類・確かめた場合のみ使える）の文言が調査範囲より広いことをクロスモデルレビューが検出（確信度82）。「マナー」語はルール系データへの問いにも現れるため、発火条件が調査の 2 分類をまたいでいた。文言を「解説に相当するデータ」へ限定し、§2.2 を対象外とした判断を実装の doc に残した。

**Action**: 調査結果を根拠に断定を書くときは、(1) 調査記録の分類（何と何を分けて記録したか）を読み直す (2) 断定の主語・範囲を、調査で「無い」と言えた粒度に一致させる (3) 対象外にした隣接分類と、なぜ絞ったかを実装側の doc に残す（次に語彙や文言を広げる人が調査記録に当たれるように）。

### ACE-49-4: 文書の版番号はマージでは解決されない — 長命ブランチでは採番そのものが衝突する

| Category | documentation-quality | Origin | PR #49 |
| Date | 2026-08-18 |

| Status | active |

**Insight**: frontmatter に `version` と Changelog を持つ文書は、長命ブランチと統合ブランチが同じ日に別々の変更を入れると、**同じ版番号が2つの異なる内容を指す**状態になる。git はテキスト衝突として報告してくれるが、「どちらを繰り上げるか」は機械には決められない。コードのコンフリクトと違い、解決には文書の owner の判断が要る。

### ACE-79-1: 非網羅の語彙表による否定判定を「無い」と書かない — 書けるのは「見つからなかった」まで

| フィールド | 値           |
| ---------- | ------------ |
| Category   | documentation-quality |
| Origin     | PR #79 |
| Date       | 2026-08-18 |
| Helpful    | 0            |
| Harmful    | 0            |
| Status     | active       |

**Insight**: 語彙表（代表エリア・対象外エリアのリスト）への照合で偽になった分岐は、「入力にエリアが書かれていない」ことを保証しない — 保証するのは「**既知の語彙に当たらなかった**」ことだけ。語彙表自身が「網羅ではなく」と注記しているのに、分岐の文言が「エリア無指定」と断定すると、未知の地名（巣鴨など）が書かれた入力に対して嘘になる。これは絶対ルール #1 の逆方向の違反（「無い」ことを確認していないのに無いと断定）で、#50 系の「検証していないものを検証済みに見せる」と同じ族。

**Context**: PR #79 で `aggregate_dataset` の query に選定根拠を載せる際、当初「エリア無指定のため先頭行」と書いた。レビュー（code-reviewer W2）が `NON_TARGET_AREAS` の「網羅ではなく」注記と突き合わせて過剰断定を指摘。「既知のエリア名が intent から見つからず」へ修正した。あわせて W1: 「先頭行」は直前の「ヘッダを除く 3 行目」と矛盾して読める（実態は固定サンプル配列の先頭で CSV の行順ではない）ため「固定サンプルの先頭」へ。

**Action**: 判定結果を文言化するときは、判定が実際に照合した集合を主語にする（「◯◯が無い」ではなく「◯◯（既知の語彙）に当たらなかった」）。特に語彙表・キーワード表・固定リストによる判定は、そのリストが網羅かどうかを確認し、非網羅なら不在の断定を書かない。位置や順序を指す語（先頭・N行目）は、隣接する事実記述と同じ座標系か確認する。

### ACE-82-3: 棄却した代替案に「より悪い」と序列を付けない — 実測が支えるのは「同じだった」まで

| フィールド | 値           |
| ---------- | ------------ |
| Category   | documentation-quality |
| Origin     | PR #82 |
| Date       | 2026-08-19 |
| Helpful    | 1            |
| Harmful    | 0            |
| Status     | active       |

**Insight**: 「なぜ A ではなく B にしたか」を書くとき、棄却した案に**序列を付けた比較**（「A のほうが悪い」）を添えたくなる。しかし実測が支えているのは多くの場合「どちらも同じ結果だった」までで、序列は書き手の印象で足された分になる。ACE-79-1（非網羅の語彙表で「無い」と断定しない）と同じ族の過剰断定で、**否定ではなく比較の形で入り込む**ぶん気づきにくい。次に読む人はこの序列を実測済みの事実として扱い、「A は検討済みで劣後」という誤った前提が定着する。

**Context**: PR #82 のチップ差し替え（`nightlife` → `nature`）で、定数コメントと CLAUDE.md / AGENTS.md の3箇所に「差し替え候補として `shopping` も検討したが、こちらも候補ゼロ（nightlife より悪い）」と書かれていた。レビューで両方を実際に `search_datasets` へ投げたところ、`ナイトライフ` と `ショッピング` は**同じ `unanswered`/`other` を返し、message も一字一句同じ**だった。「より悪い」は成り立たない。「どちらも候補ゼロで改善にならないため採用していない」へ直した。

**Action**: 選定理由に比較を書くときは、その比較を支える**観測が2件そろっているか**を確認する（A の実測・B の実測）。片方しか測っていない、または結果が同じなら、序列ではなく「同じだった」「差が無かった」と書く。CLAUDE.md / AGENTS.md のような規範文書では特に厳格に — 規範文書の断定は、次の実装者が検証せずに前提として使う。

### ACE-86-4: ハード上限が残っている限り「構造的に起きない」とは書けない

| フィールド | 値                  |
| ---------- | ------------------- |
| Category   | documentation-quality |
| Origin     | PR #86 / Issue #84 |
| Date       | 2026-08-19 |
| Helpful    | 0                   |
| Harmful    | 0                   |
| Status     | active              |

**Insight**: 「構造的に起きない」「もう起きない」は**不可能性の主張**で、反例が1つでもあれば偽になる。修正が症状の**原因**（基準のズレ・判定の誤り）を消しても、症状の**成立条件**に別のハード制約（件数上限・枠数・タイムアウト）が残っていれば、その制約側から同じ症状が再現する。「原因を直した」と「症状が起きなくなった」は別の主張で、後者を書くには制約側も潰した確認が要る。ACE-82-3（棄却した代替案への序列）と同じ形の過剰断定が、**修正の効能**を語る文でも起きる。

**Context**: PR #86 で「選定と欠損判定の述語を揃えたので『枠に入らなかっただけなのに欠損に見える』が構造的に起きない」と4箇所（コード doc / API.md / CLAUDE.md / AGENTS.md）へ書いた。しかし枠の確保には `if (reserved.size >= limit) break;` があり、**報告対象の興味が `limit` を超えると溢れた分は枠を取れない**。`interests` は最大20件・`limit` は上限10 なので仕様上ふつうに起きる入力だった。セルフレビューの2エージェント（code-reviewer / comment-analyzer）が独立に同じ4箇所を指摘した。

**Action**: 「起きない」と書く前に、**症状の成立条件を列挙して、そのそれぞれを潰したか**を確認する。潰していない条件が残るなら「◯◯の範囲では起きない」と射程を明示し、残る条件を箇条書きで並べてテストで固定する。とくに指示書（CLAUDE.md / AGENTS.md）に書く効能は、次に読むエージェントが「その境界は存在しない」として扱い、テストも書かず報告も退けるため、射程の欠落が最も高くつく。

### ACE-137-4: 依存ライブラリの「これは◯◯を受け付けない」は、API 名や用途から推し量らず叩いて確かめる

| Category | documentation-quality | Origin | PR #137 / Issue #118 |
| Date | 2026-08-22 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

生成 SQL の封じ込めを「3層」と設計し、2層目を「`db.prepare()` は1文しか受けないので、静的検証をすり抜けた複文もここで止まる」と書いた。実測すると**止まらなかった**:

- `SELECT 1; DELETE FROM gaps` → **2文目が実行され、行が消えた**
- `DELETE FROM gaps` → 実行された
- `PRAGMA table_list` / `SELECT ... FROM sqlite_master` → スキーマ・内部テーブル名が読めた
- `SELECT ...; DROP TABLE gaps` → 拒否（DDL だけは止まる）

`prepare` という名前と「プリペアドステートメント」という一般知識から「1文だけ」を推し量ったのが誤りだった。**層を1枚数えたつもりで0枚だった**ことになり、放置すれば次に触る人が「後段でも見ているから」と静的検証を緩める。

依存の挙動を防御の根拠にするなら、**その依存を実際に叩いた結果をテストとして残す**。今回は「読み取り専用ではない」ことを4件のテストとして固定した — **守れていないことを固定するテスト**なので、将来ライブラリ側が本当に拒否するようになったら落ちて教えてくれる。[ACE-113-1](#ace-113-1) が自分のコードの境界について言っていることを、依存側へ広げたもの。
