### ACE-2-1: テンプレート文書で危険なのは空のプレースホルダーではなく、確定事項と矛盾する「もっともらしい汎用記述」

| Category | documentation-quality | Origin | PR #2 |
| Date | 2026-08-15 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

`[プロジェクト名]` のような空プレースホルダーは grep で機械的に検出できるが、「本プロジェクトでは REST API と GraphQL を使用」のように文として完成した汎用記述は目視で滑り、確定事項（本プロジェクトは MCP・DB なし・認証なし）と正面から矛盾したまま残る。テンプレートから文書を起こしたときは必ず発生すると考えてよい。検出は grep ではなく、確定事項リスト（採用技術・不採用技術）を渡した別モデルへのレビュー依頼が最も安価。

### ACE-2-2: 「未適用テンプレート」の警告は索引ではなく各ファイル本体に置く — 索引を通らない到達経路があるため

| Category | documentation-quality | Origin | PR #2 |
| Date | 2026-08-15 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

未具体化のテンプレート文書に注記を付けるとき、中央索引（MASTER.md）に1行足すだけでは、grep や直リンクでその文書に直接到達した読み手（AI 含む）を素通りさせる。索引経由と直接到達の 2 経路があるかぎり、警告は入口ではなく本体側に置かなければ機能しない。両方に置くのが最小コストで、索引側は一覧性、本体側は到達保証を担う。

### ACE-4-2: ベンダリングしたテンプレートをローカル修正したら、上流との差分を文書内に列挙する

| Category | documentation-quality | Origin | PR #4 |
| Date | 2026-08-15 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

外部テンプレートをコピーしたファイルに手を入れると、セットアップコマンドの再実行や上流再同期で修正が巻き戻るが、差分がどこかを覚えている人はいない。修正が正しい場合でも（上流の自己矛盾を直した場合など）、ファイル冒頭に「上流との差分」を箇条書きで残し、再適用が必要である旨を明記する。「verbatim コピー」と書いたまま手を入れると、その注記自体が最初の嘘になる。

### ACE-6-1: 入口ドキュメントに「すべての〜は〜を持つ」型の全称命題を書かない — 例外1件で嘘になる

| Category | documentation-quality | Origin | PR #6 |
| Date | 2026-08-15 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

README のような入口文書で運用を要約すると「未具体化の文書は冒頭にバナーを持つ」のような全称命題を書きたくなるが、実際には1つ例外があるだけで文書全体の信頼が落ち、しかも入口なので誤解が最も広く伝播する。全称命題を書くなら grep 1 本で検証できる形（文言を統一する）にするか、「どれが該当するかは SSOT の索引を参照」と参照に落とす。要約は範囲を狭めるほど寿命が延びる。

### ACE-6-2: 文書へリンクするときは、リンク先が自分で持っている留保も一緒に運ぶ

| Category | documentation-quality | Origin | PR #6 |
| Date | 2026-08-15 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

「用語を確認したい → GLOSSARY.md」のような素の案内は、その文書が冒頭で宣言している留保（「A〜Z 節は一般辞書であり採用技術ではない」）を落として渡すため、当の文書が防ごうとしている誤読を入口で招く。索引・目次・READMEからリンクを張るときは、リンク先の冒頭注記を確認し、1行の但し書きとして一緒に載せる。リンクはラベルだけでなく前提も運ぶ経路である。

### ACE-8-1: 規約を書いた PR は、その規約を最初に破る — 規約追加とセルフチェックを同じコミットに入れる

| Category | documentation-quality | Origin | PR #8 |
| Date | 2026-08-15 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

「frontmatter を変更したら version と Changelog を同時更新する」と書いた PR 自身が、同じ PR で触った4文書でそれを破っていた（PR #4 でも同型を検出済みで2回目）。規約を書く作業と規約に従う作業は同一セッション内で認知的に分離してしまうため、意志では防げない。規約を追加・変更したら、その場で規約に照らして自分の差分を機械的に検査する（`git diff --name-only` × frontmatter 差分の突き合わせ）ことを同じコミットの完了条件にする。

### ACE-19-1: 同じ規定を文書内の2箇所に書くと、片方だけ読んだ読み手が「明記なし」と誤認する — 一元化するか「§Xと同一」と参照で書く

| Category | documentation-quality | Origin | PR #19 |
| Date | 2026-08-16 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

API.md で `get_provenance` の必須項目がツール別節（§3.3）と共通仕様（§4）の2箇所に書かれ、§4 にだけあるデータセットIDを §3.3 だけ読んだフロントエンドが「仕様に明記なし・要確認」と誤認し、クライアント側で ID を別途保持する余計な回避設計を提案しかけた。同じリストを2箇所に持つ文書は、差分が生じた時点で読み手がどちらを正とするか保証できない。仕様書で項目列挙が複数箇所に必要なときは、正の1箇所に寄せて他方は「§X の必須項目と同一」のように参照で書くか、両方に書くなら同一性を明記して食い違いを検出可能にする。

### ACE-21-1: ADR を承認したら、その旧前提で書かれた既存文書を grep で洗い出して同時に追随させる

| Category | documentation-quality | Origin | PR #21 |
| Date | 2026-08-16 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

ADR-008（フロントは MCP でなく `/api/*` を呼ぶ二面公開）は承認済みだったのに、旧前提「外部IFは MCP のみ」で書かれた API.md・GLOSSARY・DOMAIN・README・CLAUDE.md 等8ファイルが未追随のまま残り、チームメンバーが古い前提で API 要件を起こす実害につながった。ADR は決定を記録するだけで既存文書を書き換えてはくれないため、承認と同じ PR で旧前提の言い回し（今回なら「MCP で接続」「MCP クライアントとして」）を grep し、追随修正まで済ませる。修正しない歴史的記録（変更履歴・過去の ADR タイトル）は書き換えず区別する。
