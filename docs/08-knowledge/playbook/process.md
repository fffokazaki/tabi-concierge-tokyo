### ACE-34-2: レビューツールの規約指摘は、そのリポジトリの実績と照合してから採否を決める

| Category | process | Origin | PR #34 |
| Date | 2026-08-17 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: cross-model・汎用レビューツールは、**そのリポジトリの規約ではなく一般的な規約**を根拠に指摘してくる。信頼度が高く表示されていても、規約系の指摘（命名・配置・スタイル）は「どの規約文書に基づくか」がリポジトリ内に実在するかで採否を決める。盲目的に従うと、既存コードと逆方向の「修正」でコードベースの一貫性がむしろ壊れる。

**Context**: Codex レビューが `apiRequest.ts` を「kebab-case 規約に違反（信頼度90）」と指摘した。根拠は汎用の code-review-standards。しかしこのリポジトリの非コンポーネント TS は `mockScenarios.ts` / `usePlanState.ts` の camelCase が既存実績で、CONVENTIONS.md の命名規則もドキュメントファイルが対象。従っていれば、既存規約と食い違う1ファイルが生まれていた。逆に、同じレビューのエラー分類の指摘（try の範囲）は実挙動に基づいており妥当だったので採用した — **規約系と挙動系で検証方法が違う**。

**Action**: レビュー指摘のうち規約・スタイル系は、対応する前に (1) リポジトリの既存ファイルを `ls` して実績を見る (2) CONVENTIONS.md 等の規約文書に該当規定があるか grep する。どちらにも根拠が無ければ、既存実績を根拠に棄却し、その判断をレビュー対応コメントに残す（次のレビューで同じ指摘が来たときに再調査しないため）。挙動系の指摘は逆にコードの実挙動・実データで検証する。

### ACE-51-5: 自分が読まない設定ファイルの同期漏れは、それを読むモデルが見つける

| Category | process | Origin | PR #51 / Issue #50（PR #49 のレビュー中に判明） |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: ツールごとに指示ファイルを分けて「内容は同一」と宣言しているリポジトリでは、**自分が読まない側の同期漏れは構造的に見えない**。CLAUDE.md を読むレビュアーは CLAUDE.md しか検証せず、AGENTS.md の陳腐化は指摘の対象にならない。この盲点は注意力では埋まらないので、cross-model レビューを1本以上残すか、grep で機械的に潰す。

**Context**: `AGENTS.md` は冒頭で「内容は CLAUDE.md と同一」と宣言している。ある PR が CLAUDE.md の技術スタック表だけを更新し、AGENTS.md は旧記述のまま残った。**Claude 系のレビューエージェント4本と自分の手動レビューが全員見落とし、Codex CLI（AGENTS.md を読む側）が独立に検出した。** 実害は「同じリポジトリで作業する AI が、使うツールによって異なるプロジェクト状態を認識する」こと。cross-model レビューの価値が「別の観点」ではなく「**別の入力を読むこと**」から出た事例。

**Action**: ツール別の指示ファイル（CLAUDE.md / AGENTS.md / GEMINI.md 等）が「同一内容」を宣言しているなら、片方を編集したら必ず両方を差分で確認する。あわせて、レビュー体制から cross-model を落とさない — Claude 系だけで固めると、この種の盲点がレビュー全体の盲点になる。

- 同一内容を宣言するファイルが増えるほど手作業の同期は破れる。差分を検証する仕組み（CI での diff チェック等）に寄せる判断も検討する

### ACE-57-4: 対処案が併記された Issue では、案の魅力ではなく受け入れ条件が案を選ぶ

| Category | process | Origin | PR #57 / Issue #52 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: Issue に「対処案 (a) / (b)、判断は実装時に」と書かれていても、案が自由に選べるとは限らない。**受け入れ条件を1つずつ案に当てると、AC の1つが案そのものを排除する**ことがある。着手前に AC × 案のマトリクスを埋めると、実装してから詰むのを避けられる。

**Context**: Issue #52 は (a)「訊かれた全エリアの候補を返す」と (b)「1エリアに絞ったまま、拾わなかったエリアを欠損に載せる」を併記し、「(a) のほうが利用者の要求に近い」と書いていた。AC1 も「`gaps` に載る、**または両エリアの候補を返す**」と (a) を明示的に許している。ところが AC2 は「同じ質問で `gaps` テーブルに理由分類つきで記録される（答えなかったエリアが `area` 列から分かる）」で、(a) を採ると**両方に答えてしまうため記録すべき欠損が存在しなくなり**、AC2 が満たせない。AC1 だけ読んで (a) に進むと、`limit` の配分とスコアリングを作り直した後で気づくことになった。

**Action**: 対処案が複数ある Issue では、着手前に「AC × 案」の表を作り、各セルを「この案だとこの AC はどう満たされるか」で埋める。埋まらないセルが出たらそこが選択の根拠になる。選ばなかった案と**選ばなかった理由**は PR 本文と設計文書に残す（後から「なぜ楽な方を選んだのか」と読まれるため）。

### ACE-57-5: レビューが挙げた反例は、真偽値ではなく応答全文を出して読む

| Category | process | Origin | PR #57 / Issue #52 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: レビュー指摘の反例を確かめるとき、「指摘のとおりになっていないこと」だけを assert すると、その経路が抱える**別の欠陥**を見落とす。応答オブジェクト全体を出して目視すると、指摘とは違うものが出てくる。

**Context**: 「`category` を指定した経路でもエリアが黙って落ちるのでは」という指摘を検証するため、使い捨てのテストで `{ query: "上野・渋谷", category: "公園" }` を実際に走らせ、**わざと失敗させて diff に応答全体を出させた**。落ちてはいなかった（`unanswered` を返すので失敗は見える）が、その `message` が「利用中の10データセットに『公園』に対応するものがありません」— 都市公園・都立公園一覧は10件に**実在する**。[ACE-51-3](./architecture.md#ace-51-3)（欠損の message には実測で確かめたことだけを書く）で同じ判断をしたのに、分類ガードの分岐だけ取り残されていた。指摘そのものは空振りだったが、指摘のおかげで別の Issue（#59）が立った。

**Action**: 反例の検証は `expect(x).toBe(false)` で終わらせず、応答オブジェクトごと出力して読む。使い捨てのテストを1本書いて**意図的に失敗させ**、アサーションの diff に実値を出させるのが速い（`console.log` はテストランナーの出力設定に食われることがある）。読むときは指摘された点だけでなく、文言・分類・記録の各フィールドを一通り見る。

### ACE-62-2: 文言の嘘を直す判断をしたら、同じ言い回しを grep して姉妹分岐へ同時適用する

| Category | process | Origin | PR #62 / Issue #59 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 誤った言い回しの修正判断は、その言い回しが残っている**全分岐を grep で数え上げて同時に適用**しないと、取り残しが Issue を連鎖させる。判断の確立と適用範囲の確認は別の作業で、後者を省くと同じ修正を分岐の数だけ繰り返すことになる。

**Context**: 「利用中の10データセットに無い」の断定をやめる判断は Issue #50（PR #51）で確立したが、適用は当該分岐のみだった。分類ガード（Issue #59）が第1の取り残し、同一関数の末尾フォールバック（PR #62 のレビュー Warning）が第2の取り残し。同じ嘘が3分岐にあり、**2回に分けて後から見つかった**。`grep "対応するものがありません"` 1回で全部見つかる状態だった。

**Action**: message・文言の判断を確立した PR では、コミット前に同じ言い回し（と近い言い換え）をファイル・関数単位で grep し、該当分岐を同 PR で直すか、その場で `gh issue create` する。レビューで「姉妹分岐に同じ問題」と指摘されたら、触ったファイル内・少行数なら同じ fix commit にまとめる（CLAUDE.md のスコープ規則内）。

### ACE-73-3: 生成系コマンドの失敗フォールバックに、劣化したプレースホルダを渡さない

| Category | process | Origin | PR #73（起票は PR #69 セッション） |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: `gh issue create --json number` は失敗する（`create` は `--json` 未対応）。`||` のフォールバックへ「本文は上記と同じ内容で再試行」というプレースホルダを渡していたため、**本文が一文だけの Issue が静かに作成され**、AC 照合ゲート（/close-issue）で照合対象が無いことに初めて気づいた。フォールバックは成功時と同じ入力で再試行する形にしないと、失敗が「劣化した成功」に化けて検出が遅れる。

**Context**: Issue #70 の起票時。エラー出力は `2>/dev/null` で捨てていたため失敗にも気づかなかった。本文は PR #73 着手時に復元し、復元した旨を Issue に注記した。

**Action**: (1) `gh issue create` / `gh pr create` の作成系に `--json` を付けない（番号は出力 URL から取る）(2) `||` フォールバックには成功時と同一の本文・引数を渡す（「同上」プレースホルダ禁止）(3) 作成系コマンドの stderr を捨てない。作成直後に `gh issue view` で本文の先頭を確認すると、この型の劣化は即座に見つかる。

### ACE-74-1: 「移動のみ」リファクタは、旧版との行単位照合で機械的に証明する

| Category | process | Origin | PR #74 / Issue #71 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: ファイル分割 PR の「挙動変更なし・移動のみ」という主張は、レビュアーが目視で保証しにくい（read-only サブエージェントは git baseline に届かないことがある）。`git show develop:<file>` の**全行が分割後ファイル群のどこかに verbatim で存在するか**を数行のスクリプトで照合すると、export 付与・import 整理・新ヘッダ以外の差分ゼロを機械的に証明でき、レビューの残項目（バイト単位一致）を潰せる。

**Context**: PR #74 で Claude レビュアーが「構造は一貫しているがバイト単位は未検証」と正直に報告した。オーケストレータ側で照合スクリプトを実行し、差分が未使用 import 2行だけであることを確認してからマージした。テスト側は差分ゼロ（完全一致）。

**Action**: 移動のみを主張するリファクタでは、(1) 移動をスクリプトで実施し（手写しを避ける）(2) マージ前に旧版との行包含チェックを回して差分を列挙し (3) 許容差分（export・import・ヘッダ）を PR 本文に明記する。テストファイルの分割は describe 単位の verbatim 移動に限ると AC「テスト変更なし」がそのまま成立する。
