### ACE-34-2: レビューツールの規約指摘は、そのリポジトリの実績と照合してから採否を決める

| Category | process | Origin | PR #34 |
| Date | 2026-08-17 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: cross-model・汎用レビューツールは、**そのリポジトリの規約ではなく一般的な規約**を根拠に指摘してくる。信頼度が高く表示されていても、規約系の指摘（命名・配置・スタイル）は「どの規約文書に基づくか」がリポジトリ内に実在するかで採否を決める。盲目的に従うと、既存コードと逆方向の「修正」でコードベースの一貫性がむしろ壊れる。

**Context**: Codex レビューが `apiRequest.ts` を「kebab-case 規約に違反（信頼度90）」と指摘した。根拠は汎用の code-review-standards。しかしこのリポジトリの非コンポーネント TS は `mockScenarios.ts` / `usePlanState.ts` の camelCase が既存実績で、CONVENTIONS.md の命名規則もドキュメントファイルが対象。従っていれば、既存規約と食い違う1ファイルが生まれていた。逆に、同じレビューのエラー分類の指摘（try の範囲）は実挙動に基づいており妥当だったので採用した — **規約系と挙動系で検証方法が違う**。

**Action**: レビュー指摘のうち規約・スタイル系は、対応する前に (1) リポジトリの既存ファイルを `ls` して実績を見る (2) CONVENTIONS.md 等の規約文書に該当規定があるか grep する。どちらにも根拠が無ければ、既存実績を根拠に棄却し、その判断をレビュー対応コメントに残す（次のレビューで同じ指摘が来たときに再調査しないため）。挙動系の指摘は逆にコードの実挙動・実データで検証する。

### ACE-51-5: 自分が読まない設定ファイルの同期漏れは、それを読むモデルが見つける

| Category | process | Origin | PR #51 / Issue #50（PR #49 のレビュー中に判明） |
| Date | 2026-08-18 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

**Insight**: ツールごとに指示ファイルを分けて「内容は同一」と宣言しているリポジトリでは、**自分が読まない側の同期漏れは構造的に見えない**。CLAUDE.md を読むレビュアーは CLAUDE.md しか検証せず、AGENTS.md の陳腐化は指摘の対象にならない。この盲点は注意力では埋まらないので、cross-model レビューを1本以上残すか、grep で機械的に潰す。

**Context**: `AGENTS.md` は冒頭で「内容は CLAUDE.md と同一」と宣言している。ある PR が CLAUDE.md の技術スタック表だけを更新し、AGENTS.md は旧記述のまま残った。**Claude 系のレビューエージェント4本と自分の手動レビューが全員見落とし、Codex CLI（AGENTS.md を読む側）が独立に検出した。** 実害は「同じリポジトリで作業する AI が、使うツールによって異なるプロジェクト状態を認識する」こと。cross-model レビューの価値が「別の観点」ではなく「**別の入力を読むこと**」から出た事例。

**Action**: ツール別の指示ファイル（CLAUDE.md / AGENTS.md / GEMINI.md 等）が「同一内容」を宣言しているなら、片方を編集したら必ず両方を差分で確認する。あわせて、レビュー体制から cross-model を落とさない — Claude 系だけで固めると、この種の盲点がレビュー全体の盲点になる。

- 同一内容を宣言するファイルが増えるほど手作業の同期は破れる。差分を検証する仕組み（CI での diff チェック等）に寄せる判断も検討する

### ACE-57-4: 対処案が併記された Issue では、案の魅力ではなく受け入れ条件が案を選ぶ

| Category | process | Origin | PR #57 / Issue #52 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: Issue に「対処案 (a) / (b)、判断は実装時に」と書かれていても、案が自由に選べるとは限らない。**受け入れ条件を1つずつ案に当てると、AC の1つが案そのものを排除する**ことがある。着手前に AC × 案のマトリクスを埋めると、実装してから詰むのを避けられる。

**Context**: Issue #52 は (a)「訊かれた全エリアの候補を返す」と (b)「1エリアに絞ったまま、拾わなかったエリアを欠損に載せる」を併記し、「(a) のほうが利用者の要求に近い」と書いていた。AC1 も「`gaps` に載る、**または両エリアの候補を返す**」と (a) を明示的に許している。ところが AC2 は「同じ質問で `gaps` テーブルに理由分類つきで記録される（答えなかったエリアが `area` 列から分かる）」で、(a) を採ると**両方に答えてしまうため記録すべき欠損が存在しなくなり**、AC2 が満たせない。AC1 だけ読んで (a) に進むと、`limit` の配分とスコアリングを作り直した後で気づくことになった。

**Action**: 対処案が複数ある Issue では、着手前に「AC × 案」の表を作り、各セルを「この案だとこの AC はどう満たされるか」で埋める。埋まらないセルが出たらそこが選択の根拠になる。選ばなかった案と**選ばなかった理由**は PR 本文と設計文書に残す（後から「なぜ楽な方を選んだのか」と読まれるため）。

### ACE-57-5: レビューが挙げた反例は、真偽値ではなく応答全文を出して読む

| Category | process | Origin | PR #57 / Issue #52 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: レビュー指摘の反例を確かめるとき、「指摘のとおりになっていないこと」だけを assert すると、その経路が抱える**別の欠陥**を見落とす。応答オブジェクト全体を出して目視すると、指摘とは違うものが出てくる。

**Context**: 「`category` を指定した経路でもエリアが黙って落ちるのでは」という指摘を検証するため、使い捨てのテストで `{ query: "上野・渋谷", category: "公園" }` を実際に走らせ、**わざと失敗させて diff に応答全体を出させた**。落ちてはいなかった（`unanswered` を返すので失敗は見える）が、その `message` が「利用中の10データセットに『公園』に対応するものがありません」— 都市公園・都立公園一覧は10件に**実在する**。[ACE-51-3](./architecture.md#ace-51-3)（欠損の message には実測で確かめたことだけを書く）で同じ判断をしたのに、分類ガードの分岐だけ取り残されていた。指摘そのものは空振りだったが、指摘のおかげで別の Issue（#59）が立った。

**Action**: 反例の検証は `expect(x).toBe(false)` で終わらせず、応答オブジェクトごと出力して読む。使い捨てのテストを1本書いて**意図的に失敗させ**、アサーションの diff に実値を出させるのが速い（`console.log` はテストランナーの出力設定に食われることがある）。読むときは指摘された点だけでなく、文言・分類・記録の各フィールドを一通り見る。

### ACE-62-2: 文言の嘘を直す判断をしたら、同じ言い回しを grep して姉妹分岐へ同時適用する

| Category | process | Origin | PR #62 / Issue #59 |

**Insight**: 誤った言い回しの修正判断は、その言い回しが残っている**全分岐を grep で数え上げて同時に適用**しないと、取り残しが Issue を連鎖させる。判断の確立と適用範囲の確認は別の作業で、後者を省くと同じ修正を分岐の数だけ繰り返すことになる。

### ACE-73-3: 生成系コマンドの失敗フォールバックに、劣化したプレースホルダを渡さない

| Category | process | Origin | PR #73（起票は PR #69 セッション） |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: `gh issue create --json number` は失敗する（`create` は `--json` 未対応）。`||` のフォールバックへ「本文は上記と同じ内容で再試行」というプレースホルダを渡していたため、**本文が一文だけの Issue が静かに作成され**、AC 照合ゲート（/close-issue）で照合対象が無いことに初めて気づいた。フォールバックは成功時と同じ入力で再試行する形にしないと、失敗が「劣化した成功」に化けて検出が遅れる。

**Context**: Issue #70 の起票時。エラー出力は `2>/dev/null` で捨てていたため失敗にも気づかなかった。本文は PR #73 着手時に復元し、復元した旨を Issue に注記した。

**Action**: (1) `gh issue create` / `gh pr create` の作成系に `--json` を付けない（番号は出力 URL から取る）(2) `||` フォールバックには成功時と同一の本文・引数を渡す（「同上」プレースホルダ禁止）(3) 作成系コマンドの stderr を捨てない。作成直後に `gh issue view` で本文の先頭を確認すると、この型の劣化は即座に見つかる。

### ACE-74-1: 「移動のみ」リファクタは、旧版との行単位照合で機械的に証明する

| Category | process | Origin | PR #74 / Issue #71 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: ファイル分割 PR の「挙動変更なし・移動のみ」という主張は、レビュアーが目視で保証しにくい（read-only サブエージェントは git baseline に届かないことがある）。`git show develop:<file>` の**全行が分割後ファイル群のどこかに verbatim で存在するか**を数行のスクリプトで照合すると、export 付与・import 整理・新ヘッダ以外の差分ゼロを機械的に証明でき、レビューの残項目（バイト単位一致）を潰せる。

**Action**: 移動のみを主張するリファクタでは、(1) 移動をスクリプトで実施し（手写しを避ける）(2) マージ前に旧版との行包含チェックを回して差分を列挙し (3) 許容差分（export・import・ヘッダ）を PR 本文に明記する。テストファイルの分割は describe 単位の verbatim 移動に限ると AC「テスト変更なし」がそのまま成立する。

### ACE-49-1: 「push した」という申告は、PR の更新時刻ではなく remote の ref で確かめる

| Category | process | Origin | PR #49 |
| Date | 2026-08-18 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

**Insight**: 協働者から「修正版を push した」と連絡を受けたとき、`gh pr view` の `updated_at` は **review request でも動く**ため「更新されている＝push された」にならない。権威は `git ls-remote --heads origin <branch>` が返す OID だけ。申告を信じてレビューを始めると、前日と同じコミットを読み直すことになる。

**Context**: PR #49。「修正4件を push しました」の連絡を受けたが、remote の head は前日のままだった（timeline に commit イベントが無く `review_requested` だけ）。**PR 本文が未編集だったこと**が「push 先を間違えた」ではなく「未 push」の切り分けを決めた — 本文編集は push 不要でできる操作なので、依頼した本文追記も未対応であることが、変更一式が手元に残っている証拠になった。

**Action**: (1) `git fetch` 後に `git ls-remote --heads origin <branch>` で OID を確認する（`updated_at` を根拠にしない）(2) 期待した変更がその OID に含まれるかを `git show <sha>:<path>` で直接確かめる (3) 未 push と判定したら、相手側で走らせる確認コマンド（`git status -sb` / `git log --oneline origin/<branch>..HEAD`）を添えて返す。push 不要でできる操作（本文編集・ラベル）の有無は、原因切り分けの補助証拠になる。

### ACE-86-5: 直した経路が本番設定で1行も動かないなら、それは「修正済み」ではない

| フィールド | 値      |
| ---------- | ------- |
| Category   | process |
| Origin     | PR #86 / Issue #84 |
| Date       | 2026-08-19 |
| Helpful    | 0       |
| Harmful    | 0       |
| Status     | active  |

**Insight**: バックエンドの欠陥をフロント側の定数で回避（対症療法）したあと、本体を直す PR を出すとき、**回避のほうを戻さないと新しいコードは本番で1度も実行されない**。テストと文書だけが「直った」と主張し、実際に画面を支えているのは依然として回避のほう、という状態になる。回避は「本体が直ったら不要になる」ものなので、本体の PR で戻すか、戻さない判断を明示的に記録するかのどちらかが要る — 黙って両方残すと、次に読む人は「直っているのだからこの定数は関係ない」と誤読する。

**Context**: PR #82 で `RECOMMENDATION_LIMIT` を 4→6 に上げて同点タイの取り落ちを回避した。PR #86 でバックエンド（`selectWithInterestCoverage`）を直したが、値は 6 のまま据え置いた（Issue の受け入れ条件が「4 に戻すかはフロント側の判断」としていたため）。結果、あなたへ画面の「すべて」は候補がちょうど6件で `usable.length <= limit` の早期 return に入り、**新しい選定は本番のどの経路でも実行されない**。セルフレビュー（silent-failure 観点）が全チップ構成をトレースして指摘した。

**Action**: 対症療法を入れた PR と、本体を直す PR を**対で追跡**する（回避側にどの Issue で不要になるかを書く）。本体の PR では、回避を戻すか・戻さないなら「いま新コードは本番で発火しない」ことを**文書とテストの両方に**書く（テストで固定しないと、次の変更で静かに前提が変わる → ACE-82-4）。判断が他担当の領域なら、その場で別 Issue を起票して番号を残す。レビュー観点としては「**この修正は本番設定で実際に実行されるか**」を、テストが緑であることとは別に確認する。

### ACE-93-3: 握りつぶしを1件直すときは、同じ関数の下流と対になる画面を棚卸しする

| フィールド | 値      |
| ---------- | ------- |
| Category   | process |
| Origin     | PR #93 / Issue #89 |
| Date       | 2026-08-20 |
| Helpful    | 2            |
| Harmful    | 0       |
| Status     | active  |

**Insight**: 「未回答を黙って落とす」型の欠陥は、単独では存在しない。**同じ関数の下流の別ステップ**と、**対になる画面の同じ位置**に、ほぼ必ず同型のものが並んでいる。1件だけ直すと、直した経路と直していない経路が同じファイル内に共存し、次に読む人は「ここは直っているのだから、あちらも意図的にそうなっている」と誤読する。1件見つけた時点で、`continue` と早期 return を全部数えるのが安い。

**Context**: Issue #89（`aggregate_dataset` の `unanswered` を握りつぶす）を直す過程で、同型のものが3つ見つかった — (1) 同じ関数の下流で `get_provenance` の出典が突き合わない候補を落とす `if (!source) continue`（#92）(2) 候補が全滅したときに個々の理由が汎用 `other` へ丸められ内訳が消える（#94）(3) プラン画面 `buildPlan.ts` の同じ位置に**同じ握りつぶしと、それを正当化するコメント**が残っている（#95）。(3) のコメントは「サーバー側で `gaps` に記録済みだから落としてよい」という、Issue #89 自身が「記録には残るが画面には出ない状態は設計意図に合っていない」として明確に否定した論法だった。

**Action**: 握りつぶしを1件直すと決めたら、**着手前に**同じ関数の全 `continue` / 早期 return と、対になる画面の同じ責務の関数を読み、同型のものを列挙する。直せる範囲を決めたら、残りはその場で `gh issue create` する（PR 本文のメモで済ませない）。**別 Issue 側には、コードだけでなく「それを正当化しているコメント」も訂正対象として書く** — 否定された論法が根拠として残っていると、次の担当者がそれを正しいものとして受け取る。関連: [ACE-62-2](#ace-62-2)（同じ言い回しを grep して姉妹分岐へ同時適用する）。

### ACE-93-4: レビューで解決策が割れたら、まず両者が依拠している事実をソースで確認する

| フィールド | 値      |
| ---------- | ------- |
| Category   | process |
| Origin     | PR #93 / Issue #89 |
| Date       | 2026-08-20 |
| Helpful    | 1       |
| Harmful    | 0       |
| Status     | active  |

**Insight**: クロスモデルレビューで解決策が割れたとき、**どちらの案が良いかを比べる前に、両者が前提にしている事実を確認する**。割れる原因が「価値判断の違い」ではなく「片方（あるいは両方）が誤った事実に立っている」ことがあり、その場合は事実を確認した時点で選択問題そのものが消える。案の優劣を先に議論すると、誤った前提の上でどちらを採るかを延々と比べることになる。

**Context**: Codex が「全滅時に検索側の gap が捨てられている」と指摘し、解決策として `unanswered` の型に `gaps` を持たせることを提案した。一方 advisor は「型を拡張するな（AC は部分ケース・4ファイルに差分が及ぶ）」と述べており、解決策が真逆だった。事実だけを先に確認したところ、指摘（gap が捨てられている）は正しく、advisor はその半分を見落としていただけで、1行の修正で両立できた。さらに Toolkit が**もう一段深い事実の誤り**（[ACE-93-1](../playbook/architecture.md#ace-93-1)）を指摘し、それを `worker/core/operations.ts` で確認した結果、advisor が推奨し私が実装した改善そのものを撤回する判断になった。

**Action**: レビュー間で解決策が割れたら、(1) 各指摘が**主張している事実**と**提案している解決策**を分けて書き出す (2) 事実の側だけを、実装（該当ソース）を開いて確認する (3) 確認結果を持って改めて解決策を選ぶ。事実確認の結果、自分が既に実装した改善が空振りだと分かったら**撤回を選択肢に入れる** — 動いているコードを残す誘因が働くが、効かない分岐と誤った根拠コメントを出荷するほうが高くつく。判定に迷う場合は「この PR の受け入れ条件が要求しているか」で切り、要求していないものは別 Issue へ送る。

### ACE-138-2: API の応答が正しくても画面が壊れていることがある — 画面を出す変更は画面で確かめる

| Category | process | Origin | PR #138 / Issue #119・#120 |
| Date | 2026-08-22 |
| Helpful | 1 | Harmful | 0 |
| Status | active |

コア操作をスタブから D1 実照会（Text-to-SQL）へ差し替えた一連の PR で、検証はすべて `curl` によるコア操作の個別呼び出しだった。**個別に叩くとどれも `answered` を返す**ので、全部通っていた。

`npm run dev` でプラン画面を実際に生成したところ、**停留地が4件から1件に減っていた**。プラン画面は興味を「、」で連結して `intent` に送るため（「ラーメン、文化」）、スタブ時代は intent の内容を照合していなかった経路が、実照会では条件を全部満たそうとして0行になっていた。

### ACE-145-3: 「速くなった」は体感でなく、リクエストの開始時刻で示す

| Category | process | Origin | PR #145 / Issue #142 |
| Date | 2026-08-22 |
| Helpful | 0 | Harmful | 0 |
| Status | active |

並列化のような性能変更は「速くなった気がする」で終わりやすい。画面を出して確かめる（[ACE-138-2](#ace-138-2)）だけでは、**本当に同時に飛んでいるのか**は分からない。

`PerformanceResourceTiming` を読むと、その1点を数字で残せる。

```js
performance.getEntriesByType("resource").filter((e) => e.name.includes("/api/"))
  .map((e) => ({ n: e.name, start: Math.round(e.startTime), end: Math.round(e.responseEnd) }));
```

本番実測（2026-08-22・Version `c957fa38`）: `aggregate` 4本の `startTime` が `97442 / 97443 / 97443 / 97443` で、`search` から `provenance` 完了まで 1,786ms。同じ応答時間を直列に積むと約5.9秒。**開始時刻が揃っていること**が並列化の証拠で、合計時間だけではキャッシュが効いただけの可能性を排除できない。

測るときの落とし穴が2つある。

1. **興味チップは実クリックでないと変わらない** — `javascript_tool` の `element.click()` では `aria-pressed` が変わらない（本番ビルドで実測）。`computer` の ref クリックを使う。候補が1件しか出ない入力で測ると `aggregate` も1回しか飛ばず、並列化の検証としては空振りになる
2. **AI Gateway のキャッシュ** — 同じ入力を2回目に測ると 782〜942ms まで落ちる。未キャッシュの数字が要るなら興味の組み合わせを変える
