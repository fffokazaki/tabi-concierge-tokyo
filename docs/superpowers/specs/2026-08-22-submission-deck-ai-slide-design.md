# 提出資料 AI 技術スライド設計

## 1. 目的

提出資料の14枚構成を維持したまま、現行スライド9に分散している LLM データ取得の仕組みと、現行スライド14にある AI 仕様駆動開発を1枚へ統合する。同じスライドで、一次ユーザーが訪日外国人であること、日本の文化・マナーも案内すること、多言語対応予定であることを明確にする。

## 2. 採用案

Visual Companion で比較した3案のうち、A「2つのAIを上下で対比」を採用する。

- スライド枚数は14枚のまま
- スライド9を上下2レーンへ再構成
- 上段は「つくるAI」、下段は「届けるAI」
- スライド14から重複する開発スタイル帯を外し、チームメンバーと役割に集中させる

## 3. スライド9の構成

### 見出し

- **キッカー**: `仕組み ②　AI × OPEN DATA`
- **タイトル**: `AIでつくり、AIで届ける。`

### 上段: つくるAI

`docs/（SSOT） → Claude Code / Codex → 実装 → 検証`

- ラベル: `AI仕様駆動開発`
- 状態: `稼働中`
- 仕様、実装、検証の境界を1本の開発ループとして示す

### 下段: 届けるAI

`訪日外国人の自然文の質問 → メタデータRAG → Text-to-SQL / D1実照会 → 出典つき旅程・マナー`

- メタデータRAG、Text-to-SQL、D1実照会、出典強制は `稼働中`
- `多言語対応予定` は設計済み・未実装の色で表示する
- 多言語については「自然文をLLMで構造化する既存経路を活かして展開予定」と説明し、「簡単」「すぐできる」など未計測の工数は主張しない
- 興味チップだけの構造化入力はメタデータRAGを飛ばすため、全入力が4段を直列に通るようには描かない。詳細は発表者ノートまたは短い注記で限定する

### マナー情報の扱い

- 旅程・スポットの事実データは東京都オープンデータの出典を伴う
- マナーは JNTO 等の外部情報を `参考` として示し、オープンデータの `出典` と見た目・ラベルを分ける
- 「外国人が苦手な日本のマナー」と一般化せず、「訪日外国人が迷いやすい日本の文化・マナー」と表現する

## 4. 他スライドへの反映

- スライド3: 対象を `訪日外国人` と明示し、文化・マナーの壁を課題として維持する
- スライド5: プランが出典つき旅程とマナー案内を提供することを維持する
- スライド7: マナーの `参考` とオープンデータの `出典` を区別する説明を維持する
- スライド14: AI仕様駆動開発の帯を削除し、スライド9との重複を解消する

## 5. 状態境界

| 主張 | 状態 |
| --- | --- |
| AI仕様駆動開発 | 現在の開発方式 |
| メタデータRAG | 稼働中。ただし自然文入力時のみ |
| Text-to-SQL / D1実照会 | 稼働中 |
| 出典強制 | 稼働中 |
| マナー案内 | 稼働中。外部情報は `参考` として区別 |
| 多言語対応 | 対応予定。実装・動作検証は未実施 |

## 6. 実装対象

- `docs/submission-deck.md` を v1.11.0 へ更新
- `deck/build.js` を同じ文言と構成へ同期し、参照バージョンを v1.11.0 へ更新
- スライド14の開発スタイル帯を削除してレイアウトを戻す
- 既存の14枚構成、3層バッジ、配色、フォントを維持

## 7. 検証

- `npm run docs:check-agents-sync`
- リポジトリで定義された文書検証
- `cd deck && npm run build`
- 生成した PPTX をレンダリングし、スライド9と14を目視確認
- `submission-deck.md` のバージョンと `deck/build.js` 冒頭の参照バージョンが一致することを確認
- `多言語対応予定` が稼働中バッジになっていないことを確認
- `参考` と `出典` が混同されていないことを確認
