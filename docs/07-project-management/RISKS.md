# RISKS.md - リスク管理

## 1. リスク管理概要

### リスク管理方針

提出締切（2026-08-23 17:00）と First Stage 収録（2分厳守・ライブデモ不可）という**動かせない制約**が2つある。本書のリスクは「その2点に間に合うか」「間に合っても失格・減点にならないか」を軸に評価する。

### リスクレベル定義

| レベル | 定義 |
| ------ | ---- |
| 🔴 Critical | 発生すると提出不能・失格・強制終了に至る |
| 🟠 High | 提出はできるが、審査上の評価を大きく損なう |
| 🟡 Medium | 品質・完成度に影響するが回復可能 |
| 🟢 Low | 影響が限定的 |

## 2. 現在のリスク登録簿

### 🔴 Critical リスク

| ID | リスク | 影響 | 発生確率 | 対応 |
| -- | ------ | ---- | -------- | ---- |
| R-01 | First Stage の**2分超過による強制終了** | プレゼン後半（インパクト・クロージング）が届かない | 中 | 1分55秒着地で設計。台本は約620字に固定し、収録前に読み上げ計測する。スライドのタイムコードでペース配分 |
| R-02 | **ライブデモ実施**（規定違反） | 規定上不可。実施すれば審査に影響 | 低 | 動くデモは資料内に動画として埋め込む方針を全員で共有済み |
| R-03 | 提出締切（8/23 17:00）に資料・キャプチャが間に合わない | 提出不能 | 中 | モック（静止画＋カーソル操作）でも成立する構成にしてある。キャプチャはデモ動画のカット2・5・6から流用 |

### 🟠 High リスク

| ID | リスク | 影響 | 発生確率 | 対応 |
| -- | ------ | ---- | -------- | ---- |
| R-04 | **収録枠が早い者順で埋まる** | 希望日時で収録できず、準備期間が削られる | 中 | 提出フォーム送信直後に予約する（提出後のブラッシュアップは可） |
| R-05 | 利用オープンデータ10件リストが旧企画ベースのまま提出される | 資料の「③利用オープンデータ」と旅行アプリの中身が噛み合わない | 中 | 旅行アプリ主体の企画で使うデータセットをチームで確定する（[TASKS.md](./TASKS.md) Critical） |
| R-06 | カタログ外データ（都議会会議録等）を成果物に組み込んでしまう | 二次利用不可のデータの無断利用 | 低 | カタログ掲載データのみ組み込む。カタログ外は「将来の拡張構想」として語るに留める（[CONSTRAINTS.md](../01-context/CONSTRAINTS.md) §3） |
| R-07 | 著作権ルール違反（BGM 使用・帰属表示の欠落・いらすとや20個超） | 減点・修正要求 | 低 | BGM なし／地図は OpenStreetMap 系を優先／Google Map 使用時はロゴと帰属表示を残す |

### 🟡 Medium リスク

| ID | リスク | 影響 | 発生確率 | 対応 |
| -- | ------ | ---- | -------- | ---- |
| R-08 | **小規模店舗（ラーメン店等）のオープンデータ未カバー**（8/15 調査で確認済み） | 「あなたへ」推薦の説得力が落ちる | 高（確認済み） | 欠損を隠さず、「データ公開リクエストとして都へ還元」の実例として資料に組み込む |

| R-10 | MCP 最小実装が間に合わない | 技術力の訴求が図解のみになる | 中 | 資料上はアーキテクチャ図と役割説明で成立させ、実装は POC 範囲に絞る |

## 3. リスクカテゴリ別分析

### 技術リスク

R-10・R-11・R-12・R-13。いずれも POC スコープ（ADR-004）を受け入れたことの裏返しであり、「動的取り込みをやらない」判断とセットで管理する。

### 進行リスク

R-03・R-04。クリティカルパス（[ROADMAP.md](./ROADMAP.md) §5）上にあり、1日の遅延が収録枠の選択肢に直結する。

### コンプライアンスリスク

R-06・R-07。出典強制の設計（ADR-005）が R-06 の構造的な防御になっているが、資料内の画像・BGM・地図表示は設計の外側にあるため人的チェックが必要。

## 4. リスク対応戦略

| 戦略 | 適用リスク |
| ---- | ---------- |
| 回避 | R-02（ライブデモを行わない）、R-06（カタログ外データを組み込まない） |
| 軽減 | R-01（時間設計と事前計測）、R-03（モックで成立する構成）、R-09（提出直前の URL 更新） |
| 転化 | R-08（データ欠損を「還元の実例」という提案価値に変える） |
| 受容 | R-11・R-13（POC 前提として受け入れ、明示する） |

## 5. リスクトリガーと早期警告指標

| 監視指標 | 警告水準 | 対応 |
| -------- | -------- | ---- |
| 台本読み上げ実測時間 | 1分58秒を超えたら | 台本を削る（数字は「9,600 / 200PV / 30分→3分」の3つに絞る方針を維持） |
| 8/21 時点の画面イメージ進捗 | 未完了なら | モック構成に切り替える |
| 提出完了時刻 | 8/23 の午前中を過ぎたら | 収録枠の選択肢が狭まる前提で日程を再調整 |

## 6. コンティンジェンシープラン

| シナリオ | 代替行動 |
| -------- | -------- |
| MCP 実装が間に合わない | アーキテクチャ図＋役割説明で技術構成を示し、実装は Final Stage の到達目標として提示する |
| 画面イメージが完成しない | 既存 UI（日英2バージョン・動作確認済み）のキャプチャをそのまま使い、データ差し替えは1シナリオに絞る |
| 動画録画が間に合わない | 静止画＋カーソル操作のモック動画に切り替える（構成上成立するよう設計済み） |
| 収録が希望日で取れない | 8/29 の都内会場での対面収録を検討する |
